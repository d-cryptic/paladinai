## 1. Confidence Scoring & Calibration

### The Core Problem: LLMs Are Miscalibrated

When an LLM says "I am 90% confident", it does not statistically mean it will be correct 90% of the time. Raw LLM confidence scores are meaningless without calibration.

```
IDEAL CALIBRATION                    TYPICAL LLM (overconfident)

actual                               actual
correct                              correct
  1.0 ┤         ╭────────              1.0 ┤   ╭───────────────────
      │       ╭─╯                          │ ╭─╯
  0.8 ┤     ╭─╯                        0.8 ┤╭╯
      │   ╭─╯                              ╰╯
  0.6 ┤ ╭─╯                           0.6 ┤
      ╰─╯                                 │
  0.0 ┼──────────────                  0.0 ┼──────────────
      0.0  0.5  1.0                        0.0  0.5  1.0
      stated confidence                     stated confidence

Ideal: stated 80% → correct 80%      Reality: stated 90% → correct 65%
```

### Multi-Signal Composite Confidence

Do not use raw LLM confidence alone. Combine four signals:

```
┌─────────────────────────────────────────────────────────────┐
│                  CONFIDENCE COMPUTATION                      │
│                                                              │
│  LLM raw score ─────────────────────────┐                   │
│  (0.0–1.0 from model output)            │                   │
│                                         ▼                   │
│  Evidence completeness ─────────► WEIGHTED SUM ──► final   │
│  available_tools / requested_tools      ▲          score   │
│                                         │                   │
│  Historical accuracy ───────────────────┤                   │
│  correct / total for this intent type   │                   │
│                                         │                   │
│  Tool coverage ─────────────────────────┘                   │
│  1 - (failed_tools / total_tools)                           │
│                                                              │
│  final = w1×llm + w2×evidence + w3×history + w4×coverage   │
│                                                              │
│  Weights w1..w4 learned via logistic regression             │
│  on historical (prediction, outcome) pairs                  │
│  Start: w1=0.4, w2=0.25, w3=0.25, w4=0.10                  │
└─────────────────────────────────────────────────────────────┘
```

### Temperature Scaling (Calibration Fix)

```
RAW LLM CONFIDENCE
        │
        ▼
   logit(p) = ln(p / (1 - p))          convert to log-odds
        │
        ▼
   divide by T                          T = single scalar, learned from
        │                               validation data via NLL minimization
        ▼
   sigmoid(logit / T) = calibrated_p

   T > 1.0 → soften overconfident model (most common case)
   T < 1.0 → sharpen underconfident model
   T = 1.0 → no change

   Learn T from holdout set using scipy.optimize.minimize(NLL)
   Re-calibrate monthly as new ground truth accumulates
```

### Expected Calibration Error (ECE)

How we measure miscalibration in production:

```
Split predictions into 10 confidence buckets (0.0–0.1, 0.1–0.2, ... 0.9–1.0)

Example — Bucket 0.80–0.90:
  Predictions in bucket:  200
  Actually correct:       142     accuracy = 0.71
  Mean stated confidence: 0.84

  Calibration error for bucket = |0.71 - 0.84| = 0.13

ECE = Σ (|bucket_size| / n) × |accuracy(bucket) - confidence(bucket)|
    = weighted average across all buckets

Target: ECE < 0.05
Alarm:  ECE > 0.10 → recalibrate temperature scaling T
```

## 2. Alert Severity Classification

### Probabilistic Classification

Source severity from Alertmanager/Datadog is the starting point — not the final answer. Context adjusts it.

```
INPUT FEATURES                        LOGISTIC REGRESSION → SOFTMAX

base_severity (P1/P2/P3 encoded) ──┐
hour_of_day (0–23) ────────────────┤
traffic_percentile (0–100) ────────┤──► softmax(W×features + b) ──► P(P1) = 0.82
co_alert_count (firing now) ───────┤                                 P(P2) = 0.14
historical_p1_rate (this alert) ───┤                                 P(P3) = 0.04
time_since_last_incident (hours) ──┘
                                              │
                                              ▼
                                      classify as P1
                                      (argmax of probabilities)
                                      confidence = 0.82
```

### Confusion Matrix Tracking

```
                  PREDICTED
               P1     P2     P3
          P1 [450]   [32]   [ 5]   Precision_P1 = 450/469 = 0.96
ACTUAL    P2 [ 18]  [380]   [22]   Recall_P1    = 450/487 = 0.92
          P3 [  2]   [15]  [310]   F1_P1        = 0.94

Key rates to monitor continuously:
  False escalation rate (P3→P1):   2/327  = 0.006  → keep below 0.05
  Miss rate (P1→P3):               5/487  = 0.010  → keep below 0.02
  Overall accuracy:              1140/1182 = 0.965
```

### Severity EWMA Update

```
For each alert fingerprint, track historical severity rate:

new_rate = α × (was_it_P1_outcome) + (1-α) × old_rate
α = 0.1   ← slow moving average, stable estimate

Stored in PostgreSQL per alert fingerprint.
Used as feature historical_p1_rate in the classifier.
Updates after every incident resolution with confirmed severity.
```

### Multi-Factor Formula

```
Alert A fires ───────────────────────────────────────────────────┐
                                                                  │
              ┌──────────────────────────────────────────────┐   │
Alert B fires─┤           CORRELATION ENGINE                 │   │
              │                                              │   │
              │  label_overlap  = |A∩B| / |A∪B|  (Jaccard) │   │
              │  (same service, namespace, cluster?)         │   │
              │                           × α=0.35          │   │
              │                                              │   │
              │  time_proximity = exp(-λ × Δt_seconds)      │   │
              │  λ=0.005 → at Δt=300s: score=0.22           │   │
              │                           × β=0.30          │   │
              │                                              │   │
              │  co_occurrence  = P(B fires | A fired <5min)│   │
              │  (learned from historical incident data)     │   │
              │                           × γ=0.25          │   │
              │                                              │   │
              │  graph_distance = 1 / (FalkorDB_hops + 1)   │   │
              │  (1 hop→0.50, 2 hops→0.33, 3 hops→0.25)    │   │
              │                           × δ=0.10          │   │
              │                                              │   │
              │  TOTAL > 0.65 → CORRELATE (configurable)    │   │
              └──────────────────────────────────────────────┘   │
                               │                                  │
                               ▼                                  │
                    SAME INCIDENT ◄───────────────────────────────┘
```

## 4. Anomaly Detection — Full Suite

All methods run inside `mcp-prometheus` (and equivalent MCP servers) before returning data to the agent. The agent receives a statistical summary, not raw time series.

### Method 1 — Z-Score (Point Anomalies)

```
METRIC TIME SERIES

value
  95 ┤                          ●  ← ANOMALY
  80 ┤               ●
  65 ┤     ●   ●         ●
  50 ┤ ●          ●              ●
  35 ┤
     ┼──────────────────────────── time

mean_30d = 55, σ_30d = 12.8

z = (95 - 55) / 12.8 = 3.12   → anomalous (|z| > 3.0)

Output to agent (not raw data):
"CPU spike to 95% — 3.1σ above 30-day rolling baseline (μ=55%, σ=12.8%)"

Token reduction: 3600 data points → 1 sentence
```

### Method 2 — EWMA Control Chart (Sustained Shifts)

```
Detects gradual creep that z-score misses (e.g., slow memory leak)

EWMA_t = λ × x_t + (1 - λ) × EWMA_{t-1}      λ=0.2

Upper control limit: UCL = μ₀ + 3σ × √(λ / (2-λ))
Lower control limit: LCL = μ₀ - 3σ × √(λ / (2-λ))

value
  70 ┤         ╭────────────────── raw values creeping up
  60 ┤─────────╯
     ├──────────────────────── UCL (crossed = anomaly)
  65 ┤.............................
  55 ┤  EWMA ──────────────────────
  45 ┤.............................
     └───────────────────────── LCL
     
EWMA crosses UCL → sustained shift detected → ALARM
Catches: memory leaks, gradual disk fill, slow connection pool drain
```

### Method 3 — Seasonal Decomposition (STL)

```
PROBLEM: Raw metrics have daily/weekly patterns that look like anomalies

RAW CPU METRIC (high every Monday 9am — normal business pattern)
  │
  ▼  STL decompose (Seasonal-Trend decomposition using LOESS)

┌─────────────────────────────────────────────┐
│ Trend:       ─────────────────╱─────────    │ slowly increasing baseline
│ Seasonality: ╭─╮╭─╮╭─╮╭─╮╭─╮╭─╮╭─╮╭─╮    │ weekly pattern
│ Residual:    ~tiny noise~  ●← THIS IS       │ run anomaly detection HERE
│                              THE ANOMALY   │
└─────────────────────────────────────────────┘

Anomaly on residual = true anomaly, not "Monday morning traffic spike"
Prevents false P1 alerts every Monday at 9am
```

### Method 4 — CUSUM (Changepoint Detection)

```
Cumulative sum control chart — detects sustained mean shifts

S⁺(t) = max(0, S⁺(t-1) + (x_t - μ₀ - k))    ← detects upward shift
S⁻(t) = max(0, S⁻(t-1) - (x_t - μ₀ + k))    ← detects downward shift

k = allowable slack = 0.5 × (shift_to_detect)
h = decision threshold = 5σ

Example: detecting +10ms shift in API latency (μ₀=45ms, σ=8ms, k=4, h=40)

S⁺
  40 ┤────────────────────────────────╮  ← ALARM
     │                               ╭╯
  20 ┤                         ╭────╯
     │                    ╭───╯
   0 ┤──────────────╮────╯
     ├──────────────────────────────── time
     Day1          Day2         Day3

Detects regime change 3× faster than Shewhart chart for small shifts
Use for: slow DB degradation, gradual memory pressure, network congestion
```

### Method 5 — Granger Causality (Metric Relationships)

```
QUESTION: Does metric A predict metric B with time lag L?

Test: does adding past values of A improve prediction of B
      beyond just B's own history?

VAR model comparison:
  Restricted:   B_t = c + Σ β_i × B_{t-i} + ε
  Unrestricted: B_t = c + Σ β_i × B_{t-i} + Σ γ_i × A_{t-i} + ε

F-statistic on γ_i coefficients:
  p < 0.05 → A Granger-causes B at lag L

Discovered causal graph stored in FalkorDB:
  (:Metric{name:"gc_pause_ms"})
    -[:PREDICTS{lag_seconds:120, correlation:0.91, p_value:0.0003}]->
  (:Metric{name:"api_latency_p99"})

During RCA:
  "API latency spiked at 14:32 UTC.
   GC pause time spiked at 14:30 UTC (2min earlier, Granger r=0.91, p<0.001).
   Root cause: GC pressure from recent deployment."
```

### Method 6 — Multivariate Anomaly (Mahalanobis Distance)

```
PROBLEM: Three metrics each look normal individually, but together are anomalous

Normal baseline:    CPU=45%, mem=60%, disk_io=30%   (correlated — they move together)
Current:            CPU=90%, mem=92%, disk_io=85%   (all high simultaneously)

Mahalanobis distance accounts for correlations between metrics:

D² = (x - μ)ᵀ Σ⁻¹ (x - μ)

where Σ = covariance matrix of [CPU, mem, disk_io] from 30-day baseline

D² = 1.2  → normal (within expected correlation envelope)
D² = 18.4 → anomalous

Threshold: chi-squared critical value χ²(df=3, α=0.001) = 16.27
D² > 16.27 → multivariate anomaly → alert

Catches: resource exhaustion cascades that no single metric threshold catches
```

## 6. RAG Quality Metrics & Thresholds

### The Retrieval Quality Pyramid

```
              ┌──────────┐
              │  NDCG@5  │  ← best result ranked first?
              └────┬─────┘
             ┌─────┴──────┐
             │    MRR     │  ← where does correct result appear?
             └─────┬──────┘
            ┌──────┴───────┐
            │  Recall@k    │  ← is correct result in top-k at all?
            └──────┬───────┘
           ┌───────┴────────┐
           │  Precision@k   │  ← of top-k results, how many relevant?
           └────────────────┘
```

### NDCG@5 — Ranking Quality

```
Ideal ranking:  [✓, ✓, ✓, ✗, ✗]
  Ideal DCG = 1/log₂(2) + 1/log₂(3) + 1/log₂(4) = 1 + 0.63 + 0.50 = 2.13

Actual ranking: [✓, ✗, ✓, ✗, ✓]
  Actual DCG = 1/log₂(2) + 0 + 1/log₂(4) + 0 + 1/log₂(6) = 1 + 0.50 + 0.39 = 1.89

NDCG@5 = actual DCG / ideal DCG = 1.89 / 2.13 = 0.89

Target NDCG@5 ≥ 0.75
Alarm  NDCG@5 < 0.60 → re-embed runbook corpus with updated BGE-M3
```

### MRR — Mean Reciprocal Rank

```
Query 1: correct runbook at position 1 → 1/1 = 1.00
Query 2: correct runbook at position 3 → 1/3 = 0.33
Query 3: correct runbook at position 2 → 1/2 = 0.50
Query 4: correct runbook not in top 5  → 1/∞ = 0.00

MRR = (1.00 + 0.33 + 0.50 + 0.00) / 4 = 0.46

Target MRR ≥ 0.70
```

### Similarity Threshold Calibration

```
PRECISION-RECALL TRADEOFF (calibrated on labeled query-runbook pairs)

precision
  1.0 ┤╮
      │ ╰─╮
  0.9 │    ╰─╮  ← 0.92 threshold (semantic cache)
      │       ╰──╮
  0.8 │           ╰──╮  ← 0.78 threshold (episodic memory)
      │               ╰──╮
  0.7 │                   ╰──╮  ← 0.75 threshold (runbook retrieval)
      │                       ╰───╮
  0.6 │                            ╰──── ← 0.60 threshold (reranker min)
      ┼────────────────────────────────── recall
      0.5  0.6  0.7  0.8  0.9  1.0

Semantic cache: highest precision required (wrong cache hit = wrong answer served)
Episodic memory: looser (similar past incident is directionally useful even if not identical)
Runbook retrieval: below 0.75, say "no runbook found" → safer than hallucinating from irrelevant content
```

### Full Threshold Table for Retrieval

| Use Case | Threshold | Rationale |
|---|---|---|
| Semantic cache hit | cosine ≥ 0.92 | Wrong cache hit costs more than cache miss |
| Episodic memory match | cosine ≥ 0.78 | Similar past incident is directionally useful |
| Runbook retrieval min | score ≥ 0.75 | Below this: no retrieval > wrong retrieval |
| Reranker top-1 min | score ≥ 0.60 | Top-1 must clear this or skip retrieval entirely |

## 7. Hypothesis Scoring — Bayesian Approach

### Ranking Competing Hypotheses

```
INCIDENT: payments-api down, DB connection errors observed

THREE COMPETING HYPOTHESES:
  H1: DB connection pool exhausted
  H2: Memory leak in payments-service
  H3: Network partition between pods

BAYES THEOREM:
  P(Hᵢ | evidence) ∝ P(evidence | Hᵢ) × P(Hᵢ)
                       ─────────────────   ──────
                          likelihood        prior

PRIORS (from historical incidents for this alert fingerprint):
  P(H1: conn pool) = 0.34  ← most common historically
  P(H2: mem leak)  = 0.22
  P(H3: network)   = 0.08
  P(other)         = 0.36

LIKELIHOODS (how well does evidence support each hypothesis?):
  Evidence: high connection_wait_time + low pg_stat_activity_available
  P(evidence | H1) = 0.91  ← this evidence strongly implies conn pool
  P(evidence | H2) = 0.31
  P(evidence | H3) = 0.15

POSTERIORS (unnormalized):
  H1: 0.91 × 0.34 = 0.309
  H2: 0.31 × 0.22 = 0.068
  H3: 0.15 × 0.08 = 0.012
  Sum = 0.389

NORMALIZED:
  P(H1 | evidence) = 0.309/0.389 = 0.79  ← investigate first
  P(H2 | evidence) = 0.068/0.389 = 0.17
  P(H3 | evidence) = 0.012/0.389 = 0.03

RCA Agent Phase 1 output:
  "Primary hypothesis: DB connection pool exhaustion (confidence: 79%)
   Requesting targeted verification: SELECT count(*) FROM pg_stat_activity..."
```

### Bayesian Update After Phase 2 Evidence

```
Phase 2 targeted query returns:
  pg_stat_activity: 497/500 connections in use
  
New likelihood P(evidence_phase2 | H1) = 0.99  (near-certain confirmation)

Updated posterior:
  P(H1 | all_evidence) ≈ 0.97

Phase 3 skipped (confidence 0.97 > 0.85 threshold)
Resolution time saved: ~4-6 seconds
```

### Prior Update After Each Incident

```
After incident resolved with confirmed root cause:

if root_cause == H1:
    count_H1_correct[alert_fingerprint] += 1
    
new_prior = (alpha + count_H1_correct) / (alpha + beta + total_incidents)
alpha = 1, beta = 1  (Laplace smoothing, prevents zero probabilities)

Priors update automatically. After 50 incidents with this fingerprint,
the prior reflects actual observed frequencies for this specific system.
```

## 8. Information Theory — Alert Informativeness

### Shannon Entropy for Alert Stream Quality

```
A healthy alert stream has uncertainty (high entropy).
An alert-fatigued stream is predictable (low entropy).

Example — Tenant with well-tuned alerts:
  P(P1) = 0.10, P(P2) = 0.30, P(P3) = 0.60

  H = -(0.10×log₂(0.10) + 0.30×log₂(0.30) + 0.60×log₂(0.60))
  H = -(−0.33 + −0.52 + −0.44) = 1.29 bits

Example — Alert-fatigued tenant:
  P(P1) = 0.01, P(P2) = 0.04, P(P3) = 0.95

  H = 0.29 bits  ← nearly all alerts are P3 noise

Maximum entropy (uniform P1/P2/P3) = log₂(3) = 1.58 bits

Alert noise ratio = 1 - (H / H_max)
Report to tenant dashboard: "Your alert stream is 82% noise. 
Recommendation: tighten P3 thresholds or add suppression rules."
```

### Mutual Information for Feature Selection

```
I(feature ; root_cause) = Σ p(x,y) × log(p(x,y) / (p(x)×p(y)))

High I(alert_name ; root_cause) → alert_name is a good predictor
Low  I(alert_name ; root_cause) → alert_name is noise for classification

Use to rank which features matter most in the severity classifier.
Recompute monthly. Features that lose predictive power → remove.
```

## 10. Statistical Process Control (SPC)

### CUSUM Control Chart in Detail

```
Goal: detect +10ms sustained shift in API latency (μ₀=45ms, σ=8ms)

Parameters:
  k = 0.5 × (shift_size / σ) = 0.5 × (10/8) = 0.625 → use k=5ms (in original units)
  h = 5σ = 40ms (decision threshold)

S⁺(t) = max(0, S⁺(t-1) + (x_t - μ₀ - k))

t=1: x=47 → S⁺ = max(0, 0 + (47-45-5)) = max(0,-3) = 0
t=2: x=52 → S⁺ = max(0, 0 + (52-45-5)) = 2
t=3: x=54 → S⁺ = max(0, 2 + (54-45-5)) = 6
t=4: x=58 → S⁺ = max(0, 6 + (58-45-5)) = 14
t=5: x=61 → S⁺ = max(0, 14 + (61-45-5)) = 25
t=6: x=65 → S⁺ = max(0, 25 + (65-45-5)) = 40 → ALARM (S⁺ = h)

S⁺
  40 ┤─────────────────────────────●  ← ALARM
     │                          ╭─╯
  20 ┤                       ╭──╯
     │                    ╭──╯
   0 ┤────────────────────╯
     ┼───────────────────────────────
     t1    t2    t3    t4    t5    t6

ARL₀ (average run length under control) = 370 (false alarm rate = 1/370)
```

## 11. Graph Statistics — Service Dependency Intelligence

### Betweenness Centrality (Blast Radius Prediction)

```
SERVICE DEPENDENCY GRAPH

        payments-api ────────────────────────┐
         /        \                          │
      auth-svc   db-primary ← HIGH          │
         \        /          CENTRALITY      │

             │
         rate-limiter

Betweenness centrality of node v:
  C_B(v) = Σ σ(s,t|v) / σ(s,t)   for all pairs (s,t)
  where σ(s,t) = total shortest paths from s to t
        σ(s,t|v) = those passing through v

api-gateway: C_B = 0.51
rate-limiter: C_B = 0.08

```

```
Iteration:
```

## 14. LLM Cost-Quality Routing

### Difficulty Scoring

```
difficulty_score =
  0.30 × intent_complexity      (lookup=0.0, single_hop=0.3, multi_hop=1.0)
+ 0.25 × normalized_tool_count  (tool_count / max_observed_tools)
+ 0.20 × context_length_pct     (input_tokens / model_max_context)
+ 0.15 × urgency                (P3=0.0, P2=0.5, P1=1.0)
+ 0.10 × historical_fail_rate   (how often cheaper model failed on this intent)

Routing:
  difficulty < 0.30 → Tier A (Groq / cheap Chinese model via OpenRouter)
  difficulty < 0.65 → Tier B (mid-tier: Qwen3-72B, Claude Sonnet)
  difficulty ≥ 0.65 → Tier C (DeepSeek-R1, Claude Opus, GPT-5)
```

### Cost Per Quality Point

```
At each tier, track:
  cost_per_incident = avg_input_tokens × price_in + avg_output_tokens × price_out
  quality_score = weighted_accuracy (ECE-calibrated)

Cost-quality frontier:

quality
  0.95 ┤                      ● Tier C ($0.22/incident)
       │                 ●
  0.88 ┤           ● Tier B ($0.08/incident)
       │       ●
  0.81 ┤  ● Tier A ($0.01/incident)
       ┼──────────────────────────── cost per incident
       $0   $0.05  $0.10  $0.20

Route P1 to Tier C (accuracy worth cost for critical incidents)
Route P3 to Tier A (diminishing returns from expensive model)
```

### Multi-Armed Bandit (v2.1 Roadmap)

```
Thompson Sampling per (intent_type, model_tier) arm:

Maintain Beta(α, β) distribution per arm:
  α = successes (correct + within latency budget)
  β = failures  (wrong, slow, or expensive)

At routing time:
  Sample θᵢ ~ Beta(αᵢ, βᵢ) for each candidate model
  Route to model with highest θᵢ

After outcome:
  Success → αᵢ += 1
  Failure → βᵢ += 1

Effect: naturally explores cheaper models when they perform well,
        falls back to expensive models when quality drops.
        No manual threshold tuning required.

Implement in v2.1 after 30 days of difficulty_score data collected.
```


## 16. Evaluation Statistics

### McNemar's Test (Model Comparison)

```
When comparing current model vs new model on same test set:

              New model
              Correct   Wrong
Current  Correct [430]   [20]  ← b = 20 (new wrong, current right)
model    Wrong   [35]   [15]  ← c = 35 (new right, current wrong)

McNemar statistic:
  χ² = (|b - c| - 1)² / (b + c) = (|20 - 35| - 1)² / (20 + 35) = 3.27
  p-value = 0.071

p > 0.05 → NOT statistically significant → do not deploy new model
p < 0.05 → significant improvement → safe to deploy

Never deploy without this test. "Looks better on a few examples" is not sufficient.
```

### Bootstrap Confidence Intervals

```
Observed accuracy on test set (n=500): 0.876

Bootstrap procedure (1000 iterations):
  1. Sample 500 examples WITH replacement from test set
  2. Compute accuracy on sample
  3. Repeat 1000×
  4. 95% CI = [2.5th percentile, 97.5th percentile] of distribution

Result: Accuracy = 0.876 (95% CI: 0.851, 0.901)

Model A: 0.876 [0.851, 0.901]
Model B: 0.903 [0.881, 0.924]

CIs do not overlap → Model B is genuinely better.
CIs overlap → cannot conclude improvement with confidence.
```

### Cohen's Kappa (Label Reliability)

```
Before training models on RCA labels, verify labels are reliable.
Have two engineers independently label 100 incidents.

              Engineer B
              H1    H2    H3
Engineer  H1 [45]   [3]   [1]   ← 45 agreements on H1
A         H2  [2]  [38]   [4]
          H3  [0]   [2]  [35]

P_observed = (45+38+35)/130 = 0.906
P_expected = (49×47 + 44×43 + 40×35) / 130² = 0.333

κ = (0.906 - 0.333) / (1 - 0.333) = 0.86

κ interpretation:
  κ > 0.80 → strong agreement → labels are reliable → proceed with training
  κ 0.60-0.80 → moderate → review labeling guidelines
  κ < 0.60 → poor → do not train models, fix labeling criteria first
```

## 17. Memory Relevance Decay

### Time-Weighted Retrieval

```
RELEVANCE DECAY CURVES BY INCIDENT TYPE

relevance
  1.00 ┤●
       │ ╲ Infrastructure (λ=0.05/day) — infra stays similar
       │  ╲────────────────────────────
  0.60 ┤        ●

       │                    ╲────────────

  0.00 ┼─────────────────────────────────────────── age (days)
       0      7      14      21      30      60

relevance(t) = exp(-λ × t_days)

Final retrieval score:
  score = cosine_similarity × relevance(incident_age_days)

Example: incident from 45 days ago, cosine=0.89 (infra type, λ=0.05)
  score = 0.89 × exp(-0.05 × 45) = 0.89 × 0.105 = 0.094
  Below episodic threshold 0.78 → not retrieved (too old to be useful)
```
