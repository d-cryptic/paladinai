# Stage 3 — Agent Runtime (Eino)

**Date:** 2026-05-10
**Status:** Decisions locked (stage 3 complete)
**Scope:** Agent graph design, multi-agent structure, tool calls, streaming, checkpointing

---

## Decision 1 — Framework: Eino

**Eino** (CloudWeGo/ByteDance, Apache 2.0). Go-native, production at ByteDance scale.

Key primitives used:

| Primitive | Purpose |
|---|---|
| `compose.Graph` | State machine with typed nodes and conditional edges |
| `schema.ChatModel` | LLM interface — we implement this wrapping `paladin-gateway` |
| `schema.Tool` | Tool definition (unused directly — tools come from paladin-hub) |
| `compose.Lambda` | Arbitrary Go function as a graph node |
| `graph.Stream()` | Streaming execution, emits chunks via channel |

We do **not** use Eino's built-in LLM providers. We implement `schema.ChatModel` as an HTTP client to `paladin-gateway`. Eino stays completely decoupled from provider details.

---

## Decision 2 — Graph Style: Explicit Graph (not ReAct)

**Explicit graph with fixed nodes and edges.**

ReAct lets the LLM decide each next step — more flexible but unpredictable. For an ops tool that can take real actions (restart pods, silence alerts, scale deployments), predictability is non-negotiable. Every execution path is known, auditable, and testable.

ReAct is appropriate for open-ended research agents. It is not appropriate for incident response.

---

## Decision 3 — Multi-Agent Structure

Five specialized agents. All are Eino graphs. All run inside `paladin-agent` (same binary).

| Agent | Trigger | LLM Tier | Purpose |
|---|---|---|---|
| Supervisor | Every alert | A (Groq, fast) | Classify + route to worker |
| TriageAgent | P2/P3 alerts | A + B | Parallel tool calls + initial response |
| RCAAgent | P1 alerts | C only (Opus) | Structured 3-phase root cause analysis |
| RunbookAgent | Runbook execution steps | B | Multi-step runbook with checkpointing |
| CommsAgent | Post-resolution | A | Draft + send Slack/PD notifications |

**Why same binary, not separate services:**
- Agent handoffs are function calls — sub-millisecond, no network hop
- KEDA scales `paladin-agent` pods; each pod runs all agent types
- Different resource profiles (GPU vs CPU) would justify separation — we don't have that here
- Simplicity: one deployment, one log stream, one trace context

## Decision 4 — Shared State Struct

Every graph node reads and writes this. Fully typed — no `interface{}` or `map[string]any` in the hot path:

```go
type IncidentState struct {
    // Immutable input context
    TenantID   string
    Alert      AlertEnvelope
    Incident   IncidentRecord

    // Classification output (Supervisor)
    Intent     string   // "log_analysis" | "metric_spike" | "service_down" | "oom" | ...
    AgentType  string   // "triage" | "rca" | "runbook"
    Severity   string   // "p1" | "p2" | "p3"

    // Tool layer
    Tools       []ToolSchema  // from paladin-hub DiscoverTools()
    ToolResults []ToolResult  // indexed by tool name

    // Memory layer
    MemoryCtx MemoryContext   // episodic matches + procedural runbook chunks

    // RCA-specific (multi-hop)
    Hypothesis     string
    HopCount       int
    Confidence     float32  // 0.0-1.0, gating Phase 3

    // LLM output
    Response        string
    ProposedActions []Action
    BlastRadius     []string  // affected services

    // Control
    Step       string
    NeedsHuman bool       // pause graph for approval signal
    Error      error

    // Observability
    CheckpointID string
    SessionID    string   // NATS stream subject suffix
    TraceID      string   // OTel propagation
}
```

## Decision 5 — Supervisor Graph

Entry point for every alert. Runs first, routes to the correct worker.

```
START
  │
  ▼
[enrich]
  Load incident record from PG
  Load tenant config (LLM tier overrides, routing rules)
  Load working memory from Valkey
  │
  ▼
[classify]
  LLM: Tier A (Groq llama-3.3-70b, fast)
  Input: alert normalized fields + tenant context
  Output: intent, agent_type, severity
  │
  ▼ (conditional edge on agent_type)
  ├─ "rca"     → RCAAgent graph
  ├─ "runbook" → RunbookAgent graph
  └─ "triage"  → TriageAgent graph
                      │
                      ▼
               [collect_result]
               Merge worker output into supervisor state
                      │
                      ▼
               [comms]
               CommsAgent: draft + send notification
                      │
                      ▼
               [close]
               Write final incident state to PG
               Emit step_end event to NATS
                      │
                      ▼
                     END
```

## Decision 6 — TriageAgent Graph (P2/P3)

Target P95: **<5s**

```
START
  │
  ▼
[discover_tools]
  paladin-hub.DiscoverTools(intent, tenant_id, top_k=6)
  Returns: []ToolSchema with MCP server endpoint per tool
  │
  ▼
[parallel_tool_calls]
  goroutines via errgroup — all 6 tools fire simultaneously
  Retry policy: 1 retry with 2s timeout if first attempt fails
  Partial results acceptable — tool errors captured per-result
  Latency: max(individual tool latencies), not sum
  │
  ▼
[memory_retrieval]
  paladin-memory.Search(episodic, similar past incidents, top_k=3)
  paladin-memory.Search(procedural, relevant runbook chunks, top_k=3)
  Runs in parallel with tool calls if possible (early trigger)
  │
  ▼
[synthesize]
  LLM: Tier B (claude-sonnet-4-5, advanced tool use beta)
  Input: alert + tool results + memory context + gap notation for failed tools
  Streams tokens → NATS stream.{tenant}.{session_id}
  │
  ▼
[checkpoint]
  Write IncidentState to PG checkpoint table
  │
  ▼
END
```

## Decision 7 — RCAAgent Graph (P1 only)

Target P95: **<20s** (accuracy over speed for P1)

Three structured phases. Hard cap: 3 LLM hops total.

```
START
  │
  ▼
[broad_signal_gather]
  Parallel tool calls — broad sweep:
    mcp-prometheus: query_range last 2h (key services)
    mcp-loki: tail last 15min (error patterns)
    mcp-k8s: describe affected pods + recent events
    mcp-prometheus: recent deployments / config changes
    paladin-memory: similar past P1 incidents (episodic, top_k=5)
    paladin-memory: architecture topology (semantic)
  │
  ▼
[hypothesis]                              ← LLM HOP 1
  LLM: Tier C (claude-opus-4-7)
  Input: all broad signals + past incident context
  Output:
    - hypothesis (natural language)
    - targeted_queries: []ToolCall  (specific follow-up tool calls)
    - confidence: float32
  Emits: "hypothesis formed" event → NATS
  │
  ▼
[targeted_signal_gather]
  Execute targeted_queries from hypothesis output
  Parallel goroutines — hypothesis-driven, narrow, specific
  Same retry policy: 1 retry at 2s
  │
  ▼
[verify]                                  ← LLM HOP 2
  LLM: Tier C (claude-opus-4-7)
  Input: hypothesis + targeted signal results
  Output:
    - root_cause (confirmed or refuted)
    - confidence: float32
    - blast_radius: []string
    - recommended_actions: []Action
  │
  ▼ (conditional edge on confidence)
  ├─ confidence ≥ 0.85 → [synthesize]    (skip hop 3)
  └─ confidence < 0.85 → [refine_gather] → [synthesize]  ← LLM HOP 3 (if needed)
  │
  ▼
[synthesize]
  Assembles final RCA report
  If reached via low-confidence path: flags "low confidence — human review recommended"
  Streams full report → NATS
  │
  ▼
[checkpoint]
  │
  ▼
END
```

**Why 3 hops and not 1:**

A single LLM call with broad signals cannot perform hypothesis verification. It either skips verification (hallucinated root cause) or tries to reason from noisy broad data (low accuracy). Phase 2 tool calls are hypothesis-driven — instead of querying all metrics for 2 hours, you query the specific service, specific metric, specific 10-minute window the hypothesis points at. Signal quality is dramatically higher.

**Confidence gating:** Straightforward P1s (clear root cause, high-confidence Phase 2) skip Phase 3 and resolve faster. Complex cascading failures go through all 3 hops. The hard cap at 3 prevents runaway cost. After the cap, synthesize with available data and flag for human review.

**Cost per P1 incident (Tier C):** ~3 hops × 5K tokens = ~$0.20-0.30. Justified for P1.

## Decision 8 — RunbookAgent Graph

Handles multi-step runbook execution. Each step is checkpointed independently — pod death mid-runbook resumes at the last completed step.

```
START
  │
  ▼
[load_runbook]
  paladin-memory.Search(procedural, incident context, top_k=1)
  Returns: structured runbook with steps[]
  │
  ▼
[step_loop] ──────────────────────────────────────┐
  │                                               │
  ▼                                               │
[plan_step]                                       │
  LLM: Tier B (claude-sonnet-4-5)                 │
  Input: current step definition + system state   │
  Output: tool_calls[] to execute this step       │
  │                                               │
  ▼ (conditional edge)                            │
  ├─ step.requires_approval == true               │
  │      ▼                                        │
  │  [await_approval]                             │
  │  Emit "approval_required" → NATS              │
  │  Hatchet signal wait (blocks until human acts)│
  │  Browser sends approve/reject over WebSocket  │
  │  paladin-ws → NATS runbook.{tenant}.{id}.approval
  │      ▼                                        │
  │  [handle_decision]                            │
  │  reject → [abort] → END                       │
  │  approve → continue                           │
  │                                               │
  ▼                                               │
[execute_step]                                    │
  Parallel tool calls for this step               │
  │                                               │
  ▼                                               │
[verify_step]                                     │
  LLM: Tier B — did step succeed? retry? abort?   │
  │                                               │
  ▼ (conditional)                                 │
  ├─ success + more steps → checkpoint → ─────────┘ (loop)
  ├─ success + no more steps → [complete]
  └─ failure → [handle_failure]
                  ├─ retry (max 2) → loop
                  └─ escalate → CommsAgent → END
```

## Decision 9 — Parallel Tool Calls

Go's goroutines make this natural. No async/await ceremony:

```go
func (a *Agent) parallelToolCalls(
    ctx context.Context,
    state IncidentState,
) (IncidentState, error) {
    results := make([]ToolResult, len(state.Tools))
    g, ctx := errgroup.WithContext(ctx)

    for i, tool := range state.Tools {
        i, tool := i, tool
        g.Go(func() error {
            res, err := a.callWithRetry(ctx, tool)
            if err != nil {
                // Partial failure: capture, do not abort
                results[i] = ToolResult{Tool: tool.Name, Error: err.Error()}
                return nil
            }
            results[i] = ToolResult{Tool: tool.Name, Data: res}
            return nil
        })
    }

    _ = g.Wait()
    state.ToolResults = results
    return state, nil
}

func (a *Agent) callWithRetry(ctx context.Context, tool ToolSchema) (json.RawMessage, error) {
    // First attempt: full timeout
    ctx1, cancel1 := context.WithTimeout(ctx, 8*time.Second)
    defer cancel1()
    res, err := a.mcpClient.Call(ctx1, tool.Endpoint, tool.Name, tool.Params)
    if err == nil {
        return res, nil
    }
    // One retry with tight timeout — catches transient failures during incidents
    ctx2, cancel2 := context.WithTimeout(ctx, 2*time.Second)
    defer cancel2()
    return a.mcpClient.Call(ctx2, tool.Endpoint, tool.Name, tool.Params)
}
```

Total latency = slowest single tool. 6 tools at 200ms each = **200ms total**, not 1200ms.

## Decision 10 — Tool Call Partial Failure Policy

**Retry once (2s tight timeout), then continue with partial data.**

- First attempt timeout: 8s
- Single retry timeout: 2s (tight — catches transient, doesn't wait for dead services)
- After retry failure: capture error in `ToolResult.Error`, continue
- Synthesis prompt explicitly notes gaps:

```
Available signals: prometheus ✓, loki ✓, k8s ✓
Unavailable:       datadog (timed out after retry)

Analyze based on available signals. Flag what could not be assessed and
adjust confidence score accordingly.
```

Rationale: during infrastructure incidents, monitoring tools are themselves under stress. A transient 300ms timeout resolves on retry ~70% of the time. Aborting on any tool failure is too fragile for an ops tool.

## Decision 11 — Streaming Events to NATS

Every graph node emits structured events. Browser sees agent progress in real-time:

```go
type AgentEvent struct {
    Type      string    // "step_start" | "token" | "tool_call" | "tool_result" | "step_end" | "error" | "approval_required"
    Step      string    // graph node name
    Content   string    // token text, description, or tool result summary
    ToolName  string    // when type == "tool_call" or "tool_result"
    Metadata  map[string]string
    Timestamp time.Time
}
```

Published to `stream.{tenant}.{session_id}` → push consumer in `paladin-ws` → WebSocket to browser.

What the user sees in the UI:
```
● Analyzing incident...
  → Discovering relevant tools
  → Querying Prometheus (last 2h)   ✓ 340ms
  → Tailing Loki logs               ✓ 280ms
  → Checking K8s pod state          ✓ 190ms
  → Searching past incidents        ✓ 120ms
  → Forming hypothesis...
  → Hypothesis: connection pool exhaustion on payments-db
  → Running targeted verification...
  → Root cause confirmed (confidence: 0.91)
  ▶ Generating RCA report...
```

## Decision 12 — Checkpointing

After each significant node, serialize `IncidentState` to PG:

```sql
CREATE TABLE incident_checkpoints (
    id          TEXT PRIMARY KEY,        -- uuid v7
    incident_id TEXT NOT NULL,
    tenant_id   TEXT NOT NULL,
    step        TEXT NOT NULL,           -- graph node that just completed
    state       JSONB NOT NULL,
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX ON incident_checkpoints (incident_id, created_at DESC);
```

On pod death:
1. NATS redelivers the work item
2. Agent queries: `SELECT state FROM incident_checkpoints WHERE incident_id = $1 ORDER BY created_at DESC LIMIT 1`
3. Resumes from last completed step

No work is lost. Runbook steps that were approved by a human are not re-requested.

## Decision 13 — LLM Integration via paladin-gateway

We implement Eino's `schema.ChatModel` interface as an HTTP client to `paladin-gateway`:

```go
type GatewayModel struct {
    client   *http.Client
    endpoint string   // http://paladin-gateway/v1/chat
    model    string   // "fast" | "smart" | "deep" (aliases resolved by gateway)
    tenantID string   // injected as header for cost tracking
}

// Implements schema.ChatModel
func (m *GatewayModel) Generate(ctx context.Context, msgs []*schema.Message, opts ...model.Option) (*schema.Message, error) { ... }
func (m *GatewayModel) Stream(ctx context.Context, msgs []*schema.Message, opts ...model.Option) (*schema.StreamReader[*schema.Message], error) { ... }
```

Each agent node instantiates the correct tier:
```go
// Supervisor classify node
classifyModel := &GatewayModel{model: "fast", tenantID: state.TenantID}

// Triage synthesize node
synthesizeModel := &GatewayModel{model: "smart", tenantID: state.TenantID}

// RCA nodes
rcaModel := &GatewayModel{model: "deep", tenantID: state.TenantID}
```

Gateway resolves aliases → handles provider routing, circuit breakers, semantic cache, cost tracking. Agents know nothing about providers.

## Decision 14 — Error Handling Within the Graph

Three tiers:

| Failure | Handling |
|---|---|
| Tool call fails (after retry) | Capture in `ToolResult.Error`, continue with partial data, note gap in synthesis |
| LLM call fails | `paladin-gateway` handles retry + fallback chain internally. If all tiers fail, gateway returns error. Agent emits `error` event to NATS, orchestrator marks incident `needs_manual_review`, Slack alert fires. |
| Graph node panic | Eino recovers, emits error state. Checkpoint written with `Step="error"`. NATS NAK → redelivery (max 3). After 3 → DLQ. |

## Open Questions (carry to Stage 4)

1. **RunbookAgent source** — where do runbooks come from? Stored in Qdrant (procedural memory), pulled from GitHub/Confluence via integration, or written inline in `paladin.yaml`? Likely all three — priority order TBD.
2. **Action execution safety** — RunbookAgent proposes `kubectl rollout restart`. Which actions require approval by default vs auto-execute? Needs a policy engine (OPA rules per tenant per action type).
3. **Eino graph composition** — Eino supports composing graphs as nodes within a parent graph. Do we compose Supervisor + workers as a single compiled graph, or invoke worker graphs dynamically? Affects how Hatchet checkpoints interact with Eino state.
