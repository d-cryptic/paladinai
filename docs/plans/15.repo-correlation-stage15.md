# Stage 15 — Repo & Code Correlation

**Date:** 2026-05-10
**Status:** Design locked — implementation v1 scope
**Branch:** v2
**Scope:** Correlate deployments and git commits to active incidents. Output: specific commit + diff line as likely cause. No auto-PR in v1.

---

## Overview

When an incident fires, PaladinAI traces the blast radius back to the most likely code change that caused it. The output is a human-readable, evidence-backed statement:

> "Commit `abc123` by `@jane.doe`, deployed 14:02 (28 min before incident), likely caused this incident — specifically `src/db/pool.go:142` where `max_size` was reduced from 100 to 20. Stack trace confirms `database.Pool.Acquire()` is in the failure path."

False correlation is **worse than no correlation**. Every design decision in this stage prioritises precision over recall.

v1 scope: **correlation and highlighting only**. Auto-PR is deferred to v2 pending 30 days of production accuracy data.

## 1. Correlation Signal Hierarchy

Signals are tiered. Only strong signals may be the sole basis for a correlation report. Weak signals add context. Excluded signals are hard-blocked — no score assigned regardless of timing.

### Strong Signals

| Signal | Description |
|--------|-------------|
| Deployment proximity | Service X deployed within 30 min before incident on Service X |
| Code path overlap | `git diff` touches the exact file+function in the error stack trace |
| Known bad dependency | New dep version has a known CVE or a breaking changelog entry |
| Config parameter match | Changed config key appears verbatim in error logs |

All four are scored independently and summed. A single strong signal alone is insufficient to cross the reporting threshold — at minimum, deployment proximity + one other signal must combine to push the score above 0.70.

### Weak Signals (context only)

| Signal | When used |
|--------|-----------|
| Any deployment within 2h | Surfaced as context in the RCA narrative, never sole basis |
| Any PR merged within 4h | Listed in "recent activity" sidebar, not in root cause block |

Weak signals do not contribute to `correlation_score`. They are surfaced separately in the RCA as "recent activity" so the on-call engineer has full situational awareness.

### Never Correlate

These are hard exclusions enforced before the scoring step:

- Different service with **no FalkorDB dependency edge** (at any hop depth ≤ 3)
- Frontend bundle change with a backend database incident
- Infrastructure-layer change (network ACL, node pool resize) with application-layer incident — unless the affected service has an explicit `:DEPENDS_ON` edge to that infra node in FalkorDB
- Hotfix/rollback deployments that are themselves responses to the current incident

+-----------------------------+
      |

+-----------------------------+
| Deployment Scorer           |  per deployment
|  proximity_score            |

|  dependency_distance_score  |

|  -> correlation_score       |
+-----------------------------+
      |

+-----------------------------+

      v

```

The correlation engine runs as a **parallel goroutine** during RCA Phase 1, alongside tool fan-out calls. Results are ready before Phase 2 synthesis begins. If the engine exceeds 45 seconds, it is cancelled and the RCA proceeds without a code correlation block (incident response is never blocked on correlation).

## 3. Correlation Score Formula

```
correlation_score =
    0.40 × deployment_proximity
  + 0.35 × code_path_overlap
  + 0.15 × dependency_distance
  + 0.10 × historical_correlation
```

### Component Definitions

**deployment_proximity** — exponential decay over time before the incident:

```
deployment_proximity = exp(-λ × minutes_before_incident)
λ = 0.1

Examples:
  5 min before  → exp(-0.5)  = 0.607
  15 min before → exp(-1.5)  = 0.223
  30 min before → exp(-3.0)  = 0.050
  60 min before → exp(-6.0)  = 0.002
```

Deployments after incident start time score 0.0 on this component (they are post-hoc and listed separately).

**code_path_overlap** — binary in v1, Jaccard in v2:

```
v1: 1.0 if any stack trace function appears in changed function set, else 0.0
v2: Jaccard(changed_functions, stack_trace_functions)
```

This is the highest-weight signal. A diff that provably touches the failure path is the strongest evidence we have.

**dependency_distance** — FalkorDB hop count between deployed service and incident service:

```
dependency_distance = 1 / (hops + 1)

Same service:   1 / (0 + 1) = 1.000
Direct dep:     1 / (1 + 1) = 0.500
2-hop dep:      1 / (2 + 1) = 0.333
3-hop dep:      1 / (3 + 1) = 0.250
> 3 hops:       excluded (score = 0, skip)
```

**historical_correlation** — P(incident | deployment of this service), from ClickHouse `correlation_outcomes`:

```
historical_correlation = true_positives / total_deployments_of_service
                         (clamped to [0.0, 1.0])

Default for new service with no history: 0.0
(conservative — do not inflate score for unknown services)
```

### Threshold and Labels

| Score Range | Label | Action |
|-------------|-------|--------|
| < 0.70 | None | Not reported |
| 0.70 – 0.85 | "possibly related" | Reported with caveat |
| > 0.85 | "likely caused by" | Reported as root cause candidate |

When multiple deployments exceed threshold, all are reported ranked by score. The on-call engineer decides.

## 4. Code Path Analysis

### 4.1 Stack Trace Parsing

Stack traces are pulled from Loki logs for the incident time window. The parser handles Go, Java, and Python formats.

```go
// pkg/correlation/stacktrace.go

type StackFrame struct {
    File     string // "src/db/pool.go"
    Line     int    // 142
    Function string // "database.Pool.Acquire"
    Package  string // "database"
}

type StackTrace struct {
    Frames []StackFrame
    Raw    string
}

// ParseGoStackTrace extracts frames from a Go panic or goroutine dump.
// Handles both panics (runtime/debug.Stack) and goroutine dumps.
func ParseGoStackTrace(raw string) (StackTrace, error) {
    var frames []StackFrame
    // Match lines like: "github.com/acme/payments/src/db/pool.go:142 +0x1f4"
    re := regexp.MustCompile(`(\S+/\S+\.go):(\d+)`)
    for _, match := range re.FindAllStringSubmatch(raw, -1) {
        line, _ := strconv.Atoi(match[2])
        frames = append(frames, StackFrame{
            File: match[1],
            Line: line,
        })
    }
    // Second pass: match function names on preceding lines
    // "github.com/acme/payments/database.(*Pool).Acquire(...)"
    fnRe := regexp.MustCompile(`([\w/]+)\.([\w\.\(\)\*]+)\(`)
    // ... populate Function field on matched frames
    return StackTrace{Frames: frames, Raw: raw}, nil
}
```

### 4.2 Diff Parsing

The git diff for each deployment is fetched via `mcp-github` (or `mcp-gitlab`) using the commit SHA. The parser extracts changed files and, within each file, changed function names using heuristics (Go: `func ` prefix within ±10 lines of a diff hunk).

```go
// pkg/correlation/diff.go

type DiffHunk struct {
    File          string
    AddedLines    []int
    RemovedLines  []int
    NearFunctions []string // function names within ±10 lines of hunk
}

type CommitDiff struct {
    SHA   string
    Hunks []DiffHunk
}

// ChangedFunctions returns the deduplicated set of function names
// touched by the diff.
func (d CommitDiff) ChangedFunctions() map[string]struct{} {
    out := make(map[string]struct{})
    for _, h := range d.Hunks {
        for _, fn := range h.NearFunctions {
            out[fn] = struct{}{}
        }
    }
    return out
}
```

### 4.3 Overlap Scorer

```go
// pkg/correlation/overlap.go

// CodePathOverlap returns 1.0 if any stack trace function appears
// in the diff's changed function set, 0.0 otherwise (v1 binary).
func CodePathOverlap(trace StackTrace, diff CommitDiff) float64 {
    changed := diff.ChangedFunctions()
    for _, frame := range trace.Frames {
        if _, ok := changed[frame.Function]; ok {
            return 1.0
        }
        // Also check by file path alone (weaker match)
        for _, hunk := range diff.Hunks {
            if strings.HasSuffix(hunk.File, frame.File) {
                return 0.5 // partial file match — treated as weak
            }
        }
    }
    return 0.0
}
```

### 4.4 LLM Confirmation Pass (DeepSeek-R1)

When `code_path_overlap > 0`, a secondary LLM call confirms the semantic relationship. This is a verification step — it can lower a score but not raise it above the mechanistic result.

```go
// pkg/correlation/llm_judge.go

type LLMJudgeRequest struct {
    StackTrace string
    DiffExcerpt string // ≤ 200 lines, truncated around changed functions
    Question   string  // "Is this change likely responsible for this error?"
}

type LLMJudgeResponse struct {
    Score     float64 // 0.0 – 1.0
    Reasoning string
}

// Prompt template sent to DeepSeek-R1 via paladin-gateway:
//
// You are a senior SRE reviewing a production incident.
// Given the stack trace and the git diff below, score 0.0–1.0
// the probability that the diff caused the error.
// Be conservative. Output JSON: {"score": float, "reasoning": "..."}
//
// Stack trace:
// {{.StackTrace}}
//
// Git diff:
// {{.DiffExcerpt}}
```

The LLM score is used as a multiplier on `code_path_overlap`:

```
adjusted_overlap = code_path_overlap × llm_judge.score
```

If the LLM scores < 0.3, the overlap component is zeroed out and the correlation likely falls below threshold. This prevents false positives where function names collide across packages.

## 5. Deployment Detection

### 5.1 Sources

| Source | Mechanism | Latency |
|--------|-----------|---------|
| GitHub Deployments API | `mcp-github` — list deployments for repo, filter by environment | ~1s |
| GitLab Deployments API | `mcp-gitlab` — list project deployments | ~1s |
| Kubernetes rollout | `mcp-k8s` — `kubectl rollout history`, pod restart events, image tag delta | ~2s |

All three are queried in parallel goroutines. Results are merged and deduplicated by (service, sha, deployed_at).

### 5.2 Deployment Node in FalkorDB

Every detected deployment is written to FalkorDB for graph traversal:

```cypher
CREATE (:Deployment {
    sha:         "abc123",
    service:     "payments-service",
    deployed_at: datetime("2026-05-10T14:02:00Z"),
    deployed_by: "jane.doe",
    image_from:  "payments:v1.4.1",
    image_to:    "payments:v1.4.2",
    changelog_url: "https://github.com/acme/payments/releases/tag/v1.4.2",
    environment: "production"
})-[:DEPLOYED_TO]->(:Service {name: "payments-service"})
```

### 5.3 Deployment Watcher (Background)

A background goroutine polls GitHub/GitLab deployment webhooks every 60 seconds and writes new deployments to FalkorDB. This means the graph is pre-populated before an incident fires — correlation does not wait for deployment fetch at incident time. Real-time deployment data is already in the graph.

```
+-----------------+          +------------+
| Deployment      |  webhook | FalkorDB   |
| Watcher         |--------->| Deployment |
| (goroutine)     |  60s poll| nodes      |
+-----------------+          +------------+
```

## 6. Dependency Scope Filtering

Before any deployment is scored, FalkorDB determines whether that deployment is in scope for the incident.

### 6.1 BFS Query

```cypher
// Find all services reachable from the incident service within 3 hops
MATCH path = (src:Service {name: $incident_service})-[:DEPENDS_ON*1..3]->(dep:Service)
RETURN dep.name AS service, length(path) AS hops
```

This returns the candidate service set. Only deployments for services in this set proceed to scoring.

### 6.2 Hard Exclusion Logic

```go
// pkg/correlation/scope.go

func InScope(deployment Deployment, incident Incident, graph FalkorDBClient) (bool, int) {
    if deployment.Service == incident.Service {
        return true, 0 // same service, 0 hops
    }
    hops, found := graph.ShortestPath(incident.Service, deployment.Service, 3)
    if !found {
        return false, -1 // not in blast radius — hard exclude
    }
    return true, hops
}
```

If `InScope` returns false, the deployment is immediately skipped. No score is computed. This is the primary false-positive filter — it eliminates entire categories of irrelevant deployments before any LLM or scoring work is done.

## 7. RCA Integration

### 7.1 Execution Timing

```
RCA Phase 1 (parallel fan-out):
  ┌─────────────────────────┬─────────────────────────┐
  │ Loki log fetch          │ Correlation Engine      │
  │ Metrics fetch           │ (goroutine, 45s timeout)│
  │ Runbook RAG retrieval   │                         │
  └─────────────────────────┴─────────────────────────┘
                    |
                    v
            RCA Phase 2 (synthesis)
            LLM sees: logs + metrics + runbooks + correlation findings
```

Correlation findings are passed as a structured block in the synthesis prompt context. The synthesis LLM (DeepSeek-V3 for speed, R1 for complex incidents) can reference them when writing the root cause section.

### 7.2 Output Format in RCA Report

```markdown
## Code Correlation

**Likely contributor:** commit `abc123` — `payments-service`, deployed 14:02 (28 min before incident)
**Deployed by:** @jane.doe
**Confidence:** 0.91 — likely caused by

**Evidence:**
- `src/db/pool.go:142` — connection pool `max_size` reduced from 100 to 20
- Stack trace match: `database.Pool.Acquire()` appears in 47 of 52 error log lines
- LLM judge score: 0.88 — "The pool size reduction directly explains the connection exhaustion pattern"

**Diff excerpt:**
```diff
-   MaxSize: 100,
+   MaxSize: 20,
```

**Links:**
- Full diff: https://github.com/acme/payments/commit/abc123
- Deployment event: payments-service v1.4.2 → production (14:02 UTC)

---
*Note: This is machine-generated correlation. Verify before acting.*
```

### 7.3 "Possibly Related" Format

When score is 0.70–0.85:

```markdown
## Code Correlation

**Possibly related:** commit `def456` — `inventory-service`, deployed 13:48 (42 min before incident)
**Confidence:** 0.74 — possibly related (verify manually)

This deployment is in the blast radius of the affected service (2 FalkorDB hops). 
No direct stack trace match found. Review manually if primary investigation is inconclusive.

**Links:** https://github.com/acme/inventory/commit/def456
```

## 8. Accuracy Tracking

### 8.1 ClickHouse Schema

```sql
CREATE TABLE correlation_outcomes (
    incident_id        String,
    commit_sha         String,
    service            String,
    predicted_score    Float32,
    confidence_label   Enum8('possibly'=1, 'likely'=2),
    was_actual_cause   Nullable(Bool),   -- filled after postmortem
    feedback_source    Enum8('postmortem'=1, 'manual'=2, 'auto'=3),
    resolved_at        Nullable(DateTime),
    created_at         DateTime DEFAULT now()
) ENGINE = MergeTree()
ORDER BY (created_at, incident_id);
```

### 8.2 Metrics Tracked

| Metric | Definition | Target (before auto-PR) |
|--------|------------|--------------------------|
| true_positive_rate | `was_actual_cause=true / all_reported` | > 0.80 |
| false_positive_rate | `was_actual_cause=false / all_reported` | < 0.10 |
| precision_at_likely | TPR for score > 0.85 reports | > 0.90 |
| mean_score_when_correct | Avg predicted_score where was_actual_cause=true | — |
| mean_score_when_wrong | Avg predicted_score where was_actual_cause=false | — |

### 8.3 Feedback Collection

Feedback is collected from two paths:

1. **Postmortem sync** — after a postmortem doc is written (GitHub/Notion), a parser extracts the root cause commit SHA. If it matches a correlation prediction, `was_actual_cause=true`. If postmortem identifies a different cause, `was_actual_cause=false`.

2. **On-call thumbs up/down** — the RCA report UI (Slack or web) shows a "Was this the cause?" prompt. Engineer clicks yes/no within 24h of resolution.

### 8.4 Score Recalibration

Monthly: recalculate `historical_correlation` component weights per service from ClickHouse data. Services with high false-positive history get their `historical_correlation` baseline adjusted downward.

## 9. Auto-PR Roadmap (v2 — Design Only, Not v1)

This section exists so v1 is built with v2 in mind. No auto-PR code ships until accuracy gates are met.

### 9.1 Activation Gates

All three must hold simultaneously:

```
correlation_score    > 0.90
code_path_overlap    = 1.0  (exact function match, not file-only)
false_positive_rate  < 0.10 (from ClickHouse, rolling 30 days)
```

The 30-day accuracy window is non-negotiable. No shortcuts.

### 9.2 PR Creation Flow

```
Correlation score > 0.90 AND exact path match AND FPR gate passed
          |
          v
  Fix Generation (DeepSeek-R1)
  - Input: diff excerpt + stack trace + error description
  - Output: minimal patch to fix the regression
  - Constraint: patch must touch only lines changed in the causative commit
          |
          v
  Draft PR (mcp-github / mcp-gitlab)
  - Never auto-merge
  - Branch: paladin/fix/<incident_id>
  - Labels: paladin-suggested, needs-review
  - Pings: code owner of changed files (CODEOWNERS lookup)
  - PR body: links incident, explains root cause, shows evidence, shows fix
          |
          v
  Human reviews and merges
```

### 9.3 PR Description Template

```markdown
## Paladin Suggested Fix — Incident <incident_id>

> This PR was generated by PaladinAI. Review carefully before merging.
> Do not merge if you are uncertain.

### What happened
<incident summary>

### Root cause
Commit `<sha>` (deployed <time>) reduced `max_size` from 100 to 20,
causing connection pool exhaustion under production load.

Correlation confidence: 0.91 (likely)
Stack trace match: `database.Pool.Acquire()` — 47/52 error lines

### Proposed fix
<diff>

### Evidence
- Incident: <link>
- Causative commit: <link>
- Loki error sample: <link>

---
*PaladinAI auto-generated. Label: paladin-suggested*
```

### 9.4 Rollback Safety

If an auto-generated PR is merged and the incident recurs or worsens within 2 hours, PaladinAI alerts the on-call channel:

```
[PALADIN WARNING] Merged fix PR #<n> did not resolve incident <id>.
Correlation may have been incorrect. Consider reverting <sha>.
```

This is a monitoring alert only — no auto-revert.

## Key Design Constraints

1. **Conservatism first** — threshold at 0.70, with two confidence tiers. Default to silence if evidence is weak.
2. **Incident response never blocks on correlation** — 45s hard timeout, correlation is best-effort.
3. **No auto-PR until 30 days accuracy data** — the feature is designed but code is not written.
4. **FalkorDB scope filter is mandatory** — skipping it is not a valid optimisation. It is the primary false-positive control.
5. **LLM judge can only lower scores, not raise them** — mechanistic signals set the ceiling, LLM confirms.
6. **Feedback loop is load-bearing** — the accuracy tracking system must be operational before any correlation result is shown to users. Garbage-in from early false positives corrupts the historical signal permanently.
