## 1. CLI Architecture

### 1.1 Technology Stack

The CLI is a single Go binary. No runtime dependencies, no Docker required, no interpreters. Ships as a static binary for all target platforms.

| Concern | Library / Approach |
|---|---|
| Command routing | `github.com/spf13/cobra` |
| TUI components | `github.com/charmbracelet/bubbletea` |
| Styling / colors | `github.com/charmbracelet/lipgloss` |
| Spinner / progress | `github.com/charmbracelet/bubbles` (spinner, progress, table, textinput, list) |
| OS keychain | `github.com/zalando/go-keyring` |
| HTTP client | stdlib `net/http` with retry middleware |
| WebSocket | `github.com/gorilla/websocket` |
| YAML parsing | `gopkg.in/yaml.v3` |
| Helm interaction | Helm SDK `helm.sh/helm/v3` |
| K8s detection | `k8s.io/client-go` (read-only, uses current kubeconfig context) |

### 1.3 Config File Locations

Two distinct config files serve different purposes and should never be merged.

**User preferences** (`~/.paladin/config.yaml`) — machine-local, never committed:
```yaml
# ~/.paladin/config.yaml
api_endpoint: https://api.paladinai.io
default_tenant: acme-corp
output_format: table        # table | json | yaml
color: auto                 # auto | always | never
update_channel: stable      # stable | beta
last_update_check: "2026-05-10T03:00:00Z"
```

**Project config** (`paladin.yaml`) — project root, committed to git:
Full reference in section 6.

**Token storage:** OS keychain only. Never written to disk in plaintext.
- macOS: Keychain Services via `go-keyring`
- Linux: libsecret (GNOME Keyring) or KWallet fallback
- CI/CD environments: `PALADIN_TOKEN` environment variable (takes precedence over keychain)

### 1.5 Auto-Update Mechanism

The CLI checks for updates once per 24 hours (background goroutine, non-blocking). The check hits `https://releases.paladinai.io/latest.json` and compares semver against the embedded build version.

```go
// Embedded at build time via ldflags
var (
    Version   = "dev"
    BuildDate = "unknown"
    GitCommit = "unknown"
)
```

Update flow:
1. CLI starts, spawns background goroutine.
2. Goroutine checks last update check timestamp in `~/.paladin/config.yaml`.
3. If >24h, fetches `latest.json`.
4. If newer version: prints one-line notice at the bottom of any command output.
5. `paladin version` shows full update details and upgrade instructions.
6. User runs `paladin update` (calls install script or `brew upgrade paladin`).

Never auto-upgrade without user confirmation. The notice is informational only.

### 1.6 Shell Completion

Generated by Cobra's built-in completion engine. Users run once:

```bash
# bash
paladin completion bash > /usr/local/etc/bash_completion.d/paladin

# zsh
paladin completion zsh > "${fpath[1]}/_paladin"

# fish
paladin completion fish > ~/.config/fish/completions/paladin.fish
```

The `paladin init` wizard detects the user's shell and prints the appropriate completion install command as a post-wizard hint.

## 2. `paladin init` — Detailed Wizard Design

### 2.1 Bubble Tea Model Architecture

The wizard is a single Bubble Tea `Model` that owns a `currentStep int` and a `StepResult` for each completed step. Each step is its own sub-model implementing the `tea.Model` interface. The parent delegates `Update` and `View` to the active sub-model.

```
WizardModel
├── step: int
├── results: []StepResult
├── steps: []tea.Model
│   ├── DetectStep
│   ├── AuthStep
│   ├── TierStep
│   ├── IntegrationsStep
│   ├── DeployStep
│   └── DoctorStep
└── progress: bubbles/progress.Model  // top-of-screen progress bar
```

The top-of-screen progress bar is always visible, showing `[Step N/6] Step Name`. Steps cannot be skipped (except auth if already logged in). The user can press `Ctrl+C` to abort at any point; the wizard prints a recovery hint.

### 2.2 Step 1 — Environment Detection

**Goal:** Auto-discover the customer's existing observability stack without any destructive operations.

**Detection sources (in priority order):**

1. `kubectl config current-context` — identifies cluster name and infer cloud provider (GKE/EKS/AKS prefix patterns).
2. `kubectl get namespaces` — look for `monitoring`, `observability`, `logging`, `datadog-agent`, `grafana`, `elastic-system`.
3. `kubectl get pods --all-namespaces` — match known pod name/image patterns (prometheus, grafana, alertmanager, datadog-agent, elastic, loki, tempo, jaeger, otel-collector).
4. `helm list --all-namespaces` — match known chart names.
5. Environment variables — `DD_API_KEY`, `GRAFANA_URL`, `PAGERDUTY_TOKEN` indicate what's already configured.
6. Local kubeconfig contexts — multiple contexts indicate multi-cluster setups.

**Confidence scoring:**

| Evidence | Confidence |
|---|---|
| Helm chart found + pods running | High |
| Pods found but no Helm chart | Medium |
| Namespace found but no pods | Low |
| Environment variable only | Low |

**TUI layout for Step 1:**


Additions entered by the user are added to a manual list and carried forward to Step 4 as unconfigured integrations requiring credentials.

Detection is non-destructive: only `kubectl get` (read) calls, no writes, no exec into pods.

**If no cluster is detected:** the wizard falls back to a manual selection list of supported integrations. The user picks what they have. This supports non-K8s environments.

### 2.3 Step 2 — Authentication

**Happy path (browser available):**

1. CLI generates a PKCE code verifier + challenge.
2. Constructs auth URL: `https://auth.paladinai.io/oauth/authorize?...&code_challenge=...`
3. Opens URL in default browser via `open` (macOS) / `xdg-open` (Linux).
4. CLI starts a local HTTP listener on `127.0.0.1:9876/callback`.
5. TUI shows spinner: "Waiting for browser sign-in..."
6. Browser completes OAuth, redirects to `http://localhost:9876/callback?code=...`
7. CLI exchanges code for access + refresh tokens.
8. Stores tokens in OS keychain under key `paladin/tokens/<api_endpoint>`.

**Fallback (no browser / SSH / CI):**

1. CLI detects no `$DISPLAY` or `$BROWSER`, or user passes `--no-browser`.
2. Requests device authorization from `https://auth.paladinai.io/oauth/device`.
3. TUI shows:
   ```
   Open https://auth.paladinai.io/device in your browser and enter:
   
       ABCD-EFGH
   
   Waiting... (expires in 15:00)
   ```
4. Polls device token endpoint every 5 seconds.
5. On success: stores tokens identically to browser flow.

**Already authenticated:**

- CLI checks keychain on startup. If valid token exists (non-expired or refreshable): Step 2 is skipped entirely with a green "Already signed in as user@acme.com" status line in the progress bar.

**Token refresh:**

Access tokens expire in 1 hour. The CLI transparently refreshes using the refresh token before any API call. If the refresh token is expired (90-day limit): the CLI directs the user to `paladin auth login`.

### 2.6 Step 5 — Deploy

**Sequence:**

1. Generate `paladin.yaml` in the current directory.
2. If `paladin.yaml` already exists: show a unified diff and ask for confirmation.
3. Confirm with the user before any writes.
4. Write `paladin.yaml`.
5. Run `helm repo add paladinai https://charts.paladinai.io` (if not already added).
6. Run `helm upgrade --install paladin-agent paladinai/agent --namespace paladin-system --create-namespace -f paladin.yaml`.
7. Stream Helm output line-by-line into the TUI.
8. Poll `kubectl rollout status deployment/paladin-agent -n paladin-system` with a 120-second timeout.
9. On success: show pod status.

## 3. `paladin doctor` — Complete Check Design

### 3.1 Check Execution Model

All checks that are independent run in parallel goroutines. Checks that depend on prior results run sequentially (e.g., mTLS requires that DNS+TLS already passed; integration checks require tenant resolution).

The dependency graph:

```
DNS → TLS → mTLS → Tenant resolution → [all integration checks] → Synthetic alert → Memory roundtrip → Slack/PD test
```

Where `[all integration checks]` fan out in parallel from Tenant resolution.

### 3.2 Full Check Table

| Check | Implementation | Pass Criteria | Remediation on Fail |
|---|---|---|---|
| Control plane DNS | `net.LookupHost("api.paladinai.io")` | Returns at least one IP | Check network egress, corporate proxy, DNS resolver |
| TLS certificate | `tls.Dial("api.paladinai.io:443")` with default root CAs | Cert valid, not expired, CN matches | Check system clock, corporate CA bundle |
| mTLS handshake | `tls.Dial` with client cert loaded from keychain | Mutual TLS handshake succeeds | Run `paladin auth login` to re-provision client cert |
| Tenant resolution | `GET /api/v2/me` with bearer token | HTTP 200, `tenant_id` matches config | Run `paladin auth login` |
| Agent heartbeat | `GET /api/v2/agents/{id}/heartbeat` | Last heartbeat < 60s ago | Check `kubectl get pods -n paladin-system`, check network from cluster to control plane |
| Prometheus connectivity | MCP tool `prometheus_query` with `up` query | Returns metric series | Check `spec.integrations[prometheus].config.url`, check credentials |
| Grafana connectivity | `GET /api/health` on Grafana URL | HTTP 200 | Check URL, API key permissions |
| Alertmanager connectivity | `GET /api/v2/status` on Alertmanager URL | HTTP 200 | Check URL |
| PagerDuty connectivity | `GET /incidents` with API key | HTTP 200 | Verify `api_key` in paladin.yaml or keychain |
| Datadog connectivity | `GET /api/v1/validate` with API+App keys | HTTP 200 | Verify both `api_key` and `app_key` |
| Slack connectivity | Post to `paladin-alerts` channel via Bot token | HTTP 200, message appears | Check bot token, check bot is a member of the channel |
| OpsGenie connectivity | `GET /v2/alerts?limit=1` | HTTP 200 | Check API key |
| Synthetic alert injection | POST synthetic alert payload to `/api/v2/alerts/test` | Classification returned within 2s | Check NATS connectivity, check agent is Running and not in CrashLoopBackOff |
| Memory read/write roundtrip | Write test episode → read back by ID | Content matches, latency < 500ms | Check `paladin-memory` service health, check Redis |
| LLM reachability (tier A) | POST minimal prompt to configured Tier A endpoint | Non-error response < 10s | Check LLM provider credentials, check rate limits |
| LLM reachability (tier B) | POST minimal prompt to configured Tier B endpoint | Non-error response < 10s | Check LLM provider credentials |
| LLM reachability (tier C) | POST minimal prompt to configured Tier C endpoint | Non-error response < 10s | Check LLM provider credentials |

### 3.3 Per-Integration Doctor

`paladin doctor prometheus` runs only the Prometheus-related checks plus prerequisites (DNS, TLS, tenant). This is useful for debugging a single integration without running the full suite.

## 4. `paladin tail` — Live Alert Stream

### 4.1 Connection

`paladin tail` opens a WebSocket connection to `wss://api.paladinai.io/v2/ws/alerts` authenticated with the bearer token as a query parameter (`?token=...`) or via the `Authorization` header on the initial HTTP upgrade request.

The server pushes `AlertEvent` messages as newline-delimited JSON. The CLI reconnects automatically with exponential backoff (1s, 2s, 4s, 8s, max 30s) on disconnect.

### 4.2 Filters

```bash
paladin tail                            # all alerts for the tenant
paladin tail --severity p1              # P1 only
paladin tail --severity p1,p2           # P1 and P2
paladin tail --service payments-api     # specific service
paladin tail --tenant other-corp        # admin only: another tenant
paladin tail --since 30m                # alerts from last 30 minutes (scrollback)
```

Filters are sent to the server on connection as WebSocket query parameters. The server filters before sending, reducing unnecessary data transfer.

### 4.3 TUI Layout

```
paladin tail  (connected to acme-corp • 3 active incidents)            Ctrl+C quit

 TIME         SEVERITY   SERVICE            STATUS              ALERT
 ──────────────────────────────────────────────────────────────────────────────────

→ Press Enter on any row to open full incident view
```

1. Validates credentials with a live API call.
2. Stores secrets in the OS keychain (not in `paladin.yaml`).
3. Updates `paladin.yaml` to add the integration entry with `enabled: true` and non-secret config values.
4. Calls `paladin config apply` to push the change to the control plane.
5. Confirms with a `paladin doctor <name>` result inline.

## 8. Error Messages and Recovery

### 8.1 Error Message Anatomy

Every error shown to the user must contain three parts:

1. **What went wrong** — plain English, no jargon, no stack traces.
2. **Why it matters** — impact on setup progress.
3. **Exact command or action to fix it** — copy-pasteable.

### 8.2 Good vs Bad Error Examples

**Bad (never do this):**
```
Error: dial tcp 10.0.0.1:9090: connect: connection refused
```

**Good:**
```
Could not connect to Prometheus at http://10.0.0.1:9090.

This means PaladinAI cannot read metrics from your cluster.
Alerts will not be triaged until Prometheus is reachable.

To fix:
  1. Verify the URL:  kubectl get svc -n monitoring | grep prometheus
  2. Update paladin.yaml: spec.integrations[prometheus].config.url
  3. Re-run:          paladin doctor prometheus
```

---

**Bad:**
```
Error: rpc error: code = Unauthenticated desc = invalid token
```

**Good:**
```
Your session has expired. Sign in again to continue.

  paladin auth login
```

---

**Bad:**
```
FATA[0012] unexpected fault address 0x0
```

**Good:**
```
paladin encountered an unexpected error.

Please report this at https://github.com/paladinai/cli/issues
with the following:

  Version: paladin v2.3.1 (darwin/arm64)
  Command: paladin init
  Error ID: err_01HVXXX (auto-reported)
```

### 8.3 Common Failure Modes

| Failure | Symptom | Remediation |
|---|---|---|
| kubectl not configured | Step 1 shows no cluster detected | `kubectl config current-context` — set up kubeconfig |
| No browser in SSH session | Step 2 hangs | CLI auto-falls back to device flow; or pass `--no-browser` |
| Helm not installed | Step 5 fails at Helm command | `brew install helm` / install from helm.sh |
| Agent pods stuck Pending | Step 5 times out | `kubectl describe pod -n paladin-system` — likely resource quota or image pull issue |
| Prometheus URL unreachable from agent | Doctor fails Prometheus check | Agent is in-cluster but Prometheus URL uses `localhost` — use cluster DNS service URL |
| mTLS cert expired | Doctor fails mTLS check | `paladin auth login` — re-provisions client cert |
| Synthetic alert classification > 2s | Doctor warns | Check NATS connectivity, check agent logs for LLM timeout |
| paladin.yaml schema invalid | `paladin config validate` fails | Schema error message includes line number and field path |

### 8.4 No Raw Stack Traces to Users

The CLI catches all `panic` calls via a top-level `recover` in `main`. If a panic occurs:
1. Auto-report the error (with opt-out via `PALADIN_NO_TELEMETRY=1`).
2. Show the user-friendly "unexpected error" message (see above).
3. Write the full panic trace to `~/.paladin/logs/crash-<timestamp>.log`.
4. Print the log path so the user can attach it to a bug report.

## 10. Runbook Import Flow

### 10.1 CLI Import Command

```bash
# Import from GitHub repository
paladin runbooks import \
  --source github \
  --repo acme-corp/runbooks \
  --path docs/runbooks/ \
  --branch main

# Import from Confluence
paladin runbooks import \
  --source confluence \
  --space ENG \
  --token $CONFLUENCE_TOKEN \
  --url https://acme.atlassian.net

# Import from local directory
paladin runbooks import \
  --source file \
  --path ./runbooks/

# Import from Notion
paladin runbooks import \
  --source notion \
  --database-id <notion-db-id> \
  --token $NOTION_TOKEN
```

### 10.2 Import Pipeline

```
Source → Fetch → Parse → Chunk → Embed → Store → Index
```

1. **Fetch**: Clone/pull the source. For GitHub: GitHub API pagination. For Confluence: REST API with space traversal. For files: walk directory.
2. **Parse**: Detect format (Markdown, HTML, Confluence XML). Strip navigation, headers, footers. Extract title, last-modified date, author.
3. **Chunk**: Split into 512-token chunks with 64-token overlap. Preserve heading hierarchy in chunk metadata for citation.
4. **Embed**: Batch embed chunks using the configured embedding model (Voyage-3 by default for Pool/Bridge, configurable for Silo). Batch size: 96 chunks per request.
5. **Store**: Write chunks + embeddings to the tenant's vector store (pgvector).
6. **Index**: Refresh BM25 full-text index alongside vector index (hybrid retrieval).

### 10.3 TUI Progress During Import

```

  Parsing documents...                    ✓  (47/47)
```

### 10.4 Validation and Preview After Import

After import completes:

```

  Documents:  47
  Chunks:     312
  Embeddings: 312 (100% success)
  Skipped:    0

Test a query against your runbooks:
  paladin runbooks search "high error rate on payments service"

    "...check the connection pool exhaustion metric: payments_pool_waiting > 100..."

  Result 2 (score 0.87): docs/runbooks/database-runbook.md
    "...if the error rate correlates with deployment, roll back with..."
```

The `paladin runbooks search` command is the primary way for operators to validate that the import worked correctly before relying on it in production.

### 10.5 Re-import and Sync

Runbook sources can be re-imported at any time. The import is idempotent: chunks are identified by a content hash. Only new or changed chunks are re-embedded. Deleted documents are soft-deleted (removed from retrieval but retained for 30 days for rollback).

To set up automatic sync for a GitHub source, add to `paladin.yaml`:

```yaml
spec:
  runbooks:
    sources:
      - name: main-runbooks
        source: github
        repo: acme-corp/runbooks
        path: docs/runbooks/
        branch: main
        sync_schedule: "0 2 * * *"   # nightly at 2am
```

## Appendix C: Key Metrics for Time-to-Value

The 10-minute target breaks down as:

| Phase | Target Duration |
|---|---|
| `paladin init` Steps 1–3 (detect, auth, tier) | < 3 minutes |
| Step 4 (integration credential entry) | < 2 minutes |
| Step 5 (Helm deploy + pod ready) | < 3 minutes |
| Step 6 (doctor all checks pass) | < 1 minute |
| First real alert arrives and gets triaged | < 1 minute (depends on alert volume) |
| **Total** | **< 10 minutes** |

If no real alert arrives naturally within 5 minutes post-setup, `paladin doctor` already fired a synthetic alert in Step 6 to confirm the pipeline works end-to-end. So the customer has proof of value within 10 minutes regardless of real alert timing.
