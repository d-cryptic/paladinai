# Stage 1 — Language Split & Service Boundaries

**Date:** 2026-05-10
**Status:** Draft / Under discussion
**Scope:** High-level architecture decisions for v2

---

## Context

v1 is a monolingual Python stack (FastAPI + LangGraph + LangChain). It works but does not scale. v2 is a full revamp targeting:

- Production-ready multi-tenant SaaS
- Sub-2s alert classification, sub-5s root cause analysis
- Universal integration with any monitoring platform
- OSS model support (self-hosted inference path)
- 1000s of tools without hallucination
- No Python — Go everywhere, Rust for the LLM gateway

---

## Decision 1 — Language Stack

### Go everywhere, Rust for the gateway

| Layer | Language | Reason |
|---|---|---|
| All services | Go 1.23+ | 54x lower P99 vs Python at 5K RPS; 9.5x higher throughput; goroutines for concurrent tool calls; entire ML ecosystem is HTTP/gRPC calls anyway |
| LLM gateway | Rust (Tokio + Axum) | Pure HTTP proxying — no AI ecosystem needed; Rust's performance is undeniable for this workload |
| Embedding inference | Triton (C++/CUDA) | BGE-M3 served via Triton; Go calls gRPC. No Python needed. |
| Frontend | TypeScript / Next.js 15 | Unchanged |
| CLI | Go + Cobra + Bubble Tea | Single binary, fast, cross-platform |

**No Python at all.** The v1 assumption that Python is required for AI workloads was wrong — all the actual AI operations are HTTP/gRPC calls to external services (LLMs, vector DBs, embedding servers). Go handles this natively.

### Go agent runtime

v1 used LangGraph (Python). Replacement options evaluated:

| Option | Decision | Reason |
|---|---|---|
| LangGraph 2.0 | Rejected | Python-first; LangChain dependency bloat |
| PydanticAI | Rejected | Still Python |
| **Eino (ByteDance/CloudWeGo)** | **Candidate** | Go-native, production at ByteDance scale, Apache 2.0 |
| **Custom Go FSM** | **Candidate** | ~200 lines, fits our fixed decision tree exactly, zero deps |

Open question: Eino (full framework, more ecosystem) vs custom FSM (less code, more control). To decide in Stage 2.

The core agent loop in Go is straightforward — our decision tree is deterministic enough:

```go
type AgentState struct {
    TenantID    string
    Alert       AlertEnvelope
    Intent      string
    ToolResults map[string]any
    Step        string
}

func (a *Agent) Run(ctx context.Context, state AgentState) (AgentState, error) {
    for {
        switch state.Step {
        case "classify":   state = a.classify(ctx, state)
        case "tools":      state = a.parallelTools(ctx, state) // goroutines, not sequential
        case "synthesize": state = a.synthesize(ctx, state)
        case "done":       return state, nil
        }
    }
}
```

## Decision 2 — Service Boundaries

### Standalone projects (separate repos, open-sourceable)

**`paladin-gateway` (Rust)**
A drop-in OpenAI-compatible LLM routing gateway. Solves the LiteLLM problem — LiteLLM has serious reliability and code quality issues.

Features:
- Multi-provider routing: Anthropic, OpenAI, Groq, Fireworks, vLLM, Ollama
- Circuit breakers per provider (50% error rate / 60s window → OPEN)
- Fallback chains (YAML-configured)
- Semantic caching (optional Qdrant backend)
- Cost tracking per tenant per model (tokens in/out)
- Rate limiting per tenant per model
- Model aliases (`fast` → Groq/llama, `smart` → claude-opus)
- Streaming passthrough (SSE + WebSocket)
- BYOK — per-tenant provider API keys
- OTel spans on every request

This is a standalone OSS project. PaladinAI uses it internally. The community has no good self-hostable Rust alternative to LiteLLM/Portkey yet.

**`paladin-hub` (Go)**
MCP aggregator with semantic tool discovery. Solves the 1000-tool hallucination problem.

See Decision 4 below.

### Core services (all Go)

| Service | Responsibility | Interface |
|---|---|---|
| `paladin-edge` | HTTP REST API, rate limiting (Valkey token bucket), RLS injection, RBAC (OPA sidecar) | HTTPS REST, OpenAPI 3.1 |
| `paladin-ws` | WebSocket connection per browser tab — bidirectional: streams agent events to UI, receives commands (approve/reject runbook steps, send messages) | `wss://` |
| `paladin-ingest` | Receives webhooks (Alertmanager, Datadog, PagerDuty, custom) + OTLP from in-cluster collector. Verifies HMAC. Normalizes to `AlertEnvelope`. Publishes to NATS. | `POST /webhook/{integration}/{tenant}`, OTLP gRPC |

| `paladin-agent` | Core AI agent runtime. Pulls from NATS, runs Go FSM/Eino, calls `paladin-hub` for tool discovery+execution, calls `paladin-gateway` for LLM, reads/writes `paladin-memory`. Streams intermediate state back to NATS. | NATS pull consumer |
| `paladin-orchestrator` | Durable workflows via Hatchet (Go SDK). Owns P1/P2 incident lifecycle. Human-in-loop approval gates via Hatchet signals. | Hatchet worker |
| `paladin-memory` | Memory abstraction gRPC service. Single interface over Valkey + Zep/Graphiti + FalkorDB + Qdrant. Enforces tenant_id filter on every query. | gRPC `paladin.memory.v2` |
| `paladin-hub` | MCP aggregator + semantic tool discovery. See Decision 4. | gRPC `paladin.hub.v1` |
| `paladin-collector` | In-cluster OTel Collector distribution (Go binary). One per customer cluster. Ships telemetry to `paladin-ingest` via OTLP + mTLS. | OTel Collector |
| `paladin-cli` | `paladin init`, `paladin doctor`, `paladin integrations enable`, `paladin tail` | Binary |

## Decision 3 — Internal Communication

Two transport patterns — not everything is gRPC:

```
Async work dispatch:        NATS JetStream (alerts, triage work, runbook steps)
Synchronous internal calls: gRPC (auth validation, memory queries, hub queries)
Agent → LLM providers:      HTTP (via paladin-gateway, OpenAI-compatible)
Agent → tools:              via paladin-hub gRPC (hub proxies to MCP servers)
WebSocket client ↔ server:  bidirectional (commands + events)
```

**Rules:**
1. Go edge layer never calls LLMs directly — always through `paladin-gateway`
2. Agent workers never talk to Qdrant/FalkorDB/Valkey directly — always through `paladin-memory`
3. Agent workers never call MCP servers directly — always through `paladin-hub`
4. `tenant_id` is set by `paladin-auth` (Go), injected into every JWT claim, never sourced from LLM context window
5. The LLM context window is never a source of truth for authorization decisions

## Decision 4 — MCP Hub (Semantic Tool Discovery)

### The problem

With 20+ integration packages, each with multiple tools (query, list, create, silence, ack...), the total tool count easily reaches 100-1000. Injecting all schemas into the agent context window causes:
- Token bloat (cost)
- Tool selection hallucination
- Slower inference

### The solution: paladin-hub

A dedicated Go service that acts as a semantic layer over all MCP servers.

```
┌──────────────────────────────────────────────────────┐
│                  paladin-hub (Go)                     │
│                                                        │
│  Tool Registry:                                        │
│   - tool_id, name, description, schema (JSON)         │
│   - BGE-M3 embedding of description (via Triton)      │
│   - mcp_server_endpoint                               │
│   - per-tenant permissions                            │
│   - version, health status                            │
│                                                        │
│  gRPC API:                                             │
│   DiscoverTools(intent, tenant_id, top_k) → []Schema  │
│   ExecuteTool(tool_id, params, tenant_id) → Result    │
│   RegisterTool(manifest) → tool_id                    │
│   ListTools(tenant_id, filter) → []ToolMeta           │
│                                                        │
│  Internals:                                            │
│   Qdrant for tool embeddings (cosine search)          │
│   MCP connection pool to actual servers               │
│   Per-tenant rate limiting per tool                   │
│   Tool health monitoring + circuit breaker            │
└──────────────────────────────────────────────────────┘
```

**Agent flow with hub:**
1. Alert arrives, intent classified: `"log_analysis"`
2. Agent calls `Hub.DiscoverTools(intent="log_analysis", tenant_id, top_k=5)`
3. Hub runs BGE-M3 semantic search over all registered tool embeddings
4. Returns 5 most relevant tool schemas
5. Agent generates tool calls against those 5 schemas
6. Agent calls `Hub.ExecuteTool(tool_id, params, tenant_id)`
7. Hub validates tenant permission, proxies to actual MCP server, returns result

The agent never sees 1000 tools. It always sees ≤5-7 relevant ones.

**Open question:** Should the Hub proxy tool execution (single hop: agent → hub → MCP), or return the MCP server endpoint so the agent calls directly (two connections but less centralization)?

Proxy = more control, rate limiting in one place, easier audit.
Direct = lower latency, less single point of failure.

Decision pending.

## Decision 5 — Durable Workflows

**Temporal replaced with Hatchet.**

Temporal is operationally heavy (~200MB per worker, separate Cassandra/PG backend, complex server). For most of our alerts (P3/P2, resolved in <30s), durable orchestration adds pure overhead.

| Severity | Workflow engine |
|---|---|
| P3 | NATS → agent → done. No durable orchestration. |
| P2 | NATS → agent → Hatchet workflow if multi-step runbook |
| P1 | Hatchet workflow from alert receipt → postmortem. Human approval via Hatchet signals. |

Hatchet runs on PG 17 (which we already have). Go SDK. Steps, retries, signals, timeouts — everything Temporal offers, lighter footprint.

## Decision 6 — Auth Split

Two distinct auth concerns handled separately:

**User auth** (`paladin-auth` service)
- Humans logging into dashboard/CLI
- OIDC/SAML SSO, SCIM provisioning
- Ory Hydra (OIDC server) + Ory Kratos (identity management)
- Session tokens, refresh tokens, MFA

**Agent auth** (Vault + `paladin-ingest`)
- Integration credentials stored in HashiCorp Vault
- Per-tenant namespaces in Vault
- `paladin-ingest` writes credentials on `paladin integrations enable`
- MCP servers fetch credentials from Vault at runtime, never from agent context
- Short-lived scoped tokens per tool call

## Local Development Model

For local dev and testing: **docker-compose** with all services as containers. No K8s needed locally.

```
paladin-gateway    (Rust binary)
paladin-edge       (Go binary)
paladin-ws         (Go binary)
paladin-ingest     (Go binary)
paladin-auth       (Go binary)
paladin-agent      (Go binary)
paladin-hub        (Go binary)
paladin-memory     (Go binary)
paladin-orchestrator (Go binary)

Infrastructure:
nats               (official image)
postgres           (official image)
valkey             (official image)
qdrant             (official image)
falkordb           (official image)
hatchet-engine     (official image)
vault-dev          (dev mode)
```

`docker compose up` → full stack running locally.

Single binary mode is also viable for the simplest local testing: all Go services compiled into one binary with internal routing. Explore as a future optimization.

## Open Questions (carry to Stage 2)

1. **Eino vs custom Go FSM** for the agent runtime — ecosystem vs simplicity
2. **paladin-hub proxy vs registry-only** — control vs latency
3. **paladin-gateway scope** — what features ship in v1 of the gateway
4. **FalkorDB Go client maturity** — needs validation before committing
5. **Zep/Graphiti Go support** — currently Python-native; may need to call via gRPC or use alternative bi-temporal graph layer
6. **BGE-M3 fine-tuning pipeline** — how do we fine-tune on incident corpus without Python? Likely a one-off Python training job, not a service.
