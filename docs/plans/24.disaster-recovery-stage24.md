## 2. PostgreSQL HA & Recovery

**Topology**: 3-node Patroni cluster — 1 primary + 2 streaming replicas, multi-AZ.

```
┌──────────────────────────────────────────────────────────────┐
│  pgBouncer (clients connect here, reconnects on failover)    │
└───────────────────────┬──────────────────────────────────────┘
                        │
          ┌─────────────▼─────────────┐
          │       Patroni Primary      │──── WAL stream ──► Replica A (AZ-b)
          │  PostgreSQL 17, AZ-a       │──── WAL stream ──► Replica B (AZ-c)
          └───────────────────────────┘
                 │ WAL archive every 60s
                 ▼
             S3 (pg-wal-archive/) ◄── pg_basebackup daily snapshot
```

**Failover**:
- Patroni detects primary failure via etcd DCS; promotes best replica in <30s.
- pgBouncer pauses connections, reconnects to new primary automatically.

**PITR Procedure**:
1. Stop recovery target cluster if any.
2. `aws s3 cp s3://pg-snapshots/latest/ /pgdata/ --recursive`
3. Set `recovery_target_time` in `postgresql.conf`.
4. `pg_ctl start` → WAL replay begins from S3 archive.
5. Confirm recovery via `SELECT pg_is_in_recovery();` → `false`.

**Per-tenant schema recovery** (no full cluster restore required):
1. Restore snapshot to isolated test cluster.
2. `pg_dump -n tenant_<id> | psql -d prod_db` — inject only affected schema.

## 3. Qdrant Backup & Recovery

**Snapshot schedule**: CronJob every 6h — `POST /collections/{name}/snapshots`.

```
qdrant-snapshots/
  {tenant_id}/
    {collection}/
      {timestamp}.tar     ← gzip-compressed, S3 lifecycle = 30 days
```

**Recovery steps**:
1. Scale down paladin-agent pods (stop writes to affected collection).
2. `POST /collections/{name}/snapshots/upload` with S3-downloaded `.tar`.
3. Verify: `GET /collections/{name}` → `vectors_count` matches pre-failure.
4. Resume paladin-agent pods; re-index any writes since snapshot via reprocessed NATS events.

**Per-tenant recovery**: restore individual collection — no cluster-wide downtime.

**Limitation**: no native incremental snapshots; full collection snapshot required.

## 4. NATS JetStream Resilience

**Topology**: 3-node cluster, R=3 (all streams replicated to all nodes), file storage.

```
┌──────────┐   ┌──────────┐   ┌──────────┐
│ NATS-0   │◄──►│ NATS-1   │◄──►│ NATS-2   │
│ (leader) │   │ (replica)│   │ (replica)│
└──────────┘   └──────────┘   └──────────┘
   AZ-a           AZ-b           AZ-c
```

**Retention policy**:

| Stream  | Retention | DLQ Hold |
|---------|-----------|----------|
| ALERTS  | 24 hr     | 30 days  |
| WORK    | 7 days    | 30 days  |
| DLQ     | 30 days   | —        |

**Recovery from 2-node loss**:
1. Stop surviving node to prevent split-brain.
2. Restore JetStream data dir from last S3 tar backup.
3. Restart all 3 nodes — cluster re-forms, streams resume.
4. Re-deliver any messages with `Ack: none` from DLQ.

## 5. Full Region Failure Runbook

```
REGION FAILURE RUNBOOK (us-west-2 → us-east-1 DR)
═══════════════════════════════════════════════════

STEP 1 │ 0–5 min   │ DETECT
       │           │ • Health check failures in Cloudflare → PagerDuty P1
       │           │ • Confirm: kubectl get nodes --context=us-west-2 times out
       │           │ • Confirm: S3 us-west-2 bucket unreachable

STEP 2 │ 5–10 min  │ PARTIAL FAILOVER
       │           │ • Enable Cloudflare failover rule: EU region handles new tenants
       │           │ • US tenants: Cloudflare Workers return maintenance JSON (503)
       │           │ • Broadcast incident on status.paladinai.com

STEP 3 │ 10–30 min │ TRIAGE
       │           │ • AZ failure? → K8s reschedules to healthy AZs (automatic, wait)
       │           │ • Region failure? → Proceed to DR activation below

STEP 4 │ 30–60 min │ PROVISION DR CLUSTER
       │           │ • terraform apply -var region=us-east-1 -target=module.gke_cluster
       │           │ • kubectl apply -k overlays/us-east-1  (ArgoCD sync)
       │           │ • Restore PG: pull latest S3 snapshot + replay WAL to latest
       │           │   pg_ctl start -D /pgdata (recovery_target=immediate)

STEP 5 │ 60–90 min │ RESTORE DATA SERVICES
       │           │ • Qdrant: restore collections from S3 snapshots (parallel per tenant)
       │           │ • ClickHouse: pull S3 backup parts, ATTACH PART, verify counts
       │           │ • Valkey: restart with RDB from S3; accept cache cold start
       │           │ • FalkorDB: restore RDB snapshot; verify graph node count

STEP 6 │ 90–120 min│ VALIDATE & CUT OVER
       │           │ • kubectl run smoke-test --image=paladinai/smoke:latest
       │           │ • Test: ingest alert → triage → incident creation round-trip
       │           │ • Point Cloudflare DNS A record to us-east-1 LB IP
       │           │ • Remove maintenance 503 page for US tenants

STEP 7 │ POST      │ COMMUNICATE & CLOSE
       │           │ • Notify tenants: data window = RPO per component (see §1)
       │           │ • Postmortem doc within 48h
       │           │ • Sync recovered region back when us-west-2 restored
```

## 6. Data Retention Policy

| Data Type                  | Hot Retention | Cold / Archive     | Delete Trigger       |
|----------------------------|---------------|--------------------|----------------------|
| Raw alert payloads (R2)    | 90 days       | 7 years (R2 IA)    | After 7 years        |
| Incident records (PG)      | Forever       | —                  | GDPR erasure request |
| RCA / postmortem (PG)      | Forever       | —                  | GDPR erasure request |
| Episodes (PG + Zep)        | 2 years hot   | 7 years cold S3    | After 7 years        |
| LLM cost events (CH)       | 2 years       | —                  | After 2 years        |
| Agent traces (LangSmith)   | 90 days       | —                  | After 90 days        |
| Audit logs (CH)            | 2 years       | 7 years S3 Glacier | After 7 years        |
| Eval replays (S3)          | 6 months      | —                  | After 6 months       |
| NATS DLQ messages          | 30 days       | —                  | Auto-expire          |
| Qdrant snapshots (S3)      | 30 days       | —                  | S3 lifecycle rule    |
| PG WAL archive (S3)        | 30 days       | —                  | S3 lifecycle rule    |

**Lifecycle enforcement**: S3 lifecycle rules + ClickHouse TTL expressions + PG `pg_cron` monthly cleanup job.

## 7. GDPR Right to Erasure

**Target**: complete within 72 hours of verified request.

```
GDPR ERASURE PROCEDURE
══════════════════════

1. CRYPTO-SHRED (immediate)
   vault write transit/keys/tenant-{id}/config deletion_allowed=true
   vault delete transit/keys/tenant-{id}
   → All Vault-encrypted columns unreadable instantly

2. POSTGRESQL (< 5 min)
   DELETE FROM incidents    WHERE tenant_id = $1;
   DELETE FROM episodes     WHERE tenant_id = $1;
   DELETE FROM alert_events WHERE tenant_id = $1;
   UPDATE tenants SET deleted_at = now() WHERE id = $1;  -- soft delete for legal hold check

3. QDRANT (< 10 min)
   DELETE /collections/alerts_{tenant_id}
   DELETE /collections/episodes_{tenant_id}

4. NATS (< 2 min)
   nats stream purge ALERTS --filter="tenant.{id}.>"
   nats stream purge WORK   --filter="tenant.{id}.>"

5. OBJECT STORAGE (< 30 min)
   aws s3 rm s3://paladin-r2/tenants/{id}/ --recursive
   (Cloudflare R2 mirrors deleted within replication window)

6. CLICKHOUSE (< 10 min)
   ALTER TABLE llm_cost_events DELETE WHERE tenant_id = '{id}';
   ALTER TABLE audit_logs      DELETE WHERE tenant_id = '{id}';

7. CONFIRM & NOTIFY
   Insert erasure_confirmation(tenant_id, completed_at, steps_verified)
   Email tenant DPO with confirmation receipt
```

## 8. Chaos Testing Schedule

**Frequency**: monthly against staging cluster. Results → `chaos_test_results` (ClickHouse).

| Test Scenario                        | Expected Outcome                          | Pass Criteria                     |
|--------------------------------------|-------------------------------------------|-----------------------------------|
| Kill 1 NATS node                     | Zero message loss, cluster recovers       | No gaps in stream sequence nums   |
| Kill PG primary                      | Patroni failover <30s                     | pgBouncer reconnects, alert flows |
| Kill all paladin-agent pods          | KEDA respins, NATS redelivers             | No duplicate incidents created    |
| Saturate paladin-gateway (1k rps)    | Circuit breaker activates, fallback chain | 503 with Retry-After, no panic    |
| Corrupt 1 Qdrant shard               | Graceful degradation, no crash            | Query returns partial/error, logged|
| Inject PG replica lag >30s           | Patroni demotes lagging replica           | Primary unaffected, alert raised  |
| R2 bucket unreachable                | Writes queue, resume on restore           | No payload loss, DLQ accumulates  |

**Automation**: `chaos/` Helm chart in staging namespace; triggered by GitHub Actions schedule (`0 9 1 * *`).

## 9. Backup Verification

**Frequency**: monthly automated restore test via GitHub Actions.

```yaml
# .github/workflows/backup-verify.yml (schedule: '0 3 1 * *')
steps:
  - Restore PG snapshot to ephemeral Cloud SQL instance
  - Run: SELECT COUNT(*) FROM incidents; -- compare vs recorded baseline
  - Run schema validation: pg_dump --schema-only | diff expected.sql
  - Restore Qdrant snapshot to ephemeral node
  - Verify: GET /collections/{name} → vectors_count within 1% of baseline
  - Restore ClickHouse S3 parts to test table
  - Verify row count matches within RPO window tolerance
  - Teardown ephemeral resources
  - On failure: PagerDuty P2 alert + Slack #infra-alerts
```

**SLA**: restore test must complete and pass within 4 hours of trigger. Failure = P2 incident.
