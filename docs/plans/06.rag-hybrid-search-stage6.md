### Semantic Chunking — Boundary Detection

Fixed-size chunking destroys meaning at arbitrary token positions. The chunker uses a priority-ordered boundary strategy:

```
Priority 1: Heading boundary (## / ### / ####)
            → always split at headings, never cross them

Priority 2: Paragraph boundary (\n\n)
            → if chunk is 400–800 tokens, seal here

Priority 3: Sentence boundary (. followed by whitespace + capital)
            → fallback when paragraph is too long

Priority 4: Hard split at 800 tokens
            → only when no other boundary found in window
```

15% overlap (77 tokens for a 512-token chunk): the last 77 tokens of chunk N become the first 77 tokens of chunk N+1. Dense embeddings benefit from 10–20% overlap for cross-boundary queries; SPLADE gets no benefit from overlap. The 15% figure is the validated sweet spot across both modes.

```go
// pkg/ingestion/chunker.go

type Chunk struct {
    DocID       string
    ChunkIndex  int
    Text        string   // raw chunk text (before context enrichment)
    TokenCount  int
    Overlap     string   // last 15% of previous chunk (e.g. 77 tokens for 512-token chunks)
}

type ChunkBoundary int

const (
    BoundaryHeading   ChunkBoundary = iota // priority 1
    BoundaryParagraph                      // priority 2
    BoundarySentence                       // priority 3
    BoundaryHard                           // priority 4 (fallback)
)

func chunkDocument(text string, tokenizer Tokenizer) []Chunk {
    tokens := tokenizer.Encode(text)
    var chunks []Chunk
    var start int

    for start < len(tokens) {
        end, boundaryType := findBoundary(tokens, start, 400, 800, tokenizer)
        _ = boundaryType // logged for metrics

        // overlap = 15% of chunk size (min 1, e.g. 77 for 512-token chunks)
        chunkLen := end - start
        overlapSize := chunkLen * 15 / 100
        if overlapSize < 1 {
            overlapSize = 1
        }

        overlap := ""
        if len(chunks) > 0 && end-overlapSize > start {
            overlapTokens := tokens[end-overlapSize : end]
            overlap = tokenizer.Decode(overlapTokens)
        }

        chunkText := tokenizer.Decode(tokens[start:end])
        chunks = append(chunks, Chunk{
            ChunkIndex: len(chunks),
            Text:       chunkText,
            TokenCount: end - start,
            Overlap:    overlap,
        })

        // next chunk starts overlapSize tokens before the end of this one
        if end-overlapSize > start {
            start = end - overlapSize
        } else {
            start = end
        }
    }
    return chunks
}
```

### Idempotency — Avoiding Re-embedding Unchanged Documents

Every document is fingerprinted with its source etag (GitHub commit SHA or Confluence version ID). Before ingestion:

```go
// Check if this doc version already ingested
existing, err := store.GetDocVersion(ctx, tenantID, docID)
if err == nil && existing.ETag == fetchedETag {
    // skip: same version already in Qdrant
    return nil
}
```

After successful Qdrant upsert, write `{doc_id, etag, ingested_at, chunk_count}` to a Postgres `ingestion_log` table. On next ingestion run, all unchanged documents are skipped in O(1) per doc.

For partial updates (only some chunks changed), the chunker computes a per-chunk content hash. Only chunks whose hash has changed are re-embedded and re-upserted. Qdrant supports point-level upsert so unchanged chunks stay untouched.

### Batch vs Streaming

| Corpus size | Strategy |
|-------------|----------|
| < 1,000 docs (initial onboard) | Batch: fan-out goroutines, configurable concurrency (default 8) |
| Ongoing webhook-triggered updates | Streaming: single document through pipeline, < 5s target |
| Monthly full re-embed (model update) | Batch with worker pool, throttled to avoid Triton saturation |

The pipeline is structured as a Go channel pipeline. Each stage is a goroutine pool. Backpressure is handled by buffered channels between stages (buffer = 2× worker count).

```
fetchCh   (cap 64)  → parseCh   (cap 64)  → chunkCh  (cap 256)
→ enrichCh (cap 256) → embedCh  (cap 128)  → upsertCh (cap 128)
```

## 2. BGE-M3 Three-Mode Embedding

BGE-M3 (BAAI/bge-m3) produces three distinct representations from a single forward pass. All three are requested in one Triton call.

### The Three Modes

```
Input text
    │
    ▼
┌─────────────────────────────────────────────┐
│              BGE-M3 Encoder                 │
│  (XLM-RoBERTa backbone, served on Triton)   │
└─────────────┬────────────┬─────────────────-┘
              │            │            │
              ▼            ▼            ▼
         Dense          Sparse       ColBERT
        (1024d)        (SPLADE)    (multi-vec)
       float32       sparse vec    token vecs
     cosine sim     dot product    MaxSim
```

| Mode | Vector type | Dimension | Use case | Storage cost |
|------|-------------|-----------|----------|--------------|
| Dense | float32 | 1024 | Semantic similarity, general retrieval | 1x |
| Sparse (SPLADE) | sparse uint32→float32 | ~30k vocab | Exact keyword, error codes, service names | ~0.1x (sparse) |
| ColBERT | float32 per token | 128d × N tokens | Highest accuracy, token-level alignment | 10–20x |

**When each is used:**
- Dense: primary retrieval for all queries. Always used.
- Sparse: always fused with dense via RRF. Especially valuable for technical queries (`OOMKilled`, `payments-api`, `error-137`).
- ColBERT: used only as a reranking signal for the top-50 candidates from dense+sparse fusion. Not used for initial retrieval (too expensive at scale).

### Triton gRPC Call — Go Sketch

```go
// pkg/embedding/triton.go

import (
    "context"
    triton "github.com/paladinai/proto/triton/grpc_service"
    "google.golang.org/grpc"
)

type BGEEmbedding struct {
    Dense   []float32              // shape [1024]
    Sparse  map[uint32]float32     // token_id -> weight
    ColBERT [][]float32            // shape [seq_len, 128]
}

type TritonEmbedder struct {
    conn   *grpc.ClientConn
    client triton.GRPCInferenceServiceClient
}

func (e *TritonEmbedder) EmbedAll(ctx context.Context, text string) (*BGEEmbedding, error) {
    // Tokenize locally (BGE tokenizer, loaded once at startup)
    inputIDs, attentionMask := e.tokenizer.Encode(text)

    req := &triton.ModelInferRequest{
        ModelName:    "bge-m3",
        ModelVersion: "1",
        Inputs: []*triton.ModelInferRequest_InferInputTensor{
            {
                Name:     "input_ids",
                Datatype: "INT64",
                Shape:    []int64{1, int64(len(inputIDs))},
                Contents: &triton.InferTensorContents{
                    Int64Contents: int64Slice(inputIDs),
                },
            },
            {
                Name:     "attention_mask",
                Datatype: "INT64",
                Shape:    []int64{1, int64(len(attentionMask))},
                Contents: &triton.InferTensorContents{
                    Int64Contents: int64Slice(attentionMask),
                },
            },
        },
        // Request all three output heads in one call
        Outputs: []*triton.ModelInferRequest_InferRequestedOutputTensor{
            {Name: "dense_embedding"},   // [1, 1024] float32
            {Name: "sparse_weights"},    // [1, vocab_size] float32 (sparse)
            {Name: "colbert_embeddings"}, // [1, seq_len, 128] float32
        },
    }

    resp, err := e.client.ModelInfer(ctx, req)
    if err != nil {
        return nil, fmt.Errorf("triton bge-m3 infer: %w", err)
    }

    return parseEmbeddingResponse(resp), nil
}

func parseEmbeddingResponse(resp *triton.ModelInferResponse) *BGEEmbedding {
    emb := &BGEEmbedding{}
    for _, output := range resp.Outputs {
        switch output.Name {
        case "dense_embedding":
            emb.Dense = float32Slice(output.Contents.Fp32Contents)
        case "sparse_weights":
            emb.Sparse = toSparseMap(output.Contents.Fp32Contents) // drop zero weights
        case "colbert_embeddings":
            emb.ColBERT = toColBERTMatrix(output.Contents.Fp32Contents, output.Shape)
        }
    }
    return emb
}
```

Batch embedding (for ingest): Triton supports dynamic batching. The embed-worker sends up to 32 texts per request using `ModelInfer` with batch dimension. BGE-M3 on A100 achieves ~800 texts/sec at batch=32.

### ASCII Pipeline

```
Query text
    │
    ├──────────────────────────────────────────────────────┐
    │                                                      │
    ▼                                                      ▼
```

### RRF Formula and Go Implementation

Reciprocal Rank Fusion merges two ranked lists without needing score normalization:

```
score(d) = Σ_i  1 / (k + rank_i(d))

where:
  d       = document
  i       = retrieval method (dense, sparse)
  rank_i  = rank of d in method i's result list (1-indexed)
  k       = 60  (constant, mitigates impact of high-rank outliers)
```

```go
// pkg/retrieval/rrf.go

type ScoredDoc struct {
    PointID string
    Score   float64
    Payload map[string]interface{}
}

// RRFMerge merges ranked lists from multiple retrieval methods.
// Each list is already ordered best-first (rank 1 = index 0).
func RRFMerge(k float64, lists ...[]ScoredDoc) []ScoredDoc {
    scores := make(map[string]float64)
    payloads := make(map[string]map[string]interface{})

    for _, list := range lists {
        for rank, doc := range list {
            // rank is 0-indexed; formula uses 1-indexed
            scores[doc.PointID] += 1.0 / (k + float64(rank+1))
            if _, ok := payloads[doc.PointID]; !ok {
                payloads[doc.PointID] = doc.Payload
            }
        }
    }

    merged := make([]ScoredDoc, 0, len(scores))
    for id, score := range scores {
        merged = append(merged, ScoredDoc{
            PointID: id,
            Score:   score,
            Payload: payloads[id],
        })
    }

    // Sort descending by RRF score
    sort.Slice(merged, func(i, j int) bool {
        return merged[i].Score > merged[j].Score
    })

    return merged
}
```

### Qdrant Query API Call — Go Sketch

Qdrant 1.16 supports a unified Query API that can issue named-vector searches in parallel and return merged results. We use it for the hybrid search:

```go
// pkg/retrieval/qdrant.go

type HybridSearchRequest struct {
    TenantID  string
    QueryText string
    TopK      int // how many to return after reranking (default 5)
}

func (r *QdrantRetriever) HybridSearch(
    ctx context.Context,
    req HybridSearchRequest,
) ([]ScoredDoc, error) {

    // Step 1: embed query
    emb, err := r.embedder.EmbedAll(ctx, req.QueryText)
    if err != nil {
        return nil, fmt.Errorf("embed query: %w", err)
    }

    // Step 2: dense search (top-50)
    denseResults, err := r.qdrantClient.Search(ctx, &qdrant.SearchRequest{
        CollectionName: "runbooks_pool",
        Vector: &qdrant.NamedVector{
            Name:   "dense",
            Vector: emb.Dense,
        },
        Limit:       50,
        WithPayload: true,
        Filter: &qdrant.Filter{
            Must: []*qdrant.Condition{
                qdrant.MatchKeyword("tenant_id", req.TenantID),
            },
        },
    })
    if err != nil {
        return nil, fmt.Errorf("dense search: %w", err)
    }

    // Step 3: sparse search (top-50)
    sparseResults, err := r.qdrantClient.SearchSparse(ctx, &qdrant.SearchRequest{
        CollectionName: "runbooks_pool",
        Vector: &qdrant.NamedSparseVector{
            Name:   "sparse",
            Vector: toQdrantSparse(emb.Sparse),
        },
        Limit:       50,
        WithPayload: true,
        Filter: &qdrant.Filter{
            Must: []*qdrant.Condition{
                qdrant.MatchKeyword("tenant_id", req.TenantID),
            },
        },
    })
    if err != nil {
        return nil, fmt.Errorf("sparse search: %w", err)
    }

    // Step 4: RRF merge → top-30
    denseDocs  := qdrantResultsToScoredDocs(denseResults)
    sparseDocs := qdrantResultsToScoredDocs(sparseResults)
    merged     := RRFMerge(60.0, denseDocs, sparseDocs)
    if len(merged) > 30 {
        merged = merged[:30]
    }

    // Step 5: rerank with bge-reranker-v2-m3
    reranked, err := r.reranker.Rerank(ctx, req.QueryText, merged)
    if err != nil {
        return nil, fmt.Errorf("rerank: %w", err)
    }

    // Step 6: apply minimum score threshold (≥ 0.60)
    var results []ScoredDoc
    for _, doc := range reranked {
        if doc.Score < 0.60 {
            break // sorted descending; once below threshold, all are below
        }
        results = append(results, doc)
        if len(results) >= req.TopK {
            break
        }
    }

    return results, nil
}
```

### Reranker — bge-reranker-v2-m3 via Triton

The cross-encoder reranker scores (query, document) pairs jointly. It sees both texts simultaneously, giving much higher precision than bi-encoder retrieval.

```go
// pkg/retrieval/reranker.go

func (rr *TritonReranker) Rerank(
    ctx context.Context,
    query string,
    candidates []ScoredDoc,
) ([]ScoredDoc, error) {

    // Build batch of (query, candidate_text) pairs
    pairs := make([]string, len(candidates))
    for i, c := range candidates {
        pairs[i] = c.Payload["text"].(string)
    }

    req := buildRerankerInferRequest("bge-reranker-v2-m3", query, pairs)
    resp, err := rr.client.ModelInfer(ctx, req)
    if err != nil {
        return nil, fmt.Errorf("triton reranker: %w", err)
    }

    scores := parseRerankerScores(resp) // sigmoid(logits) → [0,1]

    reranked := make([]ScoredDoc, len(candidates))
    for i, c := range candidates {
        reranked[i] = ScoredDoc{
            PointID: c.PointID,
            Score:   float64(scores[i]),
            Payload: c.Payload,
        }
    }

    sort.Slice(reranked, func(i, j int) bool {
        return reranked[i].Score > reranked[j].Score
    })

    return reranked, nil
}
```

## 4. Agentic RAG Router

The router runs inside paladin-memory (or paladin-agent calling paladin-memory). It inspects the incoming query and decides which retrieval path(s) to activate before any vector search is initiated.

### Router Types

```go
// pkg/retrieval/router.go

type RAGPath int

const (
    SkipRetrieval RAGPath = iota // high-confidence working memory hit
    VectorHybrid                 // Qdrant hybrid search (default path)
    GraphRAG                     // FalkorDB traversal (relational)
    TemporalKG                   // Zep bi-temporal (time-anchored)
    MultiPath                    // two or more paths, results merged
)
```

### Decision Logic

```go
type IncidentQuery struct {
    Text          string
    TenantID      string
    WorkingMemory []MemoryEntry // recent context already in agent state
    Confidence    float64       // confidence from working memory match
}

func routeQuery(q IncidentQuery) RAGPath {
    text := strings.ToLower(q.Text)

    // Skip retrieval if working memory already has a high-confidence answer
    if q.Confidence >= 0.92 {
        return SkipRetrieval
    }

    isRelational := containsAny(text,
        "blast radius", "depends on", "dependency", "upstream", "downstream",
        "which services", "affect", "cascade", "propagate",
    )
    isTemporal := containsAny(text,
        "last week", "yesterday", "before the incident", "what changed",
        "when did", "history of", "previously", "rollback to",
    )
    isProcedural := containsAny(text,
        "runbook", "how to fix", "steps to", "remediation",
        "restart", "rollback", "mitigate", "resolve",
    )

    switch {
    case isRelational && isTemporal:
        return MultiPath // GraphRAG + TemporalKG

    case isRelational:
        return GraphRAG

    case isTemporal:
        return TemporalKG

    case isProcedural:
        return VectorHybrid

    default:
        // General query: use vector hybrid, with possible GraphRAG supplement
        return VectorHybrid
    }
}
```

### MultiPath Result Merging

When MultiPath is selected, both retrieval paths run in parallel (goroutines) and results are merged:

```go
func retrieveMultiPath(ctx context.Context, q IncidentQuery) ([]RetrievedChunk, error) {
    var (
        graphResults  []RetrievedChunk
        vectorResults []RetrievedChunk
        graphErr      error
        vectorErr     error
        wg            sync.WaitGroup
    )

    wg.Add(2)
    go func() {
        defer wg.Done()
        graphResults, graphErr = graphRAGRetrieve(ctx, q)
    }()
    go func() {
        defer wg.Done()
        vectorResults, vectorErr = hybridSearchRetrieve(ctx, q)
    }()
    wg.Wait()

    if graphErr != nil && vectorErr != nil {
        return nil, fmt.Errorf("both retrieval paths failed: graph=%v vector=%v", graphErr, vectorErr)
    }

    // Deduplicate by chunk ID, prefer higher-scored version
    return deduplicateAndMerge(graphResults, vectorResults), nil
}
```

## 5. GraphRAG Path (FalkorDB)

### When to Use

```
USE GraphRAG:
  "Which services depend on payments-db?"
  "What is the blast radius if auth-service goes down?"
  "Show me all upstream dependencies of checkout-api"
  "What other services could be affected by this failure?"

DO NOT USE GraphRAG:
  "Show me the runbook for connection pool exhaustion"
  "How do I restart payments-api?"
  "What does OOMKilled error 137 mean?"
  → These are procedural/factual → VectorHybrid
```

### The Graph Index Is Not a Secondary Index

The FalkorDB service dependency graph (defined in Stage 1) is the live topology maintained by paladin-topology-watcher. GraphRAG does not build a separate index — it queries the same graph that reflects the current infrastructure state. This means:

- Graph is always up to date (topology changes propagate within seconds)
- No expensive "build time" for GraphRAG — the graph exists for operational purposes
- GraphRAG adds LLM-assisted Cypher generation on top of an existing operational store

### Cypher Generation Flow

```
Natural language query
        │
        ▼
LLM call (Tier A, fast) via paladin-gateway
Prompt: "Given this service graph schema, generate a Cypher query
         that answers: [user question]"
Schema context: node types, relationship types, property names
        │
        ▼
Generated Cypher query
  e.g. MATCH (s:Service)-[:DEPENDS_ON*1..3]->(db:Database {name:'payments-db'})
       RETURN s.name, s.team, s.criticality
        │
        ▼
FalkorDB execution (paladin-graph gRPC service)
        │
        ▼
Structured result rows
        │
        ▼
Format as numbered list or table for agent context
```

### Go Sketch

```go
// pkg/retrieval/graphrag.go

type GraphRAGRetriever struct {
    gateway    GatewayClient  // paladin-gateway for LLM call
    falkordb   FalkorDBClient // paladin-graph gRPC client
}

func (g *GraphRAGRetriever) Retrieve(
    ctx context.Context,
    q IncidentQuery,
) ([]RetrievedChunk, error) {

    // Step 1: generate Cypher via LLM
    cypher, err := g.gateway.GenerateCypher(ctx, &GenerateCypherRequest{
        Question:   q.Text,
        Schema:     g.falkordb.GetSchema(ctx),
        MaxTokens:  256,
        Model:      "claude-haiku-4-5", // Tier A — cheap and fast
    })
    if err != nil {
        return nil, fmt.Errorf("generate cypher: %w", err)
    }

    // Step 2: validate Cypher (simple: check for injection, max depth)
    if err := validateCypher(cypher); err != nil {
        return nil, fmt.Errorf("invalid cypher: %w", err)
    }

    // Step 3: execute on FalkorDB
    rows, err := g.falkordb.Query(ctx, q.TenantID, cypher)
    if err != nil {
        return nil, fmt.Errorf("falkordb query: %w", err)
    }

    // Step 4: format rows as a single synthetic chunk for the agent
    formatted := formatGraphRows(rows, q.Text)
    return []RetrievedChunk{
        {
            Source:   "graph",
            Text:     formatted,
            Score:    1.0, // graph results are structural, not scored
            Metadata: map[string]string{"cypher": cypher},
        },
    }, nil
}
```

### Cypher Injection Protection

The generated Cypher is validated before execution:

- Must not contain `DELETE`, `DETACH DELETE`, `REMOVE`, `SET`, `CREATE`, `MERGE`
- Must not exceed traversal depth of 5 hops (`*1..5` maximum)
- Must include tenant filter: `{tenant_id: $tenantID}` (injected server-side if missing)
- Executed with read-only FalkorDB user credentials

## 6. Contextual Retrieval Implementation

### The Problem

Without context, a chunk like:

> "Restart the service after clearing the connection pool."

is retrieved poorly for queries about payments-api connection pool exhaustion, because the chunk text alone doesn't mention which service or what the surrounding document context is.

### The Solution — Anthropic's Contextual Retrieval

At ingest time, a 50–100 token context prefix is generated for each chunk by calling Claude Haiku via paladin-gateway. This prefix is prepended to the chunk text before embedding. The chunk text itself is stored separately.

With contextual retrieval, the same chunk becomes:

> "In the context of the payments-api connection pool exhaustion runbook (payments-service, production environment), this step describes restarting payments-api-v2 after draining active connections and clearing the connection pool. Restart the service after clearing the connection pool."

The full enriched text is embedded. At retrieval time, only the raw chunk text is shown to the agent (the context prefix is metadata, not surfaced directly).

### Prompt Caching for Cost Efficiency

Anthropic's prompt caching applies at the document level: the full document text is placed in the system prompt (cached), and each chunk is submitted as the human turn. One cache write per document, N cheap cache reads for N chunks.

```
Cache write (one-time per document, per model version):
  System: [full document text — up to 32k tokens]
  → cache_control: {"type": "ephemeral"}

Cache read (one per chunk, cheap):
  Human: "Generate a 50-100 token context for this chunk:
          [chunk text]
          Context should identify: document title, section,
          key entities (service name, environment, error type),
          and how this chunk relates to the document's purpose."
  → uses cached system prompt
```

Estimated cost: $1.02 per million document tokens (one-time ingest). Retrieval quality improvement: 49% reduction in retrieval failures, 67% when combined with reranking (from Stage 3.5 research).

### Go Implementation

```go
// pkg/ingestion/context_enrichment.go

type ContextEnricher struct {
    gateway GatewayClient
}

type EnrichedChunk struct {
    Chunk
    ContextPrefix string // generated by LLM
    FullText      string // ContextPrefix + "\n" + Chunk.Text (used for embedding)
}

func (e *ContextEnricher) EnrichChunks(
    ctx context.Context,
    doc Document,
    chunks []Chunk,
) ([]EnrichedChunk, error) {

    enriched := make([]EnrichedChunk, 0, len(chunks))

    // The document text is the cached system prompt.
    // We send all chunk enrichment requests as a streaming batch.
    for _, chunk := range chunks {
        prefix, err := e.gateway.GenerateChunkContext(ctx, &GenerateChunkContextRequest{
            DocumentText:  doc.FullText,  // will be cached by Anthropic
            ChunkText:     chunk.Text,
            Model:         "claude-haiku-4-5",
            MaxTokens:     120,
            CacheDocument: true,          // signals gateway to use prompt caching
        })
        if err != nil {
            // Non-fatal: fall back to chunk without enrichment
            prefix = ""
        }

        fullText := chunk.Text
        if prefix != "" {
            fullText = prefix + "\n" + chunk.Text
        }

        enriched = append(enriched, EnrichedChunk{
            Chunk:         chunk,
            ContextPrefix: prefix,
            FullText:      fullText,
        })
    }

    return enriched, nil
}
```

The paladin-gateway handles the Anthropic SDK call including cache_control headers. The enricher does not call Anthropic directly.

### What Gets Stored in Qdrant

```
Qdrant point payload:
  raw_text:       chunk.Text        (shown to agent)
  context_prefix: chunk.ContextPrefix (stored, not shown)
  full_text:      chunk.FullText    (was embedded — not stored to save space)
  doc_id:         doc.ID
  chunk_index:    chunk.ChunkIndex
  source_url:     doc.SourceURL
  tenant_id:      tenantID
  ingested_at:    time.Now().UTC()
  etag:           doc.ETag
```

The `full_text` (enriched text that was embedded) is not stored — only the `raw_text` is returned to the agent. The embedding already encodes the contextual information.

## 7. HyDE — Hypothetical Document Embeddings

### The Insight

Natural language queries are phrased differently from documents. A user asks: "what caused the December outage?" but the postmortem says "Root cause: certificate expiry in payments-auth triggered cascading timeouts." Embedding the query directly finds poor lexical overlap. Embedding a hypothetical answer finds the postmortem.

### When to Use vs Avoid

```
USE HyDE:
  Natural language questions:
    "what caused the December outage?"
    "why did our p99 latency spike last Tuesday?"
    "what's the usual cause of this kind of error?"
  → Query phrasing differs significantly from document language

DO NOT USE HyDE:
  Exact/technical lookup queries:
    "OOMKilled error 137 runbook"
    "payments-api connection pool exhaustion steps"
    "kubernetes pod crashloopbackoff"
  → Exact terms already match SPLADE sparse exactly
  → HyDE hypothetical answer may drift from exact terminology
  → Hurts precision for exact lookups
```

### Decision Logic — When to Activate HyDE

The RAG router sets a flag based on query characteristics:

```go
func shouldUseHyDE(query string) bool {
    // Contains question words → natural language → use HyDE
    questionWords := []string{"why", "what caused", "what happened",
                              "how did", "when did", "why did"}
    for _, w := range questionWords {
        if strings.Contains(strings.ToLower(query), w) {
            return true
        }
    }

    // Contains technical exact terms → skip HyDE
    exactPatterns := []string{
        "oomkilled", "error ", "runbook", "crashloop",
        "steps to", "how to", "exit code",
    }
    for _, p := range exactPatterns {
        if strings.Contains(strings.ToLower(query), p) {
            return false
        }
    }

    return false // default: don't use HyDE
}
```

### Implementation

```go
// pkg/retrieval/hyde.go

type HyDERetriever struct {
    gateway  GatewayClient
    embedder Embedder
    qdrant   QdrantRetriever
}

func (h *HyDERetriever) Retrieve(
    ctx context.Context,
    q IncidentQuery,
) ([]ScoredDoc, error) {

    // Step 1: generate hypothetical answer
    hypoAnswer, err := h.gateway.Complete(ctx, &CompletionRequest{
        Model:     "claude-haiku-4-5", // Tier A — cheap
        MaxTokens: 256,
        Prompt: fmt.Sprintf(
            "Write a brief, factual answer to the following question "+
            "as if you were a postmortem document or runbook. "+
            "Be specific about services, errors, and timelines.\n\n"+
            "Question: %s\n\nAnswer:", q.Text,
        ),
    })
    if err != nil {
        // Fall back to standard query embedding
        return h.qdrant.HybridSearch(ctx, HybridSearchRequest{
            TenantID:  q.TenantID,
            QueryText: q.Text,
        })
    }

    // Step 2: embed the hypothetical answer (not the original query)
    hypoEmb, err := h.embedder.EmbedAll(ctx, hypoAnswer)
    if err != nil {
        return nil, fmt.Errorf("embed hypothetical: %w", err)
    }

    // Step 3: also embed the original query
    origEmb, err := h.embedder.EmbedAll(ctx, q.Text)
    if err != nil {
        return nil, fmt.Errorf("embed original: %w", err)
    }

    // Step 4: retrieve using both embeddings, take union
    hypoResults, _ := h.qdrant.SearchDense(ctx, q.TenantID, hypoEmb.Dense, 20)
    origResults, _ := h.qdrant.SearchDense(ctx, q.TenantID, origEmb.Dense, 20)

    // Merge and deduplicate; HyDE results get slight score boost (empirical)
    merged := unionResults(hypoResults, origResults, 0.05 /* hypo boost */)

    // Step 5: rerank the union with original query text
    return h.qdrant.Rerank(ctx, q.Text, merged)
}
```

## 8. Self-RAG Reflection

### The Problem

Retrieved chunks are not always relevant. Without reflection, irrelevant or hallucination-supporting chunks get passed to the synthesis LLM, causing the 12–14% hallucination rate seen in baseline RAG systems.

### Reflection Token Types

```go
// pkg/retrieval/selfrag.go

type ReflectionScore struct {
    PointID     string
    IsRelevant  bool    // IsREL: chunk relates to the query topic
    IsSupported bool    // IsSUP: chunk contains enough info to contribute to an answer
    IsUseful    bool    // IsUSE: including this chunk improves response quality
    Reason      string  // one-sentence explanation (for observability)
}
```

**IsREL** — Does the chunk address the subject of the query at all?
- "payments-api runbook" retrieved for "auth-service error" → IsREL = false

**IsSUP** — Does the chunk contain sufficient information to be useful?
- Chunk is intro paragraph with no actionable content → IsSUP = false

**IsUSE** — Given all other retrieved chunks, does this one add marginal value?
- Duplicate of chunk already included → IsUSE = false

### Integration in Eino Graph

Self-RAG reflection runs as a node in the Eino execution graph (Stage 3, paladin-agent):

```
[retrieve_node]
     │
     ▼ top-5 chunks (post-reranker)
[reflect_node]
     │ LLM call (Tier A): score each chunk
     │ IsREL + IsSUP + IsUSE
     │
     ├─ all chunks fail IsSUP → [no_runbook_node] → "no relevant runbook found"
     │
     └─ some chunks pass    → [filter_node] → keep passing chunks
                                    │
                                    ▼
                            [synthesize_node]
                            passing chunks → LLM synthesis
```

### Go Implementation

```go
func (r *SelfRAGReflector) ScoreChunks(
    ctx context.Context,
    query string,
    chunks []ScoredDoc,
) ([]ScoredDoc, error) {

    if len(chunks) == 0 {
        return nil, nil
    }

    // Build batch reflection prompt
    prompt := buildReflectionPrompt(query, chunks)

    resp, err := r.gateway.Complete(ctx, &CompletionRequest{
        Model:     "claude-haiku-4-5", // Tier A
        MaxTokens: 512,
        Prompt:    prompt,
    })
    if err != nil {
        // On failure, pass all chunks through (fail-open for retrieval)
        return chunks, nil
    }

    scores := parseReflectionScores(resp, len(chunks))

    var passing []ScoredDoc
    for i, chunk := range chunks {
        s := scores[i]
        if s.IsRelevant && s.IsSupported && s.IsUseful {
            passing = append(passing, chunk)
        }
    }

    return passing, nil
}

func buildReflectionPrompt(query string, chunks []ScoredDoc) string {
    var sb strings.Builder
    sb.WriteString(fmt.Sprintf(
        "Query: %s\n\nFor each retrieved chunk below, respond with "+
        "IsREL (relevant), IsSUP (supports answer), IsUSE (useful to include). "+
        "Format: CHUNK_N: IsREL=true/false IsSUP=true/false IsUSE=true/false\n\n",
        query,
    ))
    for i, chunk := range chunks {
        sb.WriteString(fmt.Sprintf("CHUNK_%d:\n%s\n\n", i+1,
            chunk.Payload["raw_text"]))
    }
    return sb.String()
}
```

Target hallucination rate: 5.8% (vs 12–14% baseline). From Stage 3.5 research.

## 9. Semantic Cache for RAG Results

### Two-Level Caching

RAG caching operates at two levels:

```
Level 1 — LLM response cache (Stage 3.5):
  Cache key: sha256(final_prompt)
  TTL: varies by query type
  Hit: skip LLM synthesis entirely

Level 2 — RAG retrieval cache (this stage):
  Cache key: sha256(query_embedding_quantized + tenant_id + retrieval_params)
  TTL: 5min (dynamic queries) / 30min (runbook queries)
  Hit: skip Qdrant + reranker + Self-RAG entirely
```

The retrieval cache is especially valuable during active incidents: the same question ("what's the runbook for this?") is asked repeatedly by multiple operators. The second query hits the cache and returns in ~2ms instead of ~80ms.

### Cache Key Construction

```go
// pkg/retrieval/cache.go

func buildRAGCacheKey(
    queryEmbedding []float32,
    tenantID string,
    params RetrievalParams,
) string {
    // Quantize dense vector to int8 to reduce sensitivity to floating point noise
    quantized := quantizeFloat32ToInt8(queryEmbedding)

    h := sha256.New()
    h.Write(quantized)
    h.Write([]byte(tenantID))
    h.Write([]byte(params.CollectionName))
    binary.Write(h, binary.LittleEndian, int32(params.TopK))

    return hex.EncodeToString(h.Sum(nil))
}

func quantizeFloat32ToInt8(v []float32) []byte {
    out := make([]byte, len(v))
    for i, f := range v {
        // Scale to [-127, 127]
        scaled := f * 127.0
        if scaled > 127 { scaled = 127 }
        if scaled < -127 { scaled = -127 }
        out[i] = byte(int8(scaled))
    }
    return out
}
```

### TTL Policy

```
Query type                           TTL
─────────────────────────────────────────
Runbook query (stable content)       30 min
Postmortem / historical query        1 hour
Topology/graph query                 2 min  (topology changes frequently)
Active incident query                5 min  (things change fast)
```

Query type is determined by the router (same classification as RAGPath routing).

### Valkey Backend

Valkey (Stage 3.5, L2 semantic cache) is the backend. The retrieval cache stores serialized `[]ScoredDoc` as MessagePack (compact binary):

```go
func (c *RAGCache) Get(ctx context.Context, key string) ([]ScoredDoc, bool) {
    raw, err := c.valkey.Get(ctx, "rag:"+key).Bytes()
    if err != nil {
        return nil, false
    }
    var docs []ScoredDoc
    if err := msgpack.Unmarshal(raw, &docs); err != nil {
        return nil, false
    }
    return docs, true
}

func (c *RAGCache) Set(ctx context.Context, key string, docs []ScoredDoc, ttl time.Duration) {
    raw, err := msgpack.Marshal(docs)
    if err != nil {
        return
    }
    c.valkey.Set(ctx, "rag:"+key, raw, ttl)
}
```

Semantic cache cosine hit threshold (from Stage 3.5): ≥ 0.92. This means queries that are semantically similar (rephrased same question) hit the same cache entry. The embedding is computed first, quantized, and the key lookup resolves in O(1).

## 10. Evaluation: Retrieval Quality Metrics

### Target Metrics (from Stage 3.5)

| Metric | Target | Definition |
|--------|--------|------------|
| Recall@5 | ≥ 0.85 | Fraction of relevant docs appearing in top 5 |
| MRR | ≥ 0.70 | Mean Reciprocal Rank of first relevant doc |
| NDCG@5 | ≥ 0.75 | Normalized Discounted Cumulative Gain at 5 |
| Reranker top-1 score | ≥ 0.60 | Threshold below which we return "no runbook found" |

### Ground Truth Label Collection

**Offline (initial baseline):**
- Extract (query, relevant_runbook) pairs from postmortems:
  - A postmortem documents an incident → the runbook used is the ground truth relevant doc
  - Automated: parse postmortem "Runbook used" field (structured)
  - Manual: quarterly labeling sprint (2 engineers, 100 pairs each)
- Target: 500 labeled pairs per tenant at launch, 2,000 within 6 months

**Online (implicit signal):**
- When the synthesis LLM uses a retrieved chunk in its response (cites it), that chunk is marked as implicitly relevant
- When the agent takes a remediation action that resolves the incident (human confirms), the retrieved chunks that led to that action are marked as ground truth positives
- Stored in ClickHouse `retrieval_feedback` table with chunk IDs and outcome

**Evaluation job (nightly):**

```
Nightly cron (paladin-eval service):
  1. Load labeled pairs from Postgres (offline) + ClickHouse (online)
  2. For each pair: run hybrid search with current model
  3. Compute Recall@5, MRR, NDCG@5
  4. Compare to yesterday's metrics
  5. Alert if Recall@5 drops > 3% day-over-day
  6. Publish metrics to ClickHouse → Grafana dashboard
```

## 11. Embedding Model Updates

### Update Cadence

BGE-M3 is fine-tuned quarterly on infrastructure-domain data (Kubernetes events, cloud provider runbooks, SRE postmortems). Each fine-tuning cycle produces a new model version deployed to Triton.

### Transition Strategy — Dual-Write

When a new model version is ready:

```
Phase 1 — Shadow (week 1):
  New Triton model deployed alongside old
  New collection created: runbooks_pool_v2
  All new ingest writes to BOTH runbooks_pool (v1) and runbooks_pool_v2
  Old queries still served from runbooks_pool_v1

Phase 2 — A/B (week 2):
  10% of tenant traffic routed to runbooks_pool_v2
  Metrics collected: Recall@5 per model version
  If v2 Recall@5 > v1 Recall@5 by ≥ 2%: proceed
  If v2 worse: abort, investigate fine-tuning

Phase 3 — Cutover (week 3):
  Traffic shifted to 100% runbooks_pool_v2
  runbooks_pool_v1 kept read-only for 2 weeks (rollback insurance)
  Lazy re-embed of any docs not yet in v2 (triggered on first access)
  Full batch re-embed scheduled to complete within 2 weeks

Phase 4 — Cleanup (week 5):
  runbooks_pool_v1 deleted
  Triton v1 model unloaded
```

### Lazy Re-embed vs Batch Re-embed

| Strategy | Pros | Cons | When to use |
|----------|------|------|-------------|
| Lazy re-embed | Zero downtime, prioritizes hot docs first | Query may hit v1 or v2 result inconsistency for 2 weeks | Default for quarterly updates |
| Batch re-embed | Full collection on v2 before cutover | Triton load spike, longer transition | Major architecture changes only |

For quarterly fine-tune cycles, lazy re-embed is preferred. Hot documents (accessed in last 30 days) are prioritized: the batch re-embed job processes them first using access frequency from ClickHouse retrieval_events.

### A/B Test Implementation

The router applies tenant-level traffic splitting:

```go
func (r *QdrantRetriever) selectCollection(tenantID string) string {
    if r.abConfig.IsEnabled() {
        // Deterministic split: sha256(tenantID) % 100 < splitPercent
        h := sha256.Sum256([]byte(tenantID))
        bucket := int(h[0]) % 100
        if bucket < r.abConfig.V2SplitPercent {
            return "runbooks_pool_v2"
        }
    }
    return "runbooks_pool"
}
```

The A/B split is at tenant level (not request level) to avoid within-session inconsistency. A tenant always sees results from the same model version during the A/B window.

### Triton Model Version Management

```
Triton model repository layout:

/models/
  bge-m3/
    1/          ← current production version
      model.plan (TensorRT engine)
    2/          ← new version (shadow/A-B phase)
      model.plan
    config.pbtxt
      version_policy: { specific: { versions: [1, 2] } }
```

Triton serves both versions simultaneously. Go calls specify `ModelVersion: "1"` or `"2"` in the inference request. The router selects the version based on the collection being queried.

## 16. MMR Diversity (Maximal Marginal Relevance)

After RRF fusion, before reranker:

```
Without MMR: top-5 chunks may all be from same runbook section
With MMR (λ=0.7): top-5 covers diverse aspects of the problem

score_mmr(d) = λ × sim(query, d) - (1-λ) × max(sim(d, already_selected))

λ=0.7: 70% relevance, 30% diversity penalty
Effect: information coverage improves from ~2.3 to ~3.8 distinct aspects
Cost: O(n²) comparison at n=30, trivial

Per-intent tuning:
  Procedural queries: λ=0.65 (want diverse steps)
  Factual queries:    λ=0.85 (want most relevant facts)
```

## 17. CRAG (Corrective RAG)

After retrieval, evaluate quality with Qwen3-8B classifier:

```
Score: "Are these retrieved chunks relevant to: [query]?" → 0.0-1.0

Score > 0.7:    use retrieved chunks normally
Score 0.3-0.7:  SUPPLEMENT with external_knowledge collection (Stage 13)
Score < 0.3:    REPLACE entirely with external_knowledge search
                + flag "no internal runbook found — using external reference"

Prevents hallucination when no relevant internal runbook exists.
Falls back to research agent's external knowledge corpus.
```

## 18. Long Context Reorder

Free improvement — pure list manipulation, zero cost.

Research finding (Stanford, 2023): LLMs perform worst on information in MIDDLE of context. Best at beginning and end.

```
Reranker output: [0.92, 0.88, 0.81, 0.74, 0.68]
                  best                      worst

REORDER edges-first:
  [0.92, 0.81, 0.68, 0.74, 0.88]
   ↑ #1               ↑ #2

Most relevant chunks at positions 1 and N (where attention is highest)
Least relevant in middle (where attention drops)
Apply when passing >5 chunks to LLM
```

Reduce synthesis input tokens by 60-70% with minimal quality loss.

```

  Target: 512 tokens → ~150-200 tokens

No LLM call (pure rule-based)
Skip compression if chunk < 200 tokens already
Saves ~$0.002 per query in synthesis input cost
```

## 22. Conditional HyDE — Updated Trigger

Replace keyword-based HyDE trigger with retrieval-confidence-based.

```go
func shouldUseHyDE(query string, initialTopScore float32) bool {
    // Primary: initial retrieval ambiguous
    if initialTopScore < 0.55 {
        return true  // query doesn't match corpus well
    }
    // Secondary: natural language with no exact terms
    hasQuestion := containsAny(query, "why", "what caused", "how did")
    hasExact := containsServiceName(query) || containsErrorCode(query)
    return hasQuestion && !hasExact
}
```

HyDE called AFTER initial fast dense search to get top-1 score.
Cuts HyDE overhead by 60-70% (only fires when actually needed).

## 25. Advanced Indexing Strategies

### RAPTOR — for Large Stable Architecture Docs

Build hierarchical tree of summaries:
- Level 0 (leaves): original 512-token chunks
- Level 1: summaries of clustered leaf chunks (5-10 per cluster)
- Level 2: summaries of level-1 summaries
- Root: full document summary

Query searches ALL levels simultaneously. Reranker selects best match regardless of level.

USE WHEN: Architecture docs, system design docs, large stable references
DO NOT USE FOR: Daily postmortems, frequently updated runbooks (rebuild cost too high)
COST: ~10x ingest cost (LLM pass per cluster level), one-time
GAIN: 20% accuracy on high-level queries (RAPTOR paper benchmark)

### Parent-Child Chunking — for Runbooks

```
Index: small child chunks (128 tokens) for precise retrieval
Return: parent chunks (512 tokens) for full LLM context

Structure:
  Parent: "Section 3: Connection Pool Configuration"
    Child 1: "Default pool_size is 100 connections..."
    Child 2: "When pool exhausted, requests block..."
    Child 3: "To increase, edit config.yaml..."

Search finds child chunk → return parent chunk via parent_chunk_id

Qdrant payload additions:
  parent_chunk_id: keyword
  is_parent: bool
```

USE WHEN: Step-by-step runbooks, postmortems with structured sections
GAIN: precision of small chunks + context of large chunks

### Late Chunking — for Frequently Updated Docs

```
1. Embed ENTIRE document with long-context model (jina-embeddings-v3, 8192 tokens)
2. Embedding model sees full document context during encoding
3. After encoding: slice the output embedding sequence at chunk boundaries
4. Each chunk embedding implicitly contains full document context

Quality: near-comparable to contextual retrieval
Cost: ZERO LLM calls (vs $1.02/M tokens for contextual retrieval)
```

USE WHEN: Daily postmortems, runbooks with weekly patches, incident reports
USE CONTEXTUAL RETRIEVAL FOR: Core stable runbooks, SLA docs, ADRs

### Strategy Decision Matrix

| Doc Type | Strategy | Reason |
|---|---|---|
| Large stable arch docs | RAPTOR | Long, varied query granularity |
| Active runbooks | Parent-child chunking | Precision + full context |
| Frequently updated docs | Late chunking | No LLM cost per update |
| Critical high-value docs | Contextual retrieval | Best quality, one-time cost |
| Daily postmortems | Late chunking | Frequent refresh |
