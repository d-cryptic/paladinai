# Stage 2 — Messaging & Async Alert Flow

**Date:** 2026-05-10
**Status:** Decisions locked (stage 2 complete)
**Scope:** NATS JetStream design, alert ingestion pipeline, deduplication, correlation

---

## Decision 1 — Message Queue: NATS JetStream

**Choice: NATS JetStream 2.10.x**

| | NATS JetStream | Kafka 4.0 | Redis Streams |
|---|---|---|---|
| Latency | sub-ms | 5-15ms | sub-ms |
| Ops complexity | Single binary | Medium (KRaft) | Zero (already have Valkey) |
| Multi-tenant routing | Subject hierarchy native | Partitions (less flexible) | Manual per-stream |
| At-least-once | Yes | Yes | Yes |
| Throughput ceiling | ~1M msg/s | 10M+ | 500K msg/s |

Kafka wins at 10M+ msg/s with many independent consumer teams. We are not there. NATS gives identical semantics with far less operational weight. Redis Streams would work but NATS is purpose-built for this and subject-level tenant isolation is a first-class feature.

Graduate to Kafka only when: throughput exceeds 1M msg/s sustained OR multiple independent engineering teams need to consume the same alert stream with hard isolation guarantees.

## Decision 2 — Subject Hierarchy

Multi-tenancy at the network level — not application code.

```
alerts.{tenant_id}.{severity}.{source}
  alerts.acme.p1.alertmanager
  alerts.acme.p2.datadog
  alerts.beta.p1.cloudwatch
  alerts.beta.p3.custom

triage.{tenant_id}.{incident_id}
runbook.{tenant_id}.{incident_id}.{step_id}
rca.{tenant_id}.{incident_id}
stream.{tenant_id}.{session_id}          ← agent events → paladin-ws → browser
memory.consolidation.{tenant_id}         ← weekly consolidation trigger
evals.replay.{suite_id}
dlq.{tenant_id}.{original_subject}       ← dead letters after 3 redelivery attempts
```

**Tenant credential scoping:** NATS credentials are issued per tenant and scoped at the NATS server level:
- Tenant `acme` can only publish/subscribe to `*.acme.*`
- Enforced by NATS server, not application code
- `paladin-ingest` uses a privileged system credential to publish to any subject after resolving tenant

## Decision 4 — AlertEnvelope Schema

Every source (Alertmanager, Datadog, CloudWatch, PagerDuty, custom) normalizes to this:

```go
type AlertEnvelope struct {
    ID         string          `json:"id"`          // UUID v7 (sortable by time)
    TenantID   string          `json:"tenant_id"`
    ReceivedAt time.Time       `json:"received_at"`
    Source     string          `json:"source"`      // "alertmanager" | "datadog" | "cloudwatch" ...
    Severity   string          `json:"severity"`    // "p1" | "p2" | "p3"
    Raw        json.RawMessage `json:"raw"`         // original payload, archived to R2
    Normalized NormalizedAlert `json:"normalized"`
    TraceID    string          `json:"trace_id"`    // OTel trace propagation
}

type NormalizedAlert struct {
    Name         string            `json:"name"`
    Description  string            `json:"description"`
    Labels       map[string]string `json:"labels"`       // service, namespace, cluster, env, ...
    Annotations  map[string]string `json:"annotations"`
    StartsAt     time.Time         `json:"starts_at"`
    EndsAt       *time.Time        `json:"ends_at"`       // nil if still firing
    GeneratorURL string            `json:"generator_url"`
}
```

UUID v7 is used for `ID` — it is time-sortable, which makes incident timeline queries on PG efficient (index scan in time order).

## Decision 5 — Alert Deduplication

**Fingerprint-based deduplication.** Not per-alert-ID, not simple title matching.

```go
fingerprint = sha256(tenant_id + alert_name + significant_labels)
// significant_labels = stable entity labels: {service, namespace, cluster}
// NOT value labels: {current_value, threshold, pod_ip}
```

Logic at `paladin-orchestrator` on every incoming `AlertEnvelope`:

```
Alert arrives → compute fingerprint
  └─ No open incident with this fingerprint
       → create new incident, publish to triage.{tenant}.{incident_id}
  
  └─ Open incident exists with this fingerprint
       └─ Severity unchanged AND within dedup window (default 10min, tenant-configurable)
            → increment fired_count
            → extend active_until
            → suppress: do NOT re-publish to triage (noise reduction)
       
       └─ Severity escalated (e.g., P3 → P1)
            → update incident severity
            → re-publish to triage with escalation context
            → agent re-runs with full context including previous analysis
       
       └─ Alert resolved (EndsAt is set)
            → mark resolved_at on incident
            → open 5-minute grace window (watch for flap)
            → if re-fires within grace → same incident, increment fired_count
            → if re-fires after grace → new incident (genuine re-occurrence)
```

**Dedup window is per-tenant configurable** in `paladin.yaml` (default 10min, range 1min-60min). Some orgs have slow cascading failures; others want aggressive noise reduction.

## Decision 6 — Alert Correlation / Grouping

**Yes to correlation. Simple rules. Transparent to the user.**

When a database goes down, 15 alerts can fire within 2 minutes across 6 upstream services. Without correlation: 15 incidents, 15 agent runs, each with partial context. With correlation: 1 incident, 15 signals, agent sees the full blast radius — RCA quality goes up significantly.

**Correlation key:**

```go
correlationKey = sha256(tenant_id + namespace_label + time_bucket)
// time_bucket = unix_timestamp / 300  (5-minute bucket, configurable)
```

**Logic at `paladin-orchestrator`** (runs after deduplication):

```
Alert arrives (post-dedup: this is a new or escalating alert)
  └─ Compute correlationKey
  
  └─ Open incident exists with this correlationKey
       → add AlertEnvelope as a Signal to that incident
       → increment signal_count, update last_signal_at
       → agent re-runs only if signal crosses a significance threshold
         (e.g., signal_count crosses 3, or a new service is affected)
  
  └─ No open incident with this correlationKey
       → create new incident
       → this alert becomes the first signal (parent)
       → publish to triage.{tenant}.{incident_id}
```

**Constraints:**
1. Never correlate across different namespaces by default — cross-namespace grouping with simple rules produces more false groupings than it solves
2. Cross-service or cross-namespace correlation can be enabled per-tenant in `paladin.yaml` with explicit label matchers
3. Always show the user *why* alerts were grouped (same namespace, same 5-min window) — transparency prevents silent wrong groupings
4. Manual split: UI allows engineers to break a correlation group into separate incidents

**Upgrade path:** once 6 months of incident data accumulates, replace the time+label rules with an ML classifier trained on historical grouping decisions.

**Correlation window** is per-tenant configurable (default 5min, range 1min-30min).

## Decision 7 — Incident Lifecycle Ownership

**`paladin-orchestrator` creates the incident. `paladin-agent` only reasons.**

```
paladin-orchestrator responsibilities:
  - Consume alerts.>
  - Run deduplication (fingerprint check against PG)
  - Run correlation (correlationKey check against PG)
  - Create/update incident row in PG
  - Start Hatchet workflow (P1/P2)
  - Publish to triage.{tenant}.{incident_id}

paladin-agent responsibilities:
  - Consume triage.> and runbook.> and rca.>
  - Run Eino agent graph
  - Call paladin-hub for tool discovery
  - Call MCP servers directly for tool execution
  - Call paladin-gateway for LLM
  - Read/write paladin-memory
  - Stream events to stream.{tenant}.{session_id}
  - Write checkpoint to PG after each step
```

**Why orchestrator owns creation:**
- Single source of truth for incident lifecycle — agent is ephemeral, orchestrator is durable
- Race condition protection — multiple agent pods compete on `triage.>`; PG unique constraint on fingerprint prevents duplicate incidents even if two orchestrator pods receive the same NATS message
- Hatchet workflow must start at orchestrator level anyway for P1s — consistent entry point

## Alert Flow: Full Timeline

```
T+0ms    Source fires (Alertmanager, Datadog, CloudWatch, custom webhook)

T+5ms    paladin-ingest (Go):
         1. Receive webhook POST /webhook/{integration}/{tenant_id}
         2. Verify HMAC-SHA256 against tenant's signing key (Vault)
         3. Resolve tenant_id from path param (validated against JWT)
         4. Normalize raw payload → AlertEnvelope
         5. Archive raw payload → Cloudflare R2 (async, non-blocking)
         6. Publish AlertEnvelope → NATS alerts.{tenant}.{sev}.{source}
         7. HTTP 200 to source

T+8ms    paladin-orchestrator (Go, Hatchet worker):
         Pull consumer on ALERTS stream
         1. Compute fingerprint → deduplication check (PG, indexed)
         2. Compute correlationKey → correlation check (PG, indexed)
         3. Create/update incident row in PG (ON CONFLICT for idempotency)
         4. If P1 → start Hatchet IncidentWorkflow
         5. Publish → NATS triage.{tenant}.{incident_id}

T+10ms   paladin-agent (Go, Eino):
         Pull consumer on WORK stream
         1. Picks up triage work item
         2. Calls paladin-hub: DiscoverTools(intent_hint, tenant_id, top_k=6)
         3. Hub returns relevant tool schemas + MCP endpoints
         4. Begins Eino graph: classify → parallel tool calls → synthesize
         5. Each graph step: write checkpoint to PG
         6. Each output token/event: publish → NATS stream.{tenant}.{session_id}

T+10ms   paladin-ws (Go):
         Push consumer on EVENTS stream (stream.{tenant}.{session_id})
         Forwards events over WebSocket to browser in real-time
         Also receives commands from browser (approve/reject runbook step)
         Forwards commands → NATS runbook.{tenant}.{incident_id}.{step_id}

T+60ms   Agent parallel tool calls (goroutines, all simultaneously):
         mcp-prometheus: query_range last 1h
         mcp-loki: tail last 5min
         mcp-k8s: describe_pod
         paladin-memory: search_episodic (similar past incidents)

T+800ms  LLM call: paladin-agent → paladin-gateway (internal HTTP)
         Gateway routes to Tier A (classify) → result
         Streamed tokens → NATS stream.{tenant}.{session_id} → browser

T+2-5s   Runbook execution or RCA hypothesis delivered
         PG incident updated: status, resolution, agent_summary
         CommsAgent: post to Slack / update PagerDuty

T+post   paladin-memory writes:
         - Episode to Zep (bi-temporal: valid_at=alert_starts_at, recorded_at=now())
         - FalkorDB topology update if new dependency observed

T+weekly paladin-memory consolidation CronJob:
         Cluster episodes by signature → summarize → Qdrant semantic store
```

**P95 latency targets:**
| Step | Target |
|---|---|
| Ingest → NATS | <10ms |
| Orchestrator dedup + correlate + PG write | <20ms |
| First stream token to browser | <1.5s |
| P2/P3 full triage | <5s |
| P1 RCA initial hypothesis | <10s |

## Reliability

**At-least-once delivery:** NATS JetStream. Agent acks message only after PG checkpoint write. Pod death → redelivery to another pod, idempotent via `ON CONFLICT`.

**Dead letter queue:** After 3 NAK/redelivery attempts, NATS moves to `dlq.{tenant}.{original_subject}`. Slack notification fired to tenant ops channel. DLQ retained 30 days.

**KEDA autoscaling:**
```yaml
# paladin-agent ScaledObject
triggers:
  - type: nats-jetstream
    metadata:
      stream: WORK
      consumer: agent-workers
      lagThreshold: "10"   # scale up when >10 pending messages
minReplicaCount: 3
maxReplicaCount: 200
```
