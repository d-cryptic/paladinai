## 0. Motivation

PaladinAI's current LLM strategy routes via paladin-gateway to OpenRouter with Chinese
frontier models (Qwen3-72B, DeepSeek-R1/V3, Kimi-K2) for cost efficiency. Many tasks
are repetitive and structurally bounded: alert classification, tool routing, anomaly
summarization. These are distillable into small, fast, cheap models without meaningful
quality loss.

Stage 17 builds the pipeline to produce, evaluate, and serve those models as first-class
gateway backends — no new serving interface, just new model aliases.

## 3. Fine-tuning: QLoRA

### 3.1 Method

| Parameter      | Value                                        |
|----------------|----------------------------------------------|
| Base models    | Qwen2.5-3B-Instruct, Qwen2.5-7B-Instruct    |
| Method         | QLoRA (4-bit NF4 quantization + LoRA)        |
| LoRA rank r    | 16                                           |
| LoRA alpha     | 32                                           |
| Target modules | q_proj, k_proj, v_proj                       |
| Dropout        | 0.05                                         |
| Epochs         | 3                                            |
| Batch size     | 4 (per device), grad accum 8 → effective 32  |
| LR             | 2e-4, cosine decay                           |
| Warmup steps   | 100                                          |
| Framework      | Unsloth (2× HF Trainer throughput, Apache 2.0)|
| Hardware       | A100 40GB spot — Lambda Labs, ~$2/hr         |
| Training time  | 1000 ex, 3 epochs → ~2hr on A100            |
| Output format  | Merged GGUF (Q4_K_M) for vLLM serving        |

### 3.2 Training Job Flow

```
  +--------------------------------------------------+
  | paladin-training-job (Kubernetes Job)             |
  |                                                   |
  |  1. pull dataset from S3                          |
  |  2. shuffle + 90/10 train/val split               |
  |  3. load base model (Qwen2.5-3B-Instruct)        |
  |  4. apply BitsAndBytes 4-bit quantization         |
  |  5. attach LoRA adapters (r=16, alpha=32)         |
  |  6. Unsloth FastLanguageModel.for_training()      |
  |  7. train 3 epochs                                |
  |  8. eval on val set → log loss + accuracy         |
  |  9. merge LoRA into base weights                  |
  | 10. export GGUF Q4_K_M                            |
  | 11. push to S3: models/slm/{task}/{version}/      |
  | 12. emit OTel event: training_complete            |
  +--------------------------------------------------+
```

### 3.3 Unsloth Config Snippet

```python
from unsloth import FastLanguageModel

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="Qwen/Qwen2.5-3B-Instruct",
    max_seq_length=2048,
    dtype=None,          # auto-detect
    load_in_4bit=True,
)

model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    target_modules=["q_proj", "k_proj", "v_proj"],
    lora_alpha=32,
    lora_dropout=0.05,
    bias="none",
    use_gradient_checkpointing=True,
    random_state=42,
)
```

## 4. Distillation Strategy (Alert Classification)

Knowledge distillation is applied for the alert classification task where the output space
is fully enumerable (severity × intent combinations).

```
  Teacher: Qwen3-72B (Tier A, current production model)
      |
      | generate soft-label outputs on training set
      | temperature T=4 (softens probability distributions)
      | capture full logits over {P1, P2, P3} × {intent_classes}
      v
  +-----------------------------------------------+
  | DISTILLATION LOSS                             |
  |                                               |
  | L = alpha * KL(student || teacher_soft)       |
  |   + (1-alpha) * CrossEntropy(student, label)  |
  |                                               |
  | alpha = 0.7  (weight toward teacher signal)   |
  | T = 4        (temperature for soft labels)    |
  +-----------------------------------------------+
      |
      v
  Student: Qwen2.5-3B fine-tuned on distilled outputs
```

**Why KL not just argmax:** Soft labels preserve the teacher's uncertainty signal.
If the teacher assigns P1=0.6, P2=0.35, P3=0.05 to an ambiguous alert, the student
learns to be appropriately uncertain — not overfit to a single hard label.

**Teacher cost during distillation:** One-time pass over training corpus via
Qwen3-72B on Groq. At 1000 examples with ~200 token average: ~$0.06 total. Negligible.

## 5. Evaluation Before Deployment

Every SLM candidate must clear the Stage 10 eval suite before receiving any live traffic.

```
  +-----------------------------------------------------------+
  | SLM EVAL GATE                                             |
  +-----------------------------------------------------------+
  |                                                           |
  | 1. CORRECTNESS                                            |
  |    Run full test case taxonomy for task:                  |
  |      alert_classification: 500 cases                      |
  |      tool_routing:         400 cases                      |
  |      anomaly_summary:      300 cases (ROUGE-L scorer)     |
  |                                                           |
  |    Gate: accuracy >= baseline_model_accuracy - 1%         |
  |    Baseline: recorded in Braintrust from Stage 10 CI      |
  |                                                           |
  | 2. LATENCY                                                |
  |    P95 latency < 100ms (alert_class, anomaly_summary)     |
  |    P95 latency < 150ms (tool_routing)                     |
  |    Measured: 1000 warmup requests → 1000 timed requests   |
  |    Against: vLLM pod serving GGUF Q4_K_M on A10G         |
  |                                                           |
  | 3. STATISTICAL SIGNIFICANCE                               |
  |    McNemar's test vs baseline model on matched test cases  |
  |    p < 0.05 required (two-tailed)                         |
  |    If SLM is WORSE: block deployment, file investigation   |
  |                                                           |
  | 4. COST CHECK                                             |
  |    Cost/classification must be < $0.00003                 |
  |    (vs $0.0003 Groq 70B baseline = 10× improvement)       |
  |                                                           |
  +-----------------------------------------------------------+
  | PASS all 4 gates → eligible for A/B rollout               |
  | FAIL any gate    → block, retrain or tune hyperparams     |
  +-----------------------------------------------------------+
```

Eval runner: `paladin-eval slm --model vllm/qwen2.5-3b-paladin-v1 --task alert_classification`
Results pushed to Braintrust project `paladin-slm-eval` for audit trail.

## 6. Serving Infrastructure

SLMs are served via vLLM 0.8.x on K8s and registered as model aliases in
paladin-gateway. From the agent layer, they are indistinguishable from any other model.

```
  paladin-agent (Go)
      |
      | POST /chat/completions
      | model: "fast-local"
      v
  paladin-gateway
      |
      | resolves alias → weighted backend list
      v
  +-------------------------------+    +-------------------------------+
  | vLLM pod (A10G)               |    | Groq (fallback)               |
  | qwen2.5-3b-paladin-v1         |    | llama-3.3-70b-versatile       |
  | GGUF Q4_K_M (~2GB VRAM)      |    |                               |
  | vLLM 0.8.x                    |    | triggered if:                 |
  | max_model_len: 4096           |    |   - vLLM pod unhealthy        |
  | tensor_parallel_size: 1       |    |   - latency > 500ms (circuit) |
  | served on :8000               |    |   - KEDA scale-down in flight |
  +-------------------------------+    +-------------------------------+
      |
      | KEDA HorizontalPodAutoscaler
      | scale triggers:
      |   - GPU utilization > 70%     → scale out
      |   - pending request count > 5 → scale out
      |   - min replicas: 1           (no scale-to-zero, Tier A)
      |   - max replicas: 8
      v
  Prometheus → KEDA metrics adapter
```

**vLLM deployment spec (abbreviated):**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vllm-slm-alert-class
  namespace: paladin-inference
spec:
  replicas: 1
  template:
    spec:
      containers:
        - name: vllm
          image: vllm/vllm-openai:0.8.x
          args:
            - --model /models/qwen2.5-3b-paladin-v1.gguf
            - --max-model-len 4096
            - --quantization gguf
            - --gpu-memory-utilization 0.85
          resources:
            limits:
              nvidia.com/gpu: "1"    # A10G (24GB VRAM, 2GB used)
          volumeMounts:
            - name: model-store
              mountPath: /models
      nodeSelector:
        node.kubernetes.io/gpu-type: a10g
```

**Model registration in paladin-gateway:**

```yaml

      - alert_classification
```

## 7. A/B Traffic Routing

Rollout is entirely config-driven. No code deploy needed to adjust weights.

```yaml
# paladin-gateway: config/model_aliases.yaml

model_aliases:
  fast-local:
    description: "Fast local SLM with Groq fallback"
    backends:
      - model: groq/llama-3.3-70b-versatile
        weight: 90        # 90% during initial rollout
      - model: vllm/qwen2.5-3b-paladin-v1
        weight: 10        # shadow / canary 10%
    fallback_on_error: groq/llama-3.3-70b-versatile
```

**Rollout schedule:**

```
  Day 0:  deploy vLLM pod, weight=10%
          measure: Braintrust live scores vs CI baseline
          measure: P95 latency in Grafana

  Day 2:  if no regression (accuracy drop <1%, no latency breach)
          → update config weight to 50%
          → alert on-call if error rate spikes >0.5%

  Day 4:  if stable at 50%
          → update config weight to 100%
          → Groq backend stays as fallback (weight=0, error fallback only)

  Rollback: set weight back to 0, no restart required
            gateway picks up config reload within 30s
```

**Metrics tracked during rollout (Grafana dashboard: slm-rollout):**

| Metric                          | Alert threshold       |
|---------------------------------|-----------------------|
| Classification accuracy (live)  | < baseline − 1%       |
| P95 latency per request         | > 150ms               |
| vLLM error rate                 | > 0.5%                |
| Fallback-to-Groq rate           | > 5% (indicates load) |
| GPU utilization                 | > 85% sustained       |

## 9. Cost Analysis

### 9.1 Current State: Groq 70B via OpenRouter

```
  Model:  groq/llama-3.3-70b-versatile
  Cost:   ~$0.00059/1K input tokens, ~$0.00079/1K output tokens
  Avg tokens per classification: ~300 input, ~50 output
  Per-call cost ≈ (300 × 0.00059 + 50 × 0.00079) / 1000
               ≈ $0.000177 + $0.0000395
               ≈ ~$0.00022/call  (rounded to ~$0.0003 incl. overhead)

  At 1M classifications/month:  1M × $0.0003 = $300/month
  At 5M classifications/month:  5M × $0.0003 = $1500/month
```

### 9.2 Target: 3B SLM, Self-Hosted

```
  Hardware: 1× NVIDIA A10G (24GB VRAM)
  Instance: spot on Lambda Labs / CoreWeave
  Cost:     ~$0.60/hr = $432/month (30 days × 24hr)
  GPU VRAM: ~2GB used (GGUF Q4_K_M 3B), 22GB headroom → could colocate 7B
  Throughput: vLLM on A10G @ 3B GGUF → ~200 req/s (estimated at 350 tokens)

  Per-call cost at 1M/month:  $432 / 1,000,000 = $0.000432/call
                               (WORSE than Groq at this volume!)

  Per-call cost at 5M/month:  $432 / 5,000,000 = $0.0000864/call
                               (3.5× cheaper than Groq)

  Break-even calculation:
    $432/month (fixed GPU) = N × $0.0003 (Groq variable)
    N = $432 / $0.0003 = 1,440,000 classifications/month
    Break-even: ~1.5M classifications/month
```

### 9.3 Volume Projection

```
  +----------------------------------------------------------+
  | Tenant count | Est. classif./month | SLM monthly saving |
  +--------------+---------------------+--------------------+
  |  10 tenants  |      200K           | -$372 (not worth)  |
  |  30 tenants  |      600K           | -$252 (not worth)  |
  |  50 tenants  |    1,000K (1M)      | -$132 (borderline) |
  | 100 tenants  |    2,000K (2M)      | +$168  (adopt)     |
  | 200 tenants  |    5,000K (5M)      | +$1068 (3.5×)      |
  +--------------+---------------------+--------------------+

  Recommendation: adopt SLM for alert classification when tenant
  count crosses 100 (est. 2M classifications/month, $168/mo saving).
  Begin building pipeline now (Stage 17) so infrastructure is ready.
```

### 9.4 Latency Improvement (Independent of Cost)

```
  Groq 70B:   P50 ~80ms, P95 ~250ms (network + inference)
  vLLM 3B:    P50 ~20ms, P95 ~60ms  (local, single GPU hop)

  Latency win = 4× at P95, even if cost break-even not yet reached.
  For Tier A tasks (alert classification during active incident),
  latency reduction alone justifies SLM above ~50 tenants.
```

## 10. Implementation Sequence

```
  Phase A — Data plumbing (weeks 1-2)
    [ ] paladin-data-collector: OTel → ClickHouse → S3 batch job
    [ ] Presidio anonymization integration
```

## 11. Dependencies & Risks

| Risk                              | Mitigation                                   |
|-----------------------------------|----------------------------------------------|
| <1000 labeled examples at launch  | Delay training; never train on unlabeled data|
| SLM accuracy below gate           | Tune r/alpha, add more distillation data     |
| A10G spot preemption mid-training | Checkpoint every 100 steps → resume from S3  |
| vLLM pod OOM                      | GGUF Q4_K_M 3B = ~2GB; A10G has 24GB; safe  |
| Presidio false-negative (PII leak)| Audit 100 random examples before S3 upload  |
| Soft-label teacher cost spike     | One-time per training run, ~$0.06 total      |
| Gateway config drift              | model_aliases.yaml in git, PR-reviewed       |

**Hard dependencies:**
- Stage 10 eval framework: Braintrust CI, test case taxonomy, feedback signals
- paladin-gateway: model alias + weighted routing already implemented
- vLLM 0.8.x: deployed as paladin-inference namespace (this stage adds first pod)
- KEDA: already installed in cluster (Stage 8 multi-tenancy)
