## 2. Active Mode — Hypothesis Generation

### Input

```go
type ActiveHypothesisInput struct {
    Alert       AlertEnvelope          // from NATS alert.enriched.*
```

### Processing

```
AlertEnvelope
     │
     ├─► [parallel] FalkorDB.QueryNeighbors(alert.service, depth=2)
     ├─► [parallel] paladin-memory.GetRecentEpisodes(service, 72h)
     └─► [parallel] PG.QueryPriors(fingerprint, intent_type)
                              │
                    all 3 resolve (<800ms budget)
                              │
                              ▼
                    LLM prompt ("smart" tier)
                    ┌────────────────────────────────────────────────┐
                    │ System: You are a site reliability hypothesis   │
                    │ generator. Given the alert, topology, and       │
                    │ recent incident history, produce 3–5 competing  │
                    │ hypotheses. For each: text, prior_probability,  │
                    │ and the evidence that would confirm or refute   │
                    │ it. Rank by prior_probability descending.       │
                    │                                                 │
                    │ Prior probabilities MUST use the base rates     │
                    │ provided. Bayesian update formula:              │
                    │   P(H) = base_rate × recency_weight             │
                    │   where recency_weight decays by 0.95^days      │
                    └────────────────────────────────────────────────┘
                              │
                              ▼  <2s total end-to-end
                    HypothesisList (structured JSON, validated)
```

### Prior Probability Computation

```
base_rate = hypothesis_priors.prior_probability
            WHERE fingerprint = alert.fingerprint
              AND intent_type  = alert.intent_type

recency_weight = 0.95 ^ days_since_last_occurrence

P(H) = base_rate × recency_weight

-- If no row exists: P(H) = 0.1 (uniform uninformed prior across 5 slots)
-- Priors are normalized to sum ≈ 1.0 across the hypothesis list
```

### Output

```go
type HypothesisList struct {
    AlertID    string       `json:"alert_id"`

}

type Hypothesis struct {
    ID               string   `json:"id"`           // uuid
    Text             string   `json:"text"`          // human-readable
    PriorProbability float64  `json:"prior_probability"`

    IntentType       string   `json:"intent_type"`   // dependency_failure | resource | config | deployment | cascade

```

### RCA Agent Phase 1 Integration

```
RCA Phase 1 — Evidence Collection
      │
      ├── receives HypothesisList from Hypothesis Agent
      │
```

## 3. Passive Mode — Failure Scenario Generation

### Hatchet Workflow Definition

```go
// workflow: hypothesis-passive-scan
// schedule: "0 3 * * *" (daily 03:00, configurable)

type PassiveWorkflow struct {
    // Step 1
    LoadTopology func(ctx context.Context) (TopologySnapshot, error)

    // Step 2 (depends on LoadTopology)
    IdentifyCriticalServices func(ctx context.Context, topo TopologySnapshot) ([]ServiceNode, error)

    // Step 3 (fan-out: one goroutine per critical service)
    GenerateScenarios func(ctx context.Context, svc ServiceNode) ([]FailureScenario, error)

    // Step 4 (depends on GenerateScenarios fan-in)
    ScoreScenarios func(ctx context.Context, scenarios []FailureScenario) ([]ScoredScenario, error)

    // Step 5
    StoreResults func(ctx context.Context, scored []ScoredScenario) error

    // Step 6 (conditional: only if hypothesis.weekly_report.enabled)
    GenerateReport func(ctx context.Context, scored []ScoredScenario) error
}
```

### Critical Service Identification

```
FalkorDB Cypher:
  MATCH (s:Service)-[r:DEPENDS_ON]->(dep:Service)
  WITH s, count(r) AS out_degree
  MATCH (caller:Service)-[:DEPENDS_ON]->(s)
  WITH s, out_degree, count(caller) AS in_degree
  RETURN s.name,
         (out_degree + in_degree) AS centrality_score
  WHERE centrality_score / total_services > 0.5
  ORDER BY centrality_score DESC

-- betweenness > 0.5 threshold (configurable via paladin.yaml)
-- typically returns 3–8 services per tenant
```

## 4. Chaos Simulation Integration

```
FailureScenario
      │
      ▼
  [Synthesizer]  — generates synthetic AlertEnvelope
  "if payment-service had a connection pool exhaustion,
   what would the alert look like?"

      │
      ▼
  SyntheticAlertEnvelope {
      fingerprint:    "payment-service.connection_exhaustion.synthetic",
      alert_type:     "latency_spike",
      service_labels: {service: "payment-service"},
      is_synthetic:   true,
      scenario_id:    <FailureScenario.ID>,
  }

      │
      ▼
  Replay Harness (Stage 10 eval infra)
  ├── runs full Hypothesis Agent + RCA Agent pipeline
  ├── expected_root_cause = FailureScenario.FailureMode
  └── scores: did RCA identify correct root cause?

      │
      ├── score >= 0.5 → scenario library quality_score updated
      │
      └── score < 0.5 → detection gap flagged
            ├── FailureScenario.DetectionGaps populated / appended
            ├── quality_score stored in PG + Qdrant metadata
            └── surfaced in weekly report (if enabled)

Quality score update:
  new_score = 0.7 × existing_score + 0.3 × simulation_result
  (exponential moving average, α=0.3)
```

## 5. Hypothesis Library Schema

### PostgreSQL

```sql
-- Prior probabilities for hypothesis types per alert fingerprint
CREATE TABLE hypothesis_priors (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    fingerprint      TEXT NOT NULL,       -- alert fingerprint
    intent_type      TEXT NOT NULL,       -- dependency_failure | resource | config | deployment | cascade
    hypothesis_text  TEXT NOT NULL,       -- canonical description
    prior_probability FLOAT8 NOT NULL DEFAULT 0.1,
    evidence_count   INT    NOT NULL DEFAULT 0,
    last_updated     TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (fingerprint, intent_type)
);

CREATE INDEX idx_hypothesis_priors_fingerprint ON hypothesis_priors (fingerprint);

-- Failure scenarios from passive mode
CREATE TABLE failure_scenarios (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    service           TEXT NOT NULL,
    failure_mode      TEXT NOT NULL,
    probability       FLOAT8 NOT NULL,
    blast_radius      TEXT[] NOT NULL DEFAULT '{}',
    leading_indicators TEXT[] NOT NULL DEFAULT '{}',
    detection_gaps    TEXT[] NOT NULL DEFAULT '{}',
    quality_score     FLOAT8 NOT NULL DEFAULT 1.0,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_simulated_at TIMESTAMPTZ,
    tenant_id         TEXT NOT NULL
);

CREATE INDEX idx_failure_scenarios_service ON failure_scenarios (tenant_id, service);
CREATE INDEX idx_failure_scenarios_quality ON failure_scenarios (quality_score);
```

## 7. Prior Probability Update Loop

```
Real incident resolves (RCA finalised)
              │
              ▼
  ┌──────────────────────────────────────────────────────────┐
  │  Was actual root cause in the HypothesisList?            │
  └──────────────────────────┬───────────────────────────────┘
                             │
              ┌──────────────┴──────────────┐
              │ YES                         │ NO
              ▼                             ▼
  matched_hypothesis found            all hypotheses in list:
  (by intent_type + fingerprint)        prior_probability × 0.9
                                        (soft decay — "none of these")
              │
              ▼
  Bayesian update (online, conjugate Beta prior):
  ──────────────────────────────────────────────
  α = evidence_count × prior_probability      -- pseudo-successes
  β = evidence_count × (1 - prior_probability) -- pseudo-failures

  α_new = α + 1  (this incident confirmed this hypothesis type)
  β_new = β      (unchanged)

  new_prior = α_new / (α_new + β_new)

  UPDATE hypothesis_priors
     SET prior_probability = new_prior,
         evidence_count    = evidence_count + 1,
         last_updated      = now()
   WHERE fingerprint = $fingerprint
     AND intent_type = $matched_intent_type;

              │
              ▼
  ┌───────────────────────────────────────────┐
  │  Re-rank: SELECT * FROM hypothesis_priors │
  │           WHERE fingerprint = $fingerprint │
  │           ORDER BY prior_probability DESC  │
  │           (used for next alert of same fp) │
  └───────────────────────────────────────────┘
              │
              ▼
  NATS publish: hypothesis.priors.updated
  (triggers cache invalidation in Hypothesis Agent)
```

### Feedback Loop ASCII

```
  Alert fires
      │
      ▼
  Hypothesis Agent         RCA Agent
  generates list     ───►  collects evidence
  with priors              scores posteriors
                           identifies root cause

                                ▼
                           RCA resolves
                                │
                          ┌─────┴──────┐
                          │  Feedback  │
                          │  Handler   │
                          └─────┬──────┘
                                │
              ┌─────────────────┼─────────────────┐
              ▼                 ▼                 ▼
      PG update           Qdrant metadata    FalkorDB edge
      prior_probability   quality_score      weight update
      evidence_count++    on scenario        (:RootCause)
                                │
                                └──► next alert same fingerprint
                                     uses updated priors ◄──┐
                                                             │
                                          ──────────────────┘
                                          (loop continues)
```

### Eino Node Implementations

```go
// Node: load_topology
type LoadTopologyNode struct {
    FalkorClient falkordb.Client
}

func (n *LoadTopologyNode) Process(ctx context.Context, _ struct{}) (TopologySnapshot, error) {
    return n.FalkorClient.QueryFullGraph(ctx, tenantFromCtx(ctx))
}

// Node: generate_scenarios (called per service in fan-out)
type GenerateScenariosNode struct {
    LLM         eino.ChatModel    // "fast" tier
    MemClient   paladin_memory.Client
    FalkorClient falkordb.Client
}

func (n *GenerateScenariosNode) Process(ctx context.Context, svc ServiceNode) ([]FailureScenario, error) {
    var scenarios []FailureScenario
    var mu sync.Mutex

    g, gctx := errgroup.WithContext(ctx)
    for _, mode := range allFailureModes {
        mode := mode
        g.Go(func() error {
            s, err := n.generateOne(gctx, svc, mode)
            if err != nil { return err }
            mu.Lock()
            scenarios = append(scenarios, s)
            mu.Unlock()
            return nil
        })
    }

    return scenarios, g.Wait()
}

// Node: score_scenarios
type ScoreScenariosNode struct {
    EvalHarness eval.Harness   // Stage 10 replay infra
}

func (n *ScoreScenariosNode) Process(ctx context.Context, scenarios []FailureScenario) ([]ScoredScenario, error) {
    var out []ScoredScenario
    for _, s := range scenarios {
        synthetic := BuildSyntheticAlert(s)
        result, err := n.EvalHarness.Replay(ctx, synthetic, s.FailureMode)
        if err != nil { continue }

        alpha := 0.3 // EMA weight
        newScore := alpha*result.Score + (1-alpha)*s.QualityScore
        out = append(out, ScoredScenario{Scenario: s, QualityScore: newScore})
    }
    return out, nil
}
```

## 11. Key Invariants

```
1. Passive mode never blocks Active mode — different Hatchet workflows, no shared locks.

2. Weekly report is OFF by default — no Slack messages without explicit opt-in.

3. All LLM calls in Passive mode use "fast" tier — cost control for volume processing.

4. All LLM calls in Active mode use "smart" tier — quality matters for incident response.

5. Chaos simulation scores are EMA-smoothed (α=0.3) — single bad run doesn't discard scenario.

6. Prior probability has a floor of 0.05 and ceiling of 0.95 — never absolute certainty.

7. Hypothesis Agent in Active mode must return within 2s — runs in parallel with RCA broad sweep.

8. FalkorDB is the topology source of truth — Passive mode reads it at start of each run.

9. paladin-memory gRPC is the only path for reading/writing episode history — no direct DB access.

10. tenant_id is always propagated — all PG queries, Qdrant payloads, FalkorDB queries are scoped.
```
