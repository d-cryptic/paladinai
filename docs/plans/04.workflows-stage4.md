# Stage 4 — Workflow Design

**Date:** 2026-05-10
**Status:** Decisions locked (stage 4 complete)
**Scope:** End-to-end workflow flows for alert ingestion, triage, RCA, runbook, approval, resolution, escalation, memory, integrations, and eval replay

---

## Common Conventions

| Symbol | Meaning |
|--------|---------|
| `→` | message or function call |
| `⟹` | async NATS publish |
| `▶` | Hatchet step boundary |
| `[PG]` | checkpoint write to Postgres |
| `[VLT]` | Vault secret access |
| `[QDR]` | Qdrant vector store |

**Idempotency default:** every consumer uses NATS `Nkey` + message sequence as dedup key. Every Hatchet step is idempotent via `ExternalID = fingerprint:step_name`.

## Workflow 1 — Alert Ingestion

**Trigger:** External webhook (Alertmanager, PagerDuty, Datadog, CloudWatch)
**Owner:** `paladin-ingest`
**NATS subjects:** `alerts.{tenant}.{severity}.{source}`
**Hatchet workflow:** none
**Idempotency:** NATS message dedup window 2 min on publish side; orchestrator dedup on fingerprint
**Latency budget:** <200ms ingest → NATS publish; dedup+correlate <300ms

```
Webhook POST /v1/ingest/{source}
  │
  ├─ HMAC-SHA256 verify (header X-Hub-Signature-256)
  │    fail → 401, log, drop
  │
  ├─ Normalize to AlertEvent{tenant,fingerprint,severity,labels,startsAt}
  │    source adapters: alertmanager.go, datadog.go, cloudwatch.go, pagerduty.go
  │
  ├─ Fingerprint = SHA-256(name + labels sorted + tenant)
  │
  ⟹ NATS publish alerts.{tenant}.{severity}.{source}
       headers: Nats-Msg-Id = fingerprint:startsAt (dedup key)

paladin-orchestrator (NATS pull consumer: ALERTS stream)
  │
  ├─ Dedup check
  │    query PG: SELECT id FROM incidents WHERE fingerprint=? AND status='open'
  │    duplicate → update last_seen_at, ack, done
  │
  ├─ Correlate
  │    match open incidents: same labels within 5-min window
  │    match → attach alert to existing incident, ack, done
  │
  ├─ Create incident
  │    INSERT incidents (id=UUIDv7, fingerprint, severity, tenant, status='open')
  │    [PG] checkpoint
  │
  ⟹ NATS publish triage.{tenant}.{incident_id}
```

## Workflow 2 — P3 Triage (NATS + Eino only)

**Trigger:** `triage.{tenant}.{incident_id}` message, severity=P3
**Owner:** `paladin-orchestrator` (Eino graph, no Hatchet)
**NATS subjects:** `triage.{tenant}.{incident_id}`, `stream.{tenant}.{session_id}`
**Hatchet workflow:** none
**Idempotency:** consumer group durable name `triage-p3`; NATS exactly-once via ack policy
**Latency budget:** P95 <5s end-to-end

```
NATS pull: triage.{tenant}.{incident_id}  (severity=P3)
  │
  ├─ Eino Supervisor node
  │    classify: routing, tool plan, context fetch
  │    input → IncidentContext{labels, alerts, runbook_hints}
  │
  ├─ TriageAgent (Eino parallel branch node)
  │    goroutine-A: metrics_query tool (Prometheus)
  │    goroutine-B: log_fetch tool (Loki/CloudWatch)
  │    goroutine-C: memory_search tool (Qdrant past episodes)
  │    all capped: 2s timeout per tool call
  │
  ├─ Synthesize node
  │    merge tool results → LLM call (1 hop)
  │    output: {summary, probable_cause, confidence, suggested_action}
  │
  ├─ Stream events
  │    for each token: ⟹ stream.{tenant}.{session_id}
  │    paladin-ws → WebSocket → browser
  │
  ├─ Write memory
  │    INSERT episode (incident_id, summary, outcome='triage_done')
  │    [PG] checkpoint
  │
  └─ ack NATS message → done
```

## Workflow 3 — P1 Incident (Full Hatchet)

**Trigger:** `triage.{tenant}.{incident_id}` message, severity=P1
**Owner:** `paladin-orchestrator` spawns Hatchet workflow
**NATS subjects:** `triage.{tenant}.{incident_id}`, `stream.{tenant}.{session_id}`, `rca.{tenant}.{incident_id}`
**Hatchet workflow:** `IncidentWorkflow`
**Idempotency:** `ExternalID = incident_id` (Hatchet deduplicates on first run)
**Latency budget:** RCA P95 <20s; total P1 flow P95 <90s (excluding human approval wait)

```
NATS pull: triage.{tenant}.{incident_id}  (severity=P1)
  │
  ⟹ hatchet.TriggerWorkflow("IncidentWorkflow", input={incident_id, tenant})

  IncidentWorkflow
  │
  ▶ Step: InitContext
  │    fetch incident + recent alerts + runbook index + memory hits
  │    [PG] checkpoint
  │
  ▶ Step: RCA  (see Workflow 3a below)
  │    3-phase RCA, max 3 LLM hops
  │    output: {root_cause, confidence, evidence}
  │    [PG] checkpoint
  │
  ▶ Step: SelectRunbook
  │    match RCA output → runbook library (PG + Qdrant)
  │    output: RunbookPlan{steps[]}
  │
  ▶ Step: HumanApprovalGate  (see Workflow 5)
  │    emit approval_required event
  │    suspend until signal "approved" or "rejected"
  │    rejected → escalate or close
  │
  ▶ Step: ExecuteRunbook  (see Workflow 4)
  │    iterate RunbookPlan.steps via RunbookStepWorkflow
  │    [PG] checkpoint after each step
  │
  ▶ Step: PostmortemTrigger
  │    emit postmortem_required event
  │    ⟹ NATS postmortem.{tenant}.{incident_id}
  │    [PG] status = 'resolved'
```

### Workflow 3a — RCA (inside IncidentWorkflow.RCA step)

**LLM hops:** max 3 | **Confidence gate:** 0.85 → skip Phase 3
**Latency budget:** P95 <20s across all 3 phases

```
Phase 1 — Symptom Analysis  (LLM hop 1)
  │  input: alerts, metrics, logs (parallel fetch via goroutines)
  │  output: {symptoms[], candidate_causes[], confidence}
  │  confidence ≥ 0.85 → skip Phase 2 and 3
  │
Phase 2 — Causal Chain  (LLM hop 2)
  │  input: Phase 1 output + topology data (CMDB/k8s graph)
  │  output: {causal_chain, root_cause_candidate, confidence}
  │  confidence ≥ 0.85 → skip Phase 3
  │
Phase 3 — Validation  (LLM hop 3)
  │  input: Phase 2 output + historical episodes from Qdrant
  │  output: {root_cause, confidence, evidence, similar_past_incidents[]}
  │
  └─ return RCAResult{root_cause, confidence, evidence, hops_used}
```

## Workflow 4 — Runbook Step Execution (Hatchet child workflow)

**Trigger:** called from `IncidentWorkflow.ExecuteRunbook` step
**Owner:** `paladin-agent`
**NATS subjects:** `runbook.{tenant}.{incident_id}.{step_id}`, `stream.{tenant}.{session_id}`
**Hatchet workflow:** `RunbookStepWorkflow`
**Idempotency:** `ExternalID = incident_id:step_id`
**Latency budget:** P95 <3s per step (excluding human approval wait)

```
▶ Step: PlanStep
  │  resolve step type: tool_call | script | api_call | human_action
  │  build ToolCallPlan{tool, args, verify_condition}
  │
▶ Step: ApprovalCheck
  │  step.requires_approval?
  │    yes → HumanApprovalGate (Workflow 5) → wait signal
  │    no  → continue
  │
▶ Step: Execute
  │  parallel tool calls (goroutines) if step has multiple actions
  │    goroutine-A: tool_A.Call(args)
  │    goroutine-B: tool_B.Call(args)   (optional)
  │  timeout: 2s per tool call
  │  failure → retry ×2 with backoff, then mark step_failed
  │
▶ Step: Verify
  │  run verify_condition: metric check or API assertion
  │  pass → continue
  │  fail → emit StepVerificationFailed, escalate or retry
  │
▶ Step: Checkpoint
  │  [PG] INSERT runbook_steps (incident_id, step_id, status, result, ts)
  │  ⟹ stream.{tenant}.{session_id}  (step result token)
  │
  └─ more steps? → trigger next RunbookStepWorkflow : done
```

## Workflow 5 — Human Approval Gate

**Trigger:** Hatchet step suspends and emits `approval_required`
**Owner:** `paladin-ws` (signal routing), browser UI
**NATS subjects:** `approvals.{tenant}.{incident_id}.{gate_id}`, `signals.{tenant}.{incident_id}.{gate_id}`
**Hatchet workflow:** embedded in parent (step suspends)
**Idempotency:** gate_id = UUIDv7 per approval request; duplicate signals are no-ops
**Latency budget:** no hard budget (human-gated); auto-reject after 30 min (configurable)

```
Hatchet step suspends
  │
  ⟹ NATS publish approvals.{tenant}.{incident_id}.{gate_id}
       payload: {context, action_summary, risk_level, expires_at}
  │
  paladin-ws (NATS consumer)
  │  WebSocket push → browser
  │    {type:"approval_required", gate_id, context, actions}
  │
  Browser UI
  │  user reviews context
  │  clicks Approve or Reject
  │    → POST /v1/approvals/{gate_id}  {decision: "approved"|"rejected", reason}
  │
  paladin-ws
  │  validate session + RBAC
  │  ⟹ NATS publish signals.{tenant}.{incident_id}.{gate_id}
  │       payload: {decision, user_id, reason, ts}
  │
  paladin-orchestrator (NATS consumer on signals.>)
  │  SendSignal → Hatchet: workflow resumes with ApprovalResult
  │
  Hatchet step resumes
  │  decision=approved → continue next step
  │  decision=rejected → mark workflow status=rejected, notify
```

## Workflow 6 — Alert Resolution

**Trigger:** AlertEvent with `endsAt` set (resolved state from source)
**Owner:** `paladin-orchestrator`
**NATS subjects:** `alerts.{tenant}.{severity}.{source}`
**Hatchet workflow:** none
**Idempotency:** resolution is idempotent; duplicate resolved events update `resolved_at` only
**Latency budget:** <1s to detect resolution; 5-min grace window before close

```
NATS pull: alerts.{tenant}.{severity}.{source}
  │  endsAt ≠ zero → resolution event
  │
  ├─ Lookup open incident by fingerprint
  │    not found → log, ack, done
  │
  ├─ Start grace window timer (5 min)
  │    purpose: absorb flapping alerts (re-fires reset timer)
  │    re-fire during grace → cancel timer, incident stays open
  │
  └─ Timer fires (no re-fire in 5 min)
       │
       ├─ UPDATE incidents SET status='closed', resolved_at=now()  [PG]
       │
       ├─ Write episode to memory
       │    INSERT episodes (incident_id, summary, outcome, duration)
       │    [PG] checkpoint
       │
       ⟹ NATS publish stream.{tenant}.{session_id}
            {type:"incident_closed", incident_id, resolved_at}
```

## Workflow 7 — Alert Escalation (P3 → P1)

**Trigger:** severity update from external source OR agent confidence escalation signal
**Owner:** `paladin-orchestrator`
**NATS subjects:** `alerts.{tenant}.{severity}.{source}`, `triage.{tenant}.{incident_id}`
**Hatchet workflow:** `IncidentWorkflow` (triggered fresh on escalation)
**Idempotency:** re-fingerprint preserves `incident_id`; Hatchet `ExternalID` prevents duplicate workflow
**Latency budget:** escalation detection <500ms; re-triage triggered <1s

```
Severity update received
  │  source: webhook update (Datadog severity change) OR
  │           TriageAgent emits escalation_signal (low confidence, spreading impact)
  │
  ├─ Re-fingerprint check
  │    fingerprint unchanged (same alert, new severity)
  │    UPDATE incidents SET severity='P1' [PG]
  │
  ├─ Cancel P3 triage consumer ack (if in-flight)
  │    NATS: publish to DLQ or nak with delay
  │
  ├─ Update incident record
  │    severity=P1, escalated_at=now(), escalation_reason=...
  │    [PG] checkpoint
  │
  ⟹ NATS publish triage.{tenant}.{incident_id}
       headers: X-Escalation=true, X-Original-Severity=P3
       payload: IncidentContext with escalation_context field
  │
  paladin-orchestrator picks up triage message
  │  severity=P1 → trigger IncidentWorkflow (Hatchet)
  │  ExternalID = incident_id → deduplicates if somehow triggered twice
```

## Workflow 8 — Memory Consolidation (Weekly CronJob)

**Trigger:** Kubernetes CronJob, weekly Sunday 02:00 UTC
**Owner:** `paladin-consolidator` job (or orchestrator cron handler)
**NATS subjects:** `memory.consolidation.{tenant}` (optional trigger override)
**Hatchet workflow:** none (simple batch job)
**Idempotency:** consolidation_run keyed on `tenant:week_start`; skip if already done
**Latency budget:** no real-time constraint; completes within 30 min per tenant

```
CronJob fires (or NATS trigger for manual run)
  │
  ├─ Fetch unprocessed episodes
  │    SELECT * FROM episodes WHERE consolidated=false AND tenant=?
  │    AND created_at < now() - interval '7 days'
  │
  ├─ Cluster episodes
  │    group by: service, root_cause_category, label similarity
  │    algorithm: k-means on TF-IDF embedding (local, no LLM)
  │
  ├─ Summarize each cluster (LLM call per cluster)
  │    input: episode summaries in cluster
  │    output: {pattern, frequency, recommended_runbook_improvement}
  │    cap: max 20 LLM calls per run
  │
  ├─ Write to Qdrant semantic store
  │    upsert ConsolidatedPattern{tenant, week, cluster_id, embedding, summary}
  │    [QDR] upsert
  │
  ├─ Mark episodes consolidated
  │    UPDATE episodes SET consolidated=true WHERE id IN (...)  [PG]
  │
  └─ Write consolidation_run record
       INSERT consolidation_runs (tenant, week_start, clusters, ts)  [PG]
```

## Workflow 9 — Integration Activation

**Trigger:** `paladin integrations enable <name>` CLI command
**Owner:** CLI → `paladin-api` → `paladin-agent`
**NATS subjects:** `integrations.{tenant}.activated`
**Hatchet workflow:** none
**Idempotency:** integration record keyed on `tenant:integration_name`; enable is idempotent
**Latency budget:** CLI returns <2s; agent hot-reload <5s; doctor check <10s

```
$ paladin integrations enable datadog --api-key=... --app-key=...
  │
  CLI
  │  POST /v1/integrations/{name}  {credentials: {...}}
  │
  paladin-api
  │  ├─ Validate credentials (dry-run API call to provider)
  │  │    fail → 422 {error: "credential_validation_failed"}
  │  │
  │  ├─ Store secrets
  │  │    [VLT] Vault KV: secret/tenants/{tenant}/integrations/{name}
  │  │
  │  ├─ UPDATE integrations SET status='active', validated_at=now()  [PG]
  │  │
  │  ⟹ NATS publish integrations.{tenant}.activated
  │       payload: {name, config_hash}
  │
  paladin-agent (NATS consumer)
  │  ├─ Hot-reload integration config (no restart)
  │  │    load new integration adapter, inject credentials from Vault
  │  │
  │  ├─ Deploy mcp-{name} sidecar (if MCP-based integration)
  │  │    kubectl apply -f mcp-{name}-deployment.yaml (or local process)
  │  │
  │  ├─ Register tools in ToolHub
  │  │    ToolHub.Register({name, tools[], schema})
  │  │
  │  └─ Doctor check
  │       run integration.Doctor() → health check all registered tools
  │       result: ⟹ stream.{tenant}.system  {type:"integration_ready", name, tools[]}
  │
  CLI polls /v1/integrations/{name}/status until status='active'
  └─ print: ✓ datadog integration active — 8 tools registered
```

## Workflow 10 — Eval Replay

**Trigger:** Kubernetes CronJob nightly 03:00 UTC; also manual `paladin eval run --suite=<id>`
**Owner:** `paladin-eval` job
**NATS subjects:** `evals.replay.{suite_id}`
**Hatchet workflow:** none (sequential replay harness)
**Idempotency:** eval_run keyed on `suite_id:date`; re-run with `--force` overrides
**Latency budget:** no real-time constraint; suite completes within 2h

```
CronJob fires (or manual trigger)
  │
  paladin-eval
  │
  ├─ Fetch eval suite
  │    SELECT * FROM eval_suites WHERE id=? AND active=true
  │    suite = list of prod incidents (anonymized)
  │
  ├─ Anonymize (if not already done)
  │    strip PII: IP, hostnames → synthetic, customer names → tenant_X
  │    hash: fingerprints, labels with HMAC (eval-specific key)
  │    store anonymized incidents in eval_incidents table  [PG]
  │
  ├─ For each eval incident (sequential to avoid resource contention)
  │    │
  │    ├─ Replay through agent stack
  │    │    publish to triage.eval.{incident_id}  (eval tenant)
  │    │    run TriageAgent or IncidentWorkflow in eval mode
  │    │    capture: tool calls, LLM hops, latency, final output
  │    │
  │    ├─ Score output
  │    │    LLM-as-judge: compare agent output vs ground truth
  │    │    metrics: accuracy, latency, tool_efficiency, confidence_calibration
  │    │
  │    ├─ Write to ClickHouse
  │    │    INSERT eval_results (suite_id, incident_id, scores, latency, model, ts)
  │    │
  │    └─ Push to Braintrust
  │         braintrust.log(experiment=suite_id, input=incident, output=agent_output, scores)
  │
  └─ Write eval_run summary
       INSERT eval_runs (suite_id, date, pass_rate, avg_latency, regression_flags)  [PG]
       regression_flag: true if accuracy < previous_run - 0.05
       ⟹ NATS publish evals.replay.{suite_id}  {status:'complete', pass_rate, regressions[]}
```

## Error Handling & DLQ

```
All NATS consumers:
  max redelivery: 3
  nack backoff:   [1s, 5s, 30s]
  after 3 fails: ⟹ dlq.{tenant}.{original_subject}

DLQ consumer (paladin-orchestrator):
  alert on DLQ depth > 10
  manual replay: paladin dlq replay --subject=...
  auto-replay: none (require human review for DLQ)

Hatchet step failures:
  max retries per step: 2
  step timeout: configurable, default 60s
  workflow timeout: P3=30s, P1=10min (excluding human approval wait)
  on failure: UPDATE incidents SET status='error' [PG], notify on-call
```

## Checkpoint Strategy

| Event | Store | Key |
|-------|-------|-----|
| Incident created | PG `incidents` | `id = UUIDv7` |
| RCA phase complete | PG `rca_results` | `incident_id + phase` |
| Runbook step done | PG `runbook_steps` | `incident_id + step_id` |
| Approval decision | PG `approval_decisions` | `gate_id` |
| Incident closed | PG `incidents.resolved_at` | `id` |
| Episode written | PG `episodes` | `incident_id` |
| Consolidation done | PG `consolidation_runs` | `tenant + week_start` |
| Eval result | ClickHouse `eval_results` | `suite_id + incident_id + date` |
