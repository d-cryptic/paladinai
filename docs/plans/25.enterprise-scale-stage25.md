## 1. Tier Architecture (Bridge & Silo)

Bridge and Silo extend the day-1 Pool architecture from Stage 8. The Pool tier remains the default; tenants are promoted to Bridge or Silo on demand.

| Dimension | Bridge | Silo |
|---|---|---|
| K8s | Dedicated namespace | Dedicated cluster |
| PostgreSQL | Shared cluster, schema-per-tenant | Dedicated cluster |
| Qdrant | Per-tenant collection | Dedicated cluster |
| Valkey | Shared, key-prefixed | Dedicated instance |
| NATS | Shared server, per-tenant account | Dedicated NATS cluster |
| Vault | Per-tenant namespace | Per-tenant namespace (dedicated Vault HA) |
| FalkorDB | Shared instance, graph-per-tenant | Dedicated instance |
| vLLM | Shared inference pods, no prefix cache | Optional dedicated pods in customer VPC |
| gVisor | No | Yes (runsc runtime) |
| Provisioning | Helm + schema migration | Crossplane composition |
| Cost | $$ | $$$$ |

**Bridge provisioning flow:**

```
paladin-control
  1. Generate tenant_id
  2. Vault namespace + transit key (same as pool)
  3. Helm install paladin-stack --namespace paladin-{tenant_id}
       - sets --set tenantId={tenant_id} --set tier=bridge
  4. Apply NetworkPolicy: allow only intra-namespace + paladin-system
  5. Apply ResourceQuota for namespace
  6. Call PG: CREATE SCHEMA {tenant_id}; run schema migrations

  8. Call NATS: create account, issue credentials
  9. Emit tenant.provisioned
```

## 2. Bridge Tier: Schema-per-Tenant Migration Strategy

Each Bridge tenant gets its own PG schema. Migrations run per-schema using a namespaced migration table.

```go
// pkg/db/bridge_migrate.go

func MigrateBridgeSchema(ctx context.Context, pool *pgxpool.Pool, tenantID string) error {
    schema := fmt.Sprintf("tenant_%s", strings.ReplaceAll(tenantID, "-", "_"))

    conn, err := pool.Acquire(ctx)
    if err != nil {
        return err
    }
    defer conn.Release()

    // Create schema if not exists
    if _, err := conn.Exec(ctx,
        fmt.Sprintf("CREATE SCHEMA IF NOT EXISTS %q", schema)); err != nil {
        return fmt.Errorf("bridge: create schema: %w", err)
    }

    // Set search_path to tenant schema for migration runner
    if _, err := conn.Exec(ctx,
        fmt.Sprintf("SET search_path TO %q, public", schema)); err != nil {
        return fmt.Errorf("bridge: set search_path: %w", err)
    }

    // Run goose migrations targeting this schema
    return goose.Up(conn.Conn().Config().ConnString(), "migrations/bridge")
}
```

Migration files live in `migrations/bridge/`. On Bridge tier, RLS still applies as a defense-in-depth measure even though schema isolation provides the primary boundary.

## 3. Qdrant At-Scale: Bridge Per-Collection & Silo Dedicated

### 3.1 Bridge Tier: Per-Collection

```go
func collectionName(tenantID, dataType string) string {
    // dataType: "runbooks" | "episodic_memory" | "procedural_memory"
    return fmt.Sprintf("%s_%s", dataType, strings.ReplaceAll(tenantID, "-", "_"))
}
```

No payload filter needed — collection boundary provides isolation. paladin-memory still validates that the `tenantID` from context matches the collection it is querying.

### 3.2 Silo Tier: Dedicated Cluster

paladin-memory receives the Qdrant endpoint from its environment (injected by Crossplane into the Silo cluster's ConfigMap). The service code is identical — isolation is at infrastructure level.

### 3.3 ACORN Sub-Graph Optimization for >100 Tenants

When the shared Pool collection grows beyond ~100 tenants and millions of vectors, payload-filtered queries can degrade if the HNSW graph is not aware of the tenant boundary. Qdrant 1.16's ACORN (Approximate Closest to a Node) algorithm builds per-payload sub-graphs within the shared HNSW index.

```go
client.CreateCollection(ctx, &qdrant.CreateCollection{
    CollectionName: "runbooks",
    VectorsConfig: &qdrant.VectorsConfig{
        Config: &qdrant.VectorsConfig_Params{
            Params: &qdrant.VectorParams{
                Size:     1536,
                Distance: qdrant.Distance_Cosine,
                HnswConfig: &qdrant.HnswConfigDiff{
                    PayloadM: wrapperspb.UInt64Value(16), // ACORN: indexed links per payload group
                },
            },
        },
    },
})

// Create payload index on tenant_id — REQUIRED for ACORN sub-graph
client.CreateFieldIndex(ctx, &qdrant.CreateFieldIndexCollection{
    CollectionName: "runbooks",
    FieldName:      "tenant_id",
    FieldType:      qdrant.FieldType_FieldTypeKeyword.Enum(),
})
```

At day-1 scale (5-10 tenants) this is unnecessary. Enable when shared-collection query latency p95 > 100ms.

## 4. Tenant Promotion Paths (Pool → Bridge → Silo)

Migration is zero-downtime using a dual-write window.

### 4.1 Pool → Bridge (estimated: 30 min for 100k vectors, 10M rows)

```
Step 1: Provision Bridge namespace and Qdrant collections
  paladin tenant prepare-bridge --tenant acme-corp
  - Helm install paladin-stack in paladin-acme namespace
  - CREATE SCHEMA tenant_019600ab in shared PG
  - CREATE COLLECTION runbooks_019600ab, episodic_memory_019600ab in Qdrant

Step 2: Enable dual-write
  - paladin-control sets tenant.migration_state = 'dual-write'
  - paladin-memory: writes to pool collection AND bridge collection
  - paladin-auth: reads/writes to pool PG schema (public)

Step 3: Backfill data
  - pg_dump --schema=public --where="tenant_id='019600ab'" | pg_restore --schema=tenant_019600ab
  - Qdrant scroll + re-upsert with collection rename
  - Estimated throughput: ~50k vectors/min

Step 4: Verify
  - Row count match: SELECT count(*) from public.incidents WHERE tenant_id='...'
    vs SELECT count(*) from tenant_019600ab.incidents
  - Qdrant: count_points(runbooks) filtered vs count_points(runbooks_019600ab)

Step 5: Cut over (< 1 second downtime)
  - UPDATE tenants SET tier='bridge', migration_state='complete' WHERE id='...'
  - paladin-auth re-reads tenant record on next JWT validation
  - All subsequent queries route to Bridge schema + collections

Step 6: Cleanup (async, 48h delay for rollback window)
  - DELETE FROM public.incidents WHERE tenant_id='...'
  - Qdrant: delete points with filter tenant_id='...' from shared collection
```

### 4.2 Bridge → Silo (estimated: 1–2h)

```
Step 1: Crossplane provisions Silo cluster (~15–20 min)
Step 2: Dual-write to Silo Qdrant via paladin-memory stream
Step 3: PG logical replication slot from shared PG to Silo PG
Step 4: Verify replication lag < 100ms
Step 5: Maintenance window (< 5 min): drain Bridge, switch DNS to Silo cluster
Step 6: Verify, then DROP SCHEMA on shared PG after 48h
```

## 5. Per-Tenant NATS Accounts (Bridge & Silo)

For day-1 (Stage 8), subject-based isolation is sufficient. At scale, full NATS account isolation provides hard boundaries: a compromised credential for tenant A cannot see tenant B's messages.

```
NATS Server topology:

  System Account (paladin-ingest, paladin-control)
  │  └─ Can publish to any subject (privileged)
  │  └─ Can subscribe to $SYS.> for server events
  │
  ├─ Account: tenant-019600ab (acme)
  │    Permissions:
  │      publish:   alerts.019600ab.>
  │      subscribe: alerts.019600ab.>
  │                 incidents.019600ab.>
  │                 runbooks.019600ab.>
  │
  ├─ Account: tenant-019600cd (globex)
  │    Permissions:
  │      publish:   alerts.019600cd.>
  │      subscribe: alerts.019600cd.>
  │
  └─ (no cross-account visibility without explicit export/import)
```

**Dynamic tenant account provisioning (Go):**

```go
// pkg/nats/tenant_accounts.go

import (
    "github.com/nats-io/nkeys"
    "github.com/nats-io/jwt/v2"
)

func CreateTenantAccount(tenantID string, operatorSeed []byte) (accountJWT string, credFile string, err error) {
    // 1. Create account keypair
    akp, _ := nkeys.CreateAccount()
    apub, _ := akp.PublicKey()

    // 2. Sign account JWT with operator key
    ac := jwt.NewAccountClaims(apub)
    ac.Name = fmt.Sprintf("tenant-%s", tenantID)
    ac.Exports = jwt.Exports{}
    ac.Limits.Payload = 1024 * 1024  // 1MB max message size

    opKP, _ := nkeys.FromSeed(operatorSeed)
    accountJWT, _ = ac.Encode(opKP)

    // 3. Create user keypair (for service credential file)
    ukp, _ := nkeys.CreateUser()
    upub, _ := ukp.PublicKey()

    uc := jwt.NewUserClaims(upub)
    uc.Pub.Allow = jwt.StringList{
        fmt.Sprintf("alerts.%s.>", tenantID),
        fmt.Sprintf("incidents.%s.>", tenantID),
    }
    uc.Sub.Allow = jwt.StringList{
        fmt.Sprintf("alerts.%s.>", tenantID),
        fmt.Sprintf("incidents.%s.>", tenantID),
        fmt.Sprintf("runbooks.%s.>", tenantID),
    }

    userJWT, _ := uc.Encode(akp)
    userSeed, _ := ukp.Seed()

    credFile = fmt.Sprintf("-----BEGIN NATS USER JWT-----\n%s\n-----END NATS USER JWT-----\n"+
        "-----BEGIN USER NKEY SEED-----\n%s\n-----END USER NKEY SEED-----", userJWT, userSeed)

    return accountJWT, credFile, nil
}
```

Credentials stored in Vault at `paladin/tenants/{tenant_id}/nats-creds`. Services retrieve them at startup.

## 6. Crypto-Shredding for GDPR Right-to-Erasure

Crypto-shredding via Vault transit keys is the primary mechanism: deleting the tenant's transit key renders all encrypted data permanently unreadable without touching individual rows. Critical for GDPR/SOC2 erasure SLAs.

```
Deletion sequence (triggered by paladin-control):

1. Set tenant.state = 'deleting'
2. Suspend tenant
3. After data retention period (default 30 days, configurable to 0 for GDPR):

   a. Vault: DELETE paladin/tenants/{tenant_id}/transit/keys/tenant-{tenant_id}
      → All encrypted integration credentials become permanently unreadable (crypto-shred)

   b. PG (Bridge): DROP SCHEMA tenant_{id} CASCADE
      PG (Silo): Crossplane XR deletion → DB instance termination

   c. Qdrant (Bridge): delete_collection runbooks_{id}, episodic_memory_{id}
      Qdrant (Silo): Crossplane XR deletion → cluster termination

   d. NATS: revoke account JWT, purge stream
   e. Vault: delete tenant namespace (paladin/tenants/{id}/)
   f. Emit audit event: tenant.deleted with deletion_reason, timestamp

4. Set tenant.state = 'deleted' (record retained for billing history)
```

**GDPR right-to-erasure timeline:** paladin-control supports `--erasure-deadline 0` to skip the retention period and immediately execute deletion sequence. SOC2 typically requires 30-day SLA; GDPR allows up to 30 days but customers commonly request immediate.

## 7. KV Cache Side-Channel Mitigation

**Threat:** vLLM's KV-cache prefix sharing allows a tenant to infer another tenant's prompt content by measuring Time-to-First-Token (TTFT). If two tenants send prompts with the same prefix, the second gets a cache hit — shorter TTFT — leaking that the prefix was recently used.

**Mitigations by tier:**

| Tier | Mitigation |
|---|---|
| Pool | Prefix caching **disabled** (`--no-enable-prefix-caching` in vLLM). All tenants share inference pods. TTFT jitter: add uniform random delay 0–50ms to all completions before streaming. |
| Bridge | Prefix caching **disabled**. Inference pods shared across Bridge tenants. Same jitter. |
| Silo | Prefix caching **enabled** (performance benefit, no cross-tenant risk). Dedicated inference pods per Silo tenant (or customer VPC). No jitter needed. |

**Implementation (paladin-gateway, Rust):**

```rust
// Add jitter to TTFT for shared tiers before streaming first token
if tenant_tier != TenantTier::Silo {
    let jitter_ms = rand::thread_rng().gen_range(0..=50);
    tokio::time::sleep(Duration::from_millis(jitter_ms)).await;
}
// then begin streaming
```

## 8. Multi-Region Per-Tenant Routing

### 8.1 NATS Topology Decision

**Decision: Per-region NATS clusters, not global NATS with geo-routing.**

| Option | Pro | Con |
|---|---|---|
| Global NATS + geo-routing | Single control plane, simpler ops | GDPR: EU data crosses regions in routing metadata; latency for EU tenants to US cluster |
| Per-region clusters | Hard data boundary (EU data never leaves EU cluster), lower latency | Multiple clusters to operate, no native cross-region pub/sub |

Per-region clusters win because:
1. GDPR compliance is non-negotiable for EU tenants — a global cluster with geo-routing still routes message metadata through all nodes
2. PaladinAI's alert-response latency is more sensitive to intra-region latency than cross-region coordination
3. The Silo tier already provisions dedicated NATS; per-region for Pool/Bridge is a natural extension

Cross-region workflows (e.g., global incident aggregation for enterprise) use paladin-control as a relay — it publishes to the target region's NATS cluster directly, with explicit data residency checks before doing so.

### 8.2 Regional PostgreSQL Primaries

Each region has its own PG primary with read replicas. Tenant `data_residency.region` determines the primary. Cross-region failover requires explicit operator action — automatic failover would violate residency for EU tenants.

## 9. Data Residency Enforcement

### 9.1 EU Tenants

Tenants can specify `data_residency: eu` in `paladin.yaml`. This affects:

- PG cluster: GKE EU region (europe-west1 or eu-central1)
- Qdrant: EU-region deployment
- NATS: EU cluster
- LLM inference: EU-hosted providers only (Mistral EU, AWS Bedrock eu-central-1)
- Langfuse: self-hosted in EU (GDPR requires no data leaving EU for tracing/observability)
- Vault: EU Vault cluster

### 9.2 `paladin.yaml` Data Residency

```yaml
tenant:
  name: acme-corp
  tier: silo

  data_residency:
    region: eu-west1              # primary region
    allowed_regions:
      - eu-west1
      - eu-central1
    disallowed_regions:
      - us-*
      - ap-*

  # vLLM in customer VPC (Silo only)
  vllm:
    mode: customer-vpc
    vpc_id: vpc-0abc123
    subnet_ids:
      - subnet-0def456
    model: mistral-7b-instruct

  # Langfuse self-hosted (GDPR)
  observability:
    langfuse:
      mode: self-hosted
      endpoint: https://langfuse.internal.acme-corp.com
      public_key: ${LANGFUSE_PUBLIC_KEY}
      secret_key: ${LANGFUSE_SECRET_KEY}

  llm_providers:
    - mistral-eu                  # only EU-hosted providers allowed
```

paladin-control validates `data_residency` constraints before provisioning any infrastructure. It rejects Crossplane XR creation that would place resources in a disallowed region.

## 10. Dynamic PG Credentials via Vault DB Engine (Silo Only)

For Silo tier, Vault's database secrets engine issues short-lived PG credentials per service call. This replaces static DB passwords.

```hcl
# Vault policy for paladin-agent in Silo
path "paladin/tenants/TENANT_ID/database/creds/paladin-agent-role" {
  capabilities = ["read"]
}
```

```go
// Retrieve dynamic PG creds at service startup (refresh before expiry)
func (v *VaultClient) GetDatabaseCredentials(ctx context.Context) (user, password string, err error) {
    path := fmt.Sprintf("paladin/tenants/%s/database/creds/paladin-agent-role", v.tenantID)
    secret, err := v.client.Logical().ReadWithContext(ctx, path)
    if err != nil {
        return "", "", fmt.Errorf("vault: db creds: %w", err)
    }
    return secret.Data["username"].(string), secret.Data["password"].(string), nil
}
```

**Secret rotation flow:**

```
1. Vault lease expires (TTL: 1h for DB creds, 24h for NATS creds)
2. paladin-agent's Vault agent sidecar detects expiry via renew watcher
3. Vault agent requests new credential from engine
4. New credential written to in-memory secret store (no disk)
5. paladin-agent receives signal via inotify on the in-memory tmpfs mount
6. pgxpool.Reset() called — connections renegotiate with new DB user
7. Old Vault lease revoked
```

## 13. Tenant Suspension with Grace Period for Active P1s

When a tenant is suspended (non-payment, policy violation), in-flight P1 incidents must be allowed to complete to avoid cutting off active emergency response.

```
Suspension flow:
  1. Set tenant.state = 'suspended'
  2. paladin-edge: returns 402 for new API calls
  3. paladin-ingest: drops new alerts (logged to dead-letter queue)
  4. paladin-agent: continues processing in-flight P1 incidents until completion
     - P2/P3 incidents are paused
     - Configurable grace period: default 4h for P1 completion
  5. After grace period: KEDA scales paladin-agent to 0 for tenant's subject prefix
  6. NATS account: connection limit 0
  7. Data retained, no deletion
```

## 14. OPA Bundle Server for Policy Distribution at Scale

At >50 tenants, mounting OPA policies from ConfigMaps becomes operationally painful. Deploy an OPA bundle server (HTTP endpoint serving signed policy bundles).

```
Architecture:
  paladin-policy (Go service)
    ├─ Builds tenant-aware bundles from policy/*.rego
    ├─ Signs bundles with operator key
    └─ Serves at /bundles/{tenant_id}/policy.tar.gz

  OPA sidecar (one per paladin-edge pod)
    config:
      services:
        paladin:
          url: http://paladin-policy:8080
      bundles:
        paladin:
          service: paladin
          resource: bundles/{tenant_id}/policy.tar.gz
          polling:
            min_delay_seconds: 60
            max_delay_seconds: 120
          signing:
            keyid: paladin-operator
```

Policy updates propagate to all OPA instances within 2 minutes. Per-tenant policy customization (e.g., custom approval workflows) becomes feasible.

## Phase 4 — Compliance & Regulated Industries

### SOC2 Type II Audit Trail Requirements

SOC2 Type II requires evidence of continuous control effectiveness over a 6-12 month observation window:

- **Audit log retention:** All `audit_logs` rows retained 7 years (move to S3 Glacier after 1 year)
- **Append-only proof:** WORM (write-once-read-many) storage for audit log archives, S3 Object Lock with compliance mode
- **Access reviews:** Quarterly review of role assignments, automated report generation from `audit_logs`
- **Change management:** Every production change linked to a ticket; CI/CD enforces ticket reference in commit message
- **Vendor management:** SOC2 reports collected annually for all subprocessors (NATS, Qdrant, Vault, cloud providers)
- **Incident response runbooks:** Documented in paladin-runbooks, tested quarterly

### HIPAA

For healthcare customers handling PHI:

- **BAA (Business Associate Agreement):** Required with the customer; subprocessors (cloud, vector DB) must also sign BAAs
- **Encryption at rest:** AES-256 for all storage (PG TDE, Qdrant, Valkey AOF). Already default in Silo
- **Encryption in transit:** TLS 1.3 minimum, mTLS for service-to-service (Linkerd in Silo)
- **PHI segregation:** Tenant data residency must guarantee PHI never leaves customer-designated region
- **Audit logs:** Every access to PHI logged with actor, timestamp, action, resource. Retained 6 years (HIPAA minimum)
- **Breach notification:** Automated detection + 60-day notification SLA (paladin-control monitors audit logs for anomalous access patterns)
- **Workforce training:** Internal-only — relevant to Paladin staff with prod access

### FedRAMP-Grade Isolation

For US Federal customers (FedRAMP Moderate or High):

- **GovCloud regions only:** AWS GovCloud (us-gov-west-1), Azure Government — Crossplane composition uses `region: us-gov-west-1` and provider variant
- **FIPS-validated cryptography:** Vault Enterprise FIPS 140-2 build, BoringCrypto Go runtime for paladin-* services, OpenSSL FIPS module
- **US Persons access controls:** RBAC restricts production access to US citizens only, verified via personnel records
- **Continuous monitoring (ConMon):** Monthly vulnerability scans, automated POA&M generation, real-time SIEM integration (Splunk Federal, Elastic Federal)
- **FedRAMP boundary:** Silo tier is the only certifiable tier — Pool/Bridge have shared infrastructure that crosses FedRAMP boundaries
- **STIG-hardened images:** All container base images derived from CIS/STIG-hardened distros (Chainguard FIPS, Iron Bank)
- **gVisor enforced:** runsc runtime is mandatory in FedRAMP Silo, not optional

### Dedicated FIPS-Validated Crypto

For customers requiring FIPS 140-2 / 140-3 validation end-to-end:

- **Vault Enterprise FIPS:** FIPS 140-2 Level 1 validated; Level 2 with HSM (CloudHSM, KMS HSM)
- **TLS termination:** FIPS-validated load balancers (AWS NLB with FIPS endpoints, GCP HTTP(S) with FIPS-mode)
- **Go runtime:** `GOEXPERIMENT=boringcrypto` builds for all paladin-* services. Verified via `go tool nm | grep boring`
- **Rust crypto:** `aws-lc-rs` (FIPS-validated) for paladin-gateway instead of stock `ring`
- **Disk encryption:** Cloud-provider FIPS-validated KMS keys (AWS KMS FIPS endpoints, GCP Cloud KMS HSM-backed)
- **Crypto-shredding compatibility:** Transit keys must be FIPS-mode AES-256-GCM; key rotation policies enforced quarterly
- **Validation evidence:** Quarterly attestation reports from each FIPS-validated module, mapped to SSP (System Security Plan) controls
