# Stage 9 — Three-Tier Cache, Valkey, Semantic Cache, Tool Result Cache

**Date:** 2026-05-10
**Status:** Architecture decisions locked
**Scope:** All caching layers for LLM responses, semantic deduplication, tool results, and Anthropic prompt caching integration

---

## Overview

Caching is not optional for PaladinAI v2 — it is a core correctness and cost constraint. An incident triage session can involve dozens of repeated tool calls and near-identical LLM queries as the agent iterates hypotheses. Without caching, costs are unbounded and latency is unacceptable.

Three distinct caching tiers address different parts of the stack:

- **L1 — Exact LLM Cache**: identical requests return cached responses instantly
- **L2 — Semantic LLM Cache**: near-identical triage queries (different phrasing, same incident signature) return cached responses via vector similarity
- **L3 — Tool Result Cache**: MCP tool call results cached by tool + args + tenant

Additionally, Anthropic prompt caching operates at the provider level (separate from Valkey) and is always active for system prompt and tool catalog caching.

**Working memory** (session state stored in Valkey under `wm:{tenant_id}:{session_id}:{key}`) is covered in Stage 5 and is not repeated here.

## 1. Three-Tier Cache Architecture

```
Incoming LLM request
        |
        v
+---------------------------------------+
|         L1 — Exact LLM Cache         |
|  Key: sha256(canonical_json(request)) |
|  TTL: 30min – 4h (query-type based)  |
+---------------------------------------+
        |                    |
      HIT                   MISS
        |                    |
        v                    v
  Return cached      +-----------------------------+
    response         |  L2 — Semantic LLM Cache    |
                     |  valkey-search HNSW cosine  |
                     |  threshold: >= 0.92          |
                     |  TTL: 6h                    |
                     +-----------------------------+
                             |              |
                           HIT            MISS
                             |              |
                             v              v
                     Return L1 key's  Proceed to
                     cached response  LLM call
                             |              |
                             |              v
                             |   +------------------+
                             |   |  Anthropic API   |
                             |   |  (prompt cache   |
                             |   |  always active)  |
                             |   +------------------+
                             |              |
                             |    Write to L1 + L2
                             |    Return response
                             v
                       (Already done)


Tool call (MCP) in agent turn:
        |
        v
+----------------------------------------+
|          L3 — Tool Result Cache        |
|  Key: tool:l3:{tenant_id}:{sha256(...)}|
|  TTL: 15s – 120s (tool-type based)    |
+----------------------------------------+
        |                    |
      HIT                   MISS
        |                    |
        v                    v
  Return cached      Call MCP server
    tool result      Write to L3
                     Return result

Parallel tool calls: some L3 hit, some miss.
Serve L3 hits immediately; fire MCP calls only for misses.
Merge results before returning to agent.
```

Cache check order is always L1 → L2 → LLM. L3 is checked independently per tool call, not per LLM request.

## 2. L1 — Exact LLM Response Cache

### Key Structure

```
llm:l1:{sha256(canonical_json(model, messages, tools, params))}
```

Example:

```
llm:l1:a3f8c2d1e9b047f6...
```

### Canonical JSON Construction

Canonical JSON eliminates superficial differences (whitespace, key ordering) before hashing. The following rules apply:

- Keys sorted alphabetically at every nesting level
- No whitespace (no spaces, no newlines)
- Strings UTF-8 encoded
- Floats serialized with full precision (no rounding)
- Arrays preserve order (order matters for messages)

Go implementation sketch:

```go
// CacheKey computes the L1 cache key for an LLM request.
func CacheKey(req LLMRequest) (string, error) {
    canonical := map[string]any{
        "messages": req.Messages,  // preserve array order
        "model":    req.Model,
        "params":   req.Params,
        "tools":    sortedToolList(req.Tools), // sort by tool name for determinism
    }
    buf, err := json.Marshal(canonical)
    if err != nil {
        return "", fmt.Errorf("canonical json: %w", err)
    }
    // Ensure key ordering by re-marshaling with sorted map
    var ordered orderedMap
    if err := json.Unmarshal(buf, &ordered); err != nil {
        return "", fmt.Errorf("reorder json: %w", err)
    }
    sorted, _ := json.Marshal(ordered)
    sum := sha256.Sum256(sorted)
    return "llm:l1:" + hex.EncodeToString(sum[:]), nil
}
```

The `orderedMap` type implements `json.Marshaler` with sorted keys. Tool list is sorted by tool name since tool ordering in the catalog is not semantically significant.

### TTL Strategy by Query Type

| Query Type | TTL | Rationale |
|---|---|---|
| Alert classification | 30 min | Same alert type recurs frequently during incidents; short TTL because alert context evolves |
| Runbook lookup | 4 h | Runbooks change rarely; high reuse during incidents for the same playbook |
| RCA synthesis | 1 h | Context-dependent; RCA is incident-specific, stale RCA is harmful |
| General reasoning | 1 h | Default for uncategorized queries |

Query type is determined by the system prompt prefix tag injected by paladin-gateway before the Anthropic API call:

```
[CACHE:alert_classification] ...
[CACHE:runbook_lookup] ...
[CACHE:rca_synthesis] ...
```

paladin-gateway parses this tag to set TTL at write time and strips it from the request before hashing (so the tag itself does not affect the cache key).

### Cache Invalidation

Time-based TTL is the primary invalidation mechanism. Explicit invalidation is applied only for known content changes:

- **Runbook updated**: invalidate all L1 keys tagged with that runbook ID. paladin-gateway maintains a secondary index: `llm:l1:runbook:{runbook_id}` → set of L1 keys. On runbook update, the index set is read and each L1 key is deleted. The index entry is also deleted.
- **Model config changed**: bump a `cache_version` field in canonical JSON. Old keys become unreachable (they hash to a different key). Stale keys expire via TTL naturally.

### What Gets Cached vs. What Does Not

Cached:
- Full LLM response including text, tool call decisions, and tool call arguments
- The response is cached after full completion (not mid-stream)

Not cached:
- Streaming responses — the cache write happens after the stream completes and the response is assembled. During streaming, the L1 miss path proceeds; on completion, the assembled response is written.
- Requests with `Cache-Control: no-cache` (forwarded from client via paladin-gateway)

## 3. L2 — Semantic LLM Cache

### Purpose

Alert descriptions during an incident are rarely byte-for-byte identical even when they describe the same condition. "High memory usage on pod redis-main-2" and "redis-main-2 pod memory at 94%" are semantically equivalent but would miss L1. L2 catches these via embedding similarity.

### Key Structure

```
llm:l2:{tenant_id}:{embedding_hash}   (valkey-search HNSW index entry)
```

The HNSW index entry stores the embedding vector. The index entry value points to the L1 key where the cached response is stored:

```
HNSW index entry value: "llm:l1:a3f8c2d1e9b047f6..."
```

L2 does not store the response itself — it is an index into L1. This avoids data duplication.

### Similarity Threshold

Cosine similarity threshold: **>= 0.92**

This threshold is derived from Stage 3.5 analysis. The threshold is intentionally high because a wrong cache hit produces a wrong answer delivered with false confidence — worse than a cache miss. At 0.92 cosine similarity, two queries must be semantically near-identical, not merely related.

Hit rate target: 40-70% on repeated triage signatures during incidents (Stage 3.5).

### Per-Tenant Namespace

Cross-tenant semantic cache hits are incorrect by design. A "high memory alert on redis-main" for tenant A refers to tenant A's infrastructure. The same phrasing for tenant B refers to different infrastructure with different runbooks and different context.

Tenant ID is always part of the HNSW namespace. valkey-search supports prefix-based namespace scoping via index filter expressions.

### TTL

L2 entries: 6 hours. L2 entries point to L1 keys. If the L1 key has expired, the L2 lookup returns a miss (the L1 key is gone). paladin-gateway detects this and falls through to the LLM.

### How L2 Works End-to-End

```
1. Incoming LLM request → L1 miss
2. Extract query text from messages (user turn + system context)
3. Embed query text → 1536-dim vector (embedding model: same as RAG pipeline)
4. Search valkey-search HNSW index for tenant namespace
5. If nearest neighbor cosine >= 0.92:
   a. Read L1 key from index entry value
   b. Fetch L1 response from Valkey
   c. If L1 key exists → L2 HIT, return response
   d. If L1 key expired → L2 STALE MISS, fall through to LLM
6. If no neighbor >= 0.92 → L2 MISS, call LLM
7. After LLM response:
   a. Write response to L1 key
   b. Embed query, insert vector into HNSW index with value = L1 key
```

### Go Implementation Sketch

```go
// SemanticCacheLookup checks L2 for a semantically similar cached response.
func (c *CacheClient) SemanticCacheLookup(
    ctx context.Context,
    tenantID string,
    queryText string,
) (string, bool, error) {
    vec, err := c.embedder.Embed(ctx, queryText)
    if err != nil {
        return "", false, fmt.Errorf("embed query: %w", err)
    }

    results, err := c.valkey.Do(ctx, c.valkey.B().
        FtSearch().
        Index(fmt.Sprintf("llm:l2:%s", tenantID)).
        Query("*").
        VectorRange("embedding", 0.08). // distance = 1 - 0.92 = 0.08
        Limit().OffsetNum(0, 1).
        Build(),
    ).AsStrSlice()
    if err != nil || len(results) == 0 {
        return "", false, nil
    }

    l1Key := results[0]
    resp, err := c.valkey.Get(ctx, l1Key).Result()
    if errors.Is(err, valkey.Nil) {
        // L1 expired, stale L2 reference
        return "", false, nil
    }
    if err != nil {
        return "", false, fmt.Errorf("l2 fetch l1: %w", err)
    }
    return resp, true, nil
}
```

Note: actual valkey-search HNSW query uses COSINE distance. Distance threshold 0.08 = 1 - cosine 0.92.

## 4. L3 — Tool Result Cache

### Key Structure

```
tool:l3:{tenant_id}:{sha256(tool_name + canonical_json(args))}
```

Tenant ID is mandatory and enforced at the cache client layer — the cache client refuses to construct an L3 key without a non-empty tenant ID.

### TTL Per Tool Type

| Tool | TTL | Rationale |
|---|---|---|
| mcp-prometheus `query_range` | 30 s | Stale metrics are acceptable for agent reasoning, not for dashboards |
| mcp-loki `tail` | 15 s | Log streams change fast; stale logs miss recent errors |
| mcp-k8s `describe_pod` | 60 s | Pod state transitions slowly; 1 min stale is acceptable for triage |
| mcp-pagerduty `list_incidents` | 120 s | PagerDuty is the source of truth; 2 min stale is acceptable for read |
| mcp-slack | NOT CACHED | Slack tool calls are actions (send message, update channel) — never cache |
| mcp-github `get_file` | 5 min | Repository content changes infrequently during incidents |
| mcp-github `list_prs` | 60 s | PR list can change during deploy incidents |

Any tool not in this table defaults to 30 s TTL.

### Cache Bypass

If the incoming request includes `Cache-Control: no-cache`, paladin-gateway sets a bypass flag on the request context. The cache client checks this flag before reading L3 and skips the cache entirely. The result from the MCP call is still written to L3 on return (to warm the cache for subsequent requests).

To bypass both read and write: `Cache-Control: no-store`. This is used for debug calls.

### Partial Cache — Parallel Tool Calls

When the agent requests N tool calls in parallel:

```
Agent: [tool_a(args1), tool_b(args2), tool_c(args3)]

Cache layer:
  tool_a → L3 HIT  (return immediately)
  tool_b → L3 MISS (fire MCP call)
  tool_c → L3 HIT  (return immediately)

Result assembly:
  Wait only for tool_b MCP response.
  Merge [tool_a_cached, tool_b_fresh, tool_c_cached].
  Return merged result set to agent.
```

The cache client returns L3 hits synchronously and dispatches MCP calls for misses concurrently. The agent does not observe which results were cached vs. fresh.

### Secret Detection Before Caching

If a tool result contains secret-like patterns (API keys, tokens, credentials), it must not be cached. The cache client scans the serialized tool result before writing to L3:

```go
var secretPatterns = []*regexp.Regexp{
    regexp.MustCompile(`(?i)(api[_-]?key|secret|token|password|credential)["\s:=]+[A-Za-z0-9+/=_-]{16,}`),
    regexp.MustCompile(`sk-[A-Za-z0-9]{32,}`),           // OpenAI-style keys
    regexp.MustCompile(`xoxb-[0-9]+-[A-Za-z0-9-]+`),    // Slack bot tokens
    regexp.MustCompile(`ghp_[A-Za-z0-9]{36}`),           // GitHub personal tokens
    regexp.MustCompile(`AKIA[0-9A-Z]{16}`),              // AWS access keys
}

func containsSecret(data []byte) bool {
    for _, p := range secretPatterns {
        if p.Match(data) {
            return true
        }
    }
    return false
}
```

If a secret is detected, the result is returned to the agent but not written to L3. A metric `cache_l3_secret_skip_total` is incremented with the tool name label (no secret content in the label).

## 5. Cache Warming Strategy

All warming is asynchronous. Warming failures are logged but do not block request processing.

### On Incident Start

When PagerDuty fires an alert and an incident session is created, paladin-gateway enqueues a warming job:

1. Identify alert type from PD payload (e.g., `high_memory`, `pod_crashloop`, `slo_burn`)
2. Look up the warming playbook for that alert type (static config per alert type)
3. Pre-fire the tool calls listed in the warming playbook against MCP servers
4. Write results to L3

Example warming playbook for `pod_crashloop`:

```yaml
alert_type: pod_crashloop
warm_tools:
  - tool: mcp-k8s
    method: describe_pod
    args_template: { namespace: "{{.Namespace}}", pod: "{{.PodName}}" }
  - tool: mcp-loki
    method: tail
    args_template: { query: "{pod=\"{{.PodName}}\"}", limit: 100 }
  - tool: mcp-prometheus
    method: query_range
    args_template: { query: "container_memory_usage_bytes{pod=\"{{.PodName}}\"}", range: "1h" }
```

Template variables are filled from the PD alert payload before dispatch.

### On Shift Handover

When a new on-call engineer's session starts (detected from PD schedule or explicit handover event):

1. Identify open incidents in the tenant
2. Pre-warm L3 for tool calls that the current incident sessions have been making
3. Pre-warm L1 for runbook lookups relevant to open incident types

This reduces cold-start latency for the incoming engineer's first triage queries.

### On Integration Enable

When a tenant enables a new integration (e.g., connects Prometheus):

1. Fire a set of canary tool calls against the integration
2. Write results to L3
3. Confirm integration is reachable (side effect of warming)

## 6. Cache Invalidation Patterns

TTL-based expiry is the primary invalidation mechanism. Explicit invalidation is reserved for known content changes where stale data would produce incorrect agent behavior.

### Runbook Updated

```
Event: runbook updated (runbook_id = "rk_42")

1. Read secondary index: llm:l1:runbook:rk_42 → {l1_key_1, l1_key_2, ...}
2. DELETE each l1_key_N
3. DELETE llm:l1:runbook:rk_42
4. For L2: entries pointing to deleted L1 keys will return stale misses on next
   access — they resolve naturally (L1 key gone → L2 falls through to LLM).
   No explicit L2 cleanup required.
```

The secondary index is maintained by paladin-gateway at L1 write time: whenever a runbook lookup response is written to L1, the L1 key is added to `llm:l1:runbook:{runbook_id}` set with the same TTL.

### Integration Credential Rotated

```
Event: integration credential rotated (integration_id = "int_prometheus_prod")

1. Identify all tool names associated with this integration
2. For each tool name: SCAN tool:l3:{tenant_id}:* MATCH *{tool_name}*
   (or use a secondary index: tool:l3:integration:{integration_id} → set of L3 keys)
3. DELETE each matched L3 key
```

Using a secondary index is preferred over SCAN. At L3 write time, the L3 key is added to `tool:l3:integration:{integration_id}` with the same TTL.

### Tenant Tier Upgrade (Pool → Bridge)

When a tenant moves from Pool (shared Valkey) to Bridge/Silo (dedicated Valkey):

1. The new dedicated Valkey instance starts empty (cold)
2. Existing Pool cache keys for that tenant are left to expire naturally (TTLs are short)
3. No migration of cache data — the dedicated instance warms up organically
4. Working memory keys (Stage 5) are migrated separately (they have state, unlike cache)

## 7. Valkey Cluster Design

### Topology

```
+------------------+     +------------------+     +------------------+
|    Shard 1       |     |    Shard 2       |     |    Shard 3       |
|  Master + Replica|     |  Master + Replica|     |  Master + Replica|
|  Slots: 0-5460   |     |  Slots: 5461-10922|    |  Slots: 10923-16383|
+------------------+     +------------------+     +------------------+
```

3-shard cluster. Each shard: 1 master + 1 replica. Read from replicas for L1/L2/L3 reads (acceptable slight staleness for cache reads). Write to master.

### Memory Budget Per Tier

| Tenant Tier | Valkey Allocation |
|---|---|
| Pool | Shared cluster, per-tenant soft quota enforced via keyspace prefix + MEMORY USAGE sampling |
| Bridge | Dedicated Valkey instance (3-shard, smaller node size than Silo) |
| Silo | Dedicated Valkey instance (3-shard, full node size, tuned per tenant) |

Pool tenants share the cluster. Memory quota enforcement is soft (alert at 80%, eviction handles the rest via allkeys-lru).

### Eviction Policy

```
maxmemory-policy: allkeys-lru
```

Under memory pressure, Valkey evicts the least recently used keys across all keyspaces. Cache misses are acceptable; correctness is not compromised by eviction (the agent falls through to LLM/MCP). Working memory keys (Stage 5) on the same instance are also subject to LRU — for Silo tenants, working memory and cache are on the same dedicated instance but have separate TTL management.

### Keyspace Notifications

Enable keyspace notifications for cache miss monitoring:

```
notify-keyspace-events: Kx
```

`K` = keyspace events, `x` = expired events. This fires a notification when a key expires. paladin-gateway subscribes and increments `cache_key_expired_total` with tier label. This enables eviction rate tracking without polling.

### Memory Usage Sampling

Periodic goroutine samples MEMORY USAGE for a random subset of keys per tenant prefix. Results are written to ClickHouse for cost tracking and capacity planning. Sampling rate: 1% of keys per 5-minute window.

## 8. Anthropic Prompt Caching Integration

### What Anthropic Prompt Caching Does

Anthropic caches the prefix of requests at their infrastructure. On a cache hit, the cached prefix is not re-processed, reducing cost to 10% of the full token cost for those tokens. This is entirely separate from Valkey — it operates in-flight at Anthropic's API layer.

### Where cache_control Breakpoints Are Placed

paladin-gateway injects `cache_control: {"type": "ephemeral"}` breakpoints at two positions in every Anthropic API request:

```
[system prompt]                    ← cache_control breakpoint here (end of system prompt)
[tool catalog (all MCP tools)]     ← cache_control breakpoint here (end of tool catalog)
[user messages / conversation]     (not cached — changes every turn)
```

This maximizes the cached prefix size. The system prompt (~2k tokens) and tool catalog (~8k tokens for full MCP catalog) are identical across all requests in a session and across sessions for the same tenant configuration.

### How paladin-gateway Manages This

paladin-gateway constructs every Anthropic request with these breakpoints unconditionally. No request is sent without them. This is enforced in the Anthropic client wrapper:

```go
// BuildAnthropicRequest constructs an Anthropic API request with prompt cache breakpoints.
func BuildAnthropicRequest(session *Session, userMessages []Message) anthropic.Request {
    return anthropic.Request{
        Model: session.Model,
        System: []anthropic.ContentBlock{
            {
                Type: "text",
                Text: session.SystemPrompt,
                CacheControl: &anthropic.CacheControl{Type: "ephemeral"},
            },
        },
        Tools: appendCacheControl(session.ToolCatalog), // cache_control on last tool
        Messages: userMessages,
    }
}
```

### Interaction with Valkey Cache

Both caches are always active simultaneously. They are independent layers:

```
Valkey L1/L2 cache:   application-level, before Anthropic API call
Anthropic cache:      provider-level, during Anthropic API call (if Valkey misses)
```

Cost hierarchy per request:

| Scenario | Cost |
|---|---|
| Valkey L1 or L2 hit | $0 (no Anthropic API call) |
| Valkey miss + Anthropic cache hit | ~10% of full call cost (cached prefix not billed at full rate) |
| Valkey miss + Anthropic cache miss | 100% of full call cost |

### Cost Calculation

For a typical alert triage request with 10k input tokens (2k system + 8k tool catalog + context):

```
Full call cost:                 10,000 tokens × $3/Mtok  = $0.030
Anthropic cache hit (prefix):  10,000 tokens × $0.30/Mtok = $0.003
Valkey L1/L2 hit:              $0.000
```

During active incidents, the cache hit distribution target:
- Valkey L1 hit: 20-30% of requests (exact repeats)
- Valkey L2 hit: 40-70% of remaining requests (semantic matches)
- Anthropic cache hit: ~90% of Valkey misses (system prompt + tools always cached)
- Full call: <5% of total requests

### Per-Tenant Hit Rate

Per-tenant hit rate is tracked separately to identify tenants with unusual cache behavior:

- High miss rate → tenant is generating highly variable queries (may need warming tuning)
- Abnormally high hit rate → tenant may have a stuck incident loop (same query repeated excessively)

### Latency Impact

Latency metrics are captured with cache hit/miss labels to measure actual impact:

```
cache_request_duration_seconds{cache="hit", tier="l1"}  → P50, P95, P99
cache_request_duration_seconds{cache="miss", tier="l2"} → P50, P95, P99
```

Expected impact (targets):
- L1 hit: <5ms P99 (Valkey read)
- L2 hit: <30ms P99 (Valkey embed + HNSW search + Valkey read)
- L3 hit: <5ms P99 (Valkey read)
- L3 miss: <500ms P99 (MCP call latency dominates)

```yaml
alert: SemanticCacheHitRateLow

      (rate(cache_hit_total{tier="l2"}[15m]) + rate(cache_miss_total{tier="l2"}[15m])) < 0.30

  summary: "L2 semantic cache hit rate below 30% for 10 minutes"
```

L2 hit rate below 30% indicates the semantic cache is not functioning as intended. Possible causes:
- Embedding model changed (vectors from old model are incompatible)
- Incident type is genuinely novel (no cached triage signatures match)
- HNSW index is corrupted or empty (Valkey restart without persistence)
- Threshold 0.92 is too high for current alert phrasing variance

## 10. Cache Security

### Keys Never Contain Raw Data

All cache keys are hashes. No cache key contains a prompt, query text, tool argument value, or any user-supplied string in plaintext. The sha256 hash is one-way — a leaked cache key reveals nothing about the underlying request.

### L3 Secret Detection

As described in section 4, tool results are scanned for secret patterns before L3 write. If a secret pattern is detected:

1. Result is returned to the agent (the agent gets correct data)
2. Result is NOT written to L3 (no secret persisted in Valkey)
3. Metric `cache_l3_secret_skip_total` is incremented
4. Log entry at WARN level: tool name, tenant ID, pattern type matched (no secret value logged)

### Tenant Isolation Enforcement

The cache client layer enforces tenant isolation structurally:

```go
type CacheClient struct {
    tenantID string  // set at construction time, immutable
    valkey   *valkey.Client
}

// NewCacheClient constructs a tenant-scoped cache client.
// tenantID is mandatory and validated to be non-empty.
func NewCacheClient(tenantID string, v *valkey.Client) (*CacheClient, error) {
    if tenantID == "" {
        return nil, errors.New("cache: tenant_id is required")
    }
    return &CacheClient{tenantID: tenantID, valkey: v}, nil
}
```

All key construction methods are methods on `CacheClient` and embed `c.tenantID` — it is impossible to read or write a key for a different tenant using this client. Shared Valkey cluster access uses the same client type; tenant isolation is enforced in software, not by separate Valkey instances (except for Silo tenants who have dedicated instances).

### No Cross-Tenant L2 Lookups

The valkey-search HNSW index is scoped per tenant. The index name includes the tenant ID:

```
FT.CREATE llm:l2:{tenant_id} ...
```

Lookups always query the tenant-scoped index. There is no global HNSW index.

### Valkey Auth and TLS

- Valkey cluster requires AUTH with a per-environment token (no anonymous access)
- All connections use TLS (cluster inter-node and client-to-cluster)
- Credentials stored in Doppler, injected as environment variables at runtime
- paladin-gateway and agent-runtime connect with separate Valkey credentials (least privilege)

## Summary of Cache Key Taxonomy

| Tier | Key Pattern | TTL |
|---|---|---|
